Docs-only research change (see proposal.md — Why, Current state): the deliverable is one verified findings + comparison document with a ranked recommendation, and the implementation it informs is a separate follow-up proposal. This design fixes how the research is conducted — the experiment rig, the comparison method, and the boundaries the deliverable must record — so its claims are evidence, not inspection dressed as evidence.

## Context

- One spawn seam: every afk-runner stage agent reaches its binary through `runStageAgent` (`afk-runner/src/agent-layer.ts:253`) → review-loop `runAgent` → `buildAgentCommand` (`review-loop/src/agent-command.ts:286`). The opencode branch (`opencodeCommand`, agent-command.ts:133–150) builds no config and inherits `process.env` unchanged; afk-runner sets no `OPENCODE_CONFIG_CONTENT`, so its agents run under whatever ambient/default opencode config the invoking environment provides — no runner-owned MCP surface exists. The claude route has an MCP seam (`defaultCreateClaudeSpawnDir`, review-loop/src/agent-command.ts:71–79, an intentionally empty `{mcpServers:{}}` doc behind `--strict-mcp-config --mcp-config`) that afk-runner cannot reach — `runSpawn` (agent-layer.ts:226–251) threads no backend option.
- "Levels of task work" are code, not concepts: per-role (`AgentRoleSchema`, `afk-runner/src/config.ts:11–20`), per-stage (seven spawn sites: estimator, drafter, reviewer/skeptic, review resolver, escalation resolver, decomposer, atomicity), per-depth (S/M/L caps/tail shape). `modelFor` (config.ts:127) is the existing per-role hook and is currently role-insensitive; `RunnerConfigSchema` is a strict six-key object (config.ts:49–69).
- Binary-level MCP mechanics are on record from the sibling research (`opencode-agent/docs/mcp-integration-research.md`): config block shapes, `<server>_<tool>` naming, `<server>_*` grants living in each profile's own permission map, the `ask` deadlock, the OAuth dead end, 30s-bounded failure degradation, and the `AGENT_MCP_SERVERS` + `buildOpencodeConfig` single-seam injection. That injection point is the opencode-agent workspace's; afk-runner runs none of it.
- papai-core precedents are cites, not imports: `src/mcp/` (papai as MCP client — pooled streamable-http connections, allow/deny tool filters, three-state `tool_prefs`) and `src/mcp-server/` (papai hosts plugin tools at `/mcp/plugin/<pluginId>` — a candidate remote server runner agents could consume).
- Constraints: `skip_specs: true`, Capabilities: none; no changes to `afk-runner/src/**`, `review-loop/src/**`, tests, workflows, or runtime config; live experiments are required by the proposal's Verification section and must be credentialess and pid-disciplined; the security doctrine carries forward — an `mcp` entry is executable configuration.

## Goals / Non-Goals

**Goals:**

- A repeatable experiment rig that drives the pinned real binaries through the same spawn shape afk-runner's agents use, so every behavioural claim in the deliverable is either **verified** or explicitly labelled **by inspection**.
- A decided comparison method — scoring dimensions fixed before anything is ranked — for the four injection surfaces (proposal Required content 1, options a–d) and the four scoping axes (role/stage/depth/global).
- The merge-vs-override experiment the prior research left pending, run against afk-runner's spawn path in both configurations (ambient-only and content-set).
- A ranked recommendation with named follow-ups and an outline of the implementation change, in exactly the shape proposal Required content 5 asks for.

**Non-Goals:**

- No production code and no config schema. The follow-up implementation change owns the design decisions about `RunnerConfig` shape and injection code; this design only fixes how the research compares options.
- No credential-containment design (loopback proxy / value scrubbing) — recorded as a follow-up, as in the prior research.
- No general MCP marketplace survey — the catalogue is bounded to candidates the repo already names (D5).
- No design of the claude-backend threading through afk-runner's seam — recorded as a prerequisite finding only (proposal Required content 1d).

## Decisions

**D1 — One deliverable, re-grounded, not copy-cited.** `docs/architecture/afk-runner-mcp-research.md`, SPDX header, evidence-first section order, and per-claim **verified**/**by inspection** labels with `file:line` anchors — the sibling doc's conventions. The prior research's conclusions are inputs to re-verify against afk-runner's path, not portable findings: afk-runner sets no `OPENCODE_CONFIG_CONTENT` (so "config content is model-readable" binds the *follow-up's* options, not afk-runner's current state) and runs no `buildOpencodeConfig` (so the verified single-seam injection point does not exist here). Alternative considered: a short addendum to the sibling doc — rejected because the spawn paths differ materially and afk-runner's docs home is `docs/architecture/`, beside `afk-runner.md`.

**D2 — Experiment rig: the review-loop spawn shape.** Experiments drive the real pinned binaries exactly as `buildAgentCommand` composes them — opencode: `opencode run --dir <cwd>` under the environment afk-runner's children actually inherit (unchanged `process.env`, plus explicitly-set `OPENCODE_CONFIG_CONTENT` variants when testing option (a)); claude: the native profile block (`--strict-mcp-config --mcp-config <doc>`) with a non-empty doc replacing what `defaultCreateClaudeSpawnDir` writes empty, driven through review-loop's claude spawn path since afk-runner cannot reach it today. Stub MCP servers are throwaway fixtures in a temp dir (the prior research's minimal trace-logged JSON-RPC responder pattern); every child records its pid before `exec` and teardown kills recorded pids only, never by name; only placeholder credential values appear anywhere. Harnesses are ephemeral — not committed — and the doc records reproduction commands instead. Alternative considered: committed fixtures under `tests/afk-runner/` — rejected: the change's Files-to-touch list forbids tests, and the doc must stand on its own recorded commands.

**D3 — The merge-vs-override experiment is a first-class deliverable, run twice.** The prior research's pending experiment (whether a repo-local `opencode.json` under the spawn cwd loads at all, and merges with or overrides pipeline-provided config) is more consequential here than there, because option (a) would set `OPENCODE_CONFIG_CONTENT` and option (b) would rely on ambient file discovery. So it runs in both configurations: **ambient-only** (afk-runner's current state — is the file loaded, from the spawn cwd and from `--dir`?) and **content-set** (does a discovered file merge with, override, or lose to `OPENCODE_CONFIG_CONTENT`, including pipeline-owned permission blocks). An option whose behaviour cannot be verified live carries that label into the ranking and is scored as an explicit unknown, never a guess (proposal Required content 1).

**D4 — Scoping comparison scored on dimensions fixed before ranking.** Per-role vs per-stage vs per-depth vs global compared on five dimensions, decided now and applied unchanged: (1) **trust edge** — who can influence the server set; (2) **blast radius** — which agents get work servers vs read-only checking servers (reviewer/skeptic vs drafter/decomposer), and how grants differ per level; (3) **config surface** — extension of the strict six-key `RunnerConfigSchema` vs an env knob vs a separate file, scored on what the operator must know and what validation catches (the schema is strict, so an extension is a deliberate schema change — the follow-up's to design); (4) **grant composition** — how the shape emits opencode `<server>_*` per-profile grants and claude-side equivalents per level, and how it composes with the `modelFor` per-role hook precedent; (5) **cost profile** — whether the shape pays server startups for stages that never use the tools. The recommendation names one shape and its config surface; a mixed shape (e.g. global set + per-role narrowing) may win but is stated as the composition it is.

**D5 — The server catalogue is bounded by repo precedents, not a survey.** Candidates: a structural code index server (the `codeindex` pattern); papai-hosted remotes (`/mcp/plugin/<pluginId>`, context-vault) — reachable only over streamable-http per papai's pool, which local stdio-spawned routes must be measured against; task-tracker access (Kaneo/YouTrack-shaped); web search. Each entry records transport constraints, the install/pinning story for stdio servers on ephemeral runners, and startup/timeout behaviour (the 30s bound on record). Sources are the repo's own docs and code anchors; external servers appear only as shape examples, not endorsements.

**D6 — The security doctrine is a gate on every option, restated per surface.** Carried from the prior research and binding here: an `mcp` entry is executable configuration — a `local` entry is arbitrary command execution, a `remote` entry is an exfiltration endpoint over unrestricted egress; anything a credential reaches in config content is model-readable on the `OPENCODE_CONFIG_CONTENT` route (S3-9 class) and readable by children on the claude route; untrusted text — task files, chat messages, issue bodies — never defines a server, on any option, as a design decision needing no binary evidence; unattended grants are `allow` or absent, never `ask`; degradation is never a hang (30s bound), with the one on-record caveat that a status poller must bound its own calls. The deliverable also records what the runner should emit/log when a server fails (L0/L1 agent events — `agent-noise-schemas.ts` is the existing event surface) so a dead server is visible without failing the run (proposal Required content 4).

**D7 — The ranking and follow-up outline obey the proposal's shape.** Ranked from the D4/D6-scored tables; each named follow-up states its own change's capability name at **feature-domain granularity** (an implementation change named for the afk-runner MCP injection surface, not one micro-change per experiment), a sketch of the config surface and injection point, and the two already-deferred items — credential containment, per-server opt-out — recorded as their own follow-ups. The outline is proposal-shaped: what the implementation change would decide, not how it is implemented.

**D8 — The deliverable records the system boundaries explicitly, so the follow-up cannot conflate them.** Four statements the doc must carry:

- **Gating / tool-prefs.** Afk-runner's stage agents are opencode/claude subprocesses gated by opencode permission maps (`<server>_*` keys inside each profile's deny-by-default map) and the claude CLI's own `--mcp-config`/allowlist surface — papai-core's capability gating and per-context `tool_prefs` do **not** apply to them, because the runner is an MCP client outside papai's context model. Conversely, consuming a papai-hosted server (`/mcp/plugin/<pluginId>`) from a runner agent bypasses papai's `tool_prefs` allow/deny resolution entirely — a stated consequence, not a defect to fix here.
- **Scope model.** This change adds no persisted state — the deliverable is repo content keyed to nothing (no storage context id, config context id, platform instance id, or user id). The follow-up's config, whatever surface wins in D4, keys at the **runner level** (per-invocation afk-runner config file or env), outside papai's per-user/group scope model entirely.
- **Dependency surface.** None. No DB change (no drizzle migration, no backfill), no new packages — the experiments consume the already-pinned binaries (`opencode-ai@1.18.7` as the workflow installs; `@anthropic-ai/claude-code@2.1.251` per review-loop's pin) and the zod-declared shapes already on record. No new module is created: the doc sits in the existing `docs/architecture/` home beside `afk-runner.md`, and the sibling research doc is cited, never imported — afk-runner's copy-never-import discipline applied to its docs layer.
- **Hook surface.** The write-hook pipeline gates the three file writes — the new doc (SPDX header mandatory, licence-header gate) and the two pointer edits (`afk-runner.md`, CLAUDE.md table) — for headers/format; docs are not gateable implementation code, so no TDD test pair and no mutation floor applies (a docs-only diff selects zero Stryker targets). The change's own order of work: experiments → evidence recorded → doc drafted → `bun run lint` / `typecheck` / `format:check`.

## Risks / Trade-offs

- [Live experiments spawn real binaries and stdio children that can outlive them] → pid-record-before-exec teardown, kill by recorded pid only (never by name), post-experiment hygiene check; a hung child is itself bounded by the binary's 30s timeout.
- [Findings drift with any pin bump] → every behavioural claim anchored `file:line` with a re-verify note, the sibling doc's convention.
- [The merge-vs-override experiment may not be verifiable in the available environment] → the affected option carries the unverified label into D4's ranking and is scored as an explicit unknown; the ranking states which conclusions it changes.
- [A research doc reads as authorization to implement] → the recommendation section frames the implementation change as a separate follow-up proposal; this change's Capabilities section records none.
- [Doc examples could leak real tokens into a committed file] → placeholder values only; the licence-header and format/lint gates apply to the new file on write.
- [The per-stage axis could tempt a sprawling recommendation the runner cannot validate] → D4's cost-profile dimension and D7's feature-domain-granularity outline keep the recommendation to one shape with a config surface small enough for the follow-up to propose.

## Migration Plan

Docs-only rollout: land the research doc (SPDX header required by the licence gate), the optional one-line pointer in `docs/architecture/afk-runner.md`, and the CLAUDE.md docs-table row. Rollback is `git revert` of the docs commit; no runtime surface exists to migrate or un-migrate.
