## Purpose

Builds and maintains the per-group knowledge-base corpus via a chunk, normalize, and embed pipeline with scheduled reindex and LLM-judged distillation, so retrieval always serves fresh, scrubbed, and vetted knowledge.

## ADDED Requirements

### Requirement: Chunk, normalize, and secret-scrub pipeline
The system SHALL normalize every source document (strip code fences to raw code, strip HTML tags, remove image markup, inline links as `text (url)`, strip backticks, collapse whitespace) before chunking; split by headings into sections, target 500 tokens (`cl100k_base`) with 50-token overlap, and hard-split oversized sections at codepoint and line boundaries so chunks are sequences of complete lines never breaking multi-byte characters; embed via Vercel AI SDK and store as float32 BLOBs. The system SHALL scrub secret-shaped strings before normalize/chunk/embed (Bearer values, credential-like `key=value`, vendor-prefixed tokens `glpat`/`ghp`/`xox`, `AKIA` keys, 32+ hex runs, JWTs) replacing them with `[REDACTED]`; if a document normalizes to empty the system SHALL still delete prior chunks for that `source_type`/`source_ref` so stale chunks do not survive.

#### Scenario: Oversized section is hard-split on line boundaries
- **WHEN** a section exceeds 500 tokens and contains markdown table rows
- **THEN** chunks are split at line starts within the token budget and no chunk starts mid-word inside the table

#### Scenario: Secrets are redacted preserves ticket IDs and URLs
- **WHEN** a thread contains `Bearer eyJ...` and an internal URL `https://tracker/ISSUE-123`
- **THEN** the Bearer value is replaced with `[REDACTED]` while the issue URL and ticket id remain in the chunk

#### Scenario: Empty document purges stale chunks
- **WHEN** a previously indexed source ref now normalizes to empty
- **THEN** the system deletes all chunks for that `source_type`/`source_ref` and inserts zero new rows, leaving no orphans

### Requirement: Curated KB source and optional GitLab README source
The system SHALL index a per-config-context curated knowledge-base file and, when configured, a GitLab README fetched via `providerRuntime.httpFetch`. The curated KB SHALL be read from the configured path/URL declared as optional (`required: false`) in `configRequirements` (scope `context`) — unset curated KB does not gate `eligible` and reindex simply skips that source — re-indexed when its content hash changes and skipped when unchanged. The curated KB path SHALL be validated allowlisted, without traversal, sandboxed to `KNOWLEDGE_BASE_DATA_DIR` (optional env, default `./data/knowledge-base` resolved to absolute once at startup via cached `path.resolve(process.cwd(), KNOWLEDGE_BASE_DATA_DIR)` — if env value is already absolute it is used directly without `process.cwd()`; relative values are anchored to startup WorkingDirectory and cached, not re-resolved per tick — before jail checks; directory created on demand with 0755 if missing (mkdir respects umask; EACCES/EROFS on read-only volume surfaces via plugin_runtime_events per Decision 6); `No env var required` in proposal refers to plugin activation, not this optional data-dir override), jail via `path.resolve` + `startsWith` with directory-boundary check then `realpath` (symlink-resolved) + `startsWith` re-check with boundary, then atomic `open` + `fstat` size check; each `startsWith` check SHALL be `(resolved === dataDir || resolved.startsWith(dataDir + path.sep))` (and same for `realpath` result) so `/data/knowledge-base-evil` does not pass when `dataDir=/data/knowledge-base`; check order SHALL be `path.resolve` → `startsWith(+sep||===)` → `realpath` → `startsWith(+sep||===)` → `open` (with `O_NOFOLLOW` (fallback only when platform lacks O_NOFOLLOW support; on ELOOP/EPERM from symlink do not retry without flag — fail closed — fd `realpath` re-verify still required)) → `fstat`; TOCTOU between `realpath` and `open` is mitigated by the fd re-verify; if dir is missing creation is attempted, if still missing or outside jail the source is skipped with a structured warning, not an error, with `bytesLimit: 5_242_880` (5 MiB) enforced as file-size limit for local `fs` reads — pre-checked via `fstat` and enforced during read as a byte-counted streaming cap (`read` loop aborts at `5_242_880` even if `fstat` raced or file is sparse/pipe; `fs.readFile` without streaming limit does not satisfy this spec) — and as `httpFetch` `bytesLimit`, `rateLimit` applied only to `httpFetch` per `src/web/` conventions; traversal outside the allowlist is refused (an unsandboxed `fs` read does not satisfy this spec). If `fstat` reports `> 5_242_880` the source SHALL be skipped with a structured warning and prior chunks for that `source_type`/`source_ref` SHALL be left intact (size-gate is not an empty-document purge); only an actually empty normalized document triggers the empty-document delete-orpan rule. The curated KB URL (when fetching via `httpFetch`) SHALL be subject to the same `providerAllowedHosts` (including `providerAllowedHostsFromConfig` tiered hosts) and public-URL checks as the GitLab README — admin-sourced hosts bypass public-IP restriction, context-sourced hosts require HTTPS + public-IP validation; the fetch SHALL enforce the same `bytesLimit`/`rateLimit` as GitLab. The GitLab README SHALL only be fetched when `providerAllowedHosts` (including `providerAllowedHostsFromConfig` tiered hosts) permits the host and public-URL checks pass; admin-sourced hosts bypass public-IP restriction (operator-trusted), context-sourced hosts require full HTTPS + public-IP validation, and the fetch SHALL enforce `bytesLimit: 5_242_880` (5 MiB) and `rateLimit` per `src/web/` conventions (same limits as curated-KB `httpFetch`). Both sources SHALL produce chunks with `source_type` `curated_kb` and `readme` respectively and `source_ref` as the stable permalink/blob URL.

#### Scenario: Curated KB unchanged skips embedding
- **WHEN** the curated KB file hash equals the stored cursor hash and chunks still exist for that ref
- **THEN** reindex does not call embed or rewrite chunks for that source

#### Scenario: GitLab host blocked by allowlist is not fetched
- **WHEN** the configured GitLab URL's host is not in `providerAllowedHosts` nor in the tiered dynamic hosts
- **THEN** the fetch is refused, no chunks are indexed for that source, and a structured warning is logged without leaking the token

#### Scenario: README fetch respects curated KB independence
- **WHEN** GitLab README fetch fails transiently
- **THEN** curated KB chunks remain intact and serve retrieval; the failure does not purge other sources

### Requirement: Embedding batching and SQLite storage
The system SHALL embed chunks in batches of at most 32 texts with bounded concurrency (`p-limit` 3) through the per-config-context LLM provider (central creds with BYOK override resolved per `storageContextId` group mapping), serialize embeddings as raw float32 BLOBs (`toBlob`/`fromBlob`), and persist to SQLite `chunks` with hand-written migration `src/db/migrations/<seq>_knowledge_base.ts` (`<seq>` is the next sequential number after the current max in `src/db/migrations/` per `src/db/migrate.ts:validatePairwiseOrder`) (`Migration { id, up(db) }` via `src/db/migrate.ts`) partitioned by `config_context_id TEXT NOT NULL` — columns `id INTEGER PRIMARY KEY, config_context_id, source_type, source_ref, content, embedding BLOB NOT NULL, content_hash, indexed_at, kind, source_date` with compound UNIQUE index on `(config_context_id, source_type, source_ref)` — `embedding` SHALL be `BLOB NOT NULL` (raw float32 via `toBlob`/`fromBlob`; NULL embeddings are not scorable and would corrupt the dimension guard `byteLength !== queryDims * 4`) — isolating each group's corpus and guaranteeing idempotent delete-then-insert (non-unique index would allow duplicate rows on retry), with `PRAGMA busy_timeout=5000` SHALL be set at DB connection open (`src/db/index.ts`/`src/db/drizzle.ts`, not inside the migration transaction per `src/db/migrate.ts:114`) and retry on `SQLITE_BUSY` so concurrent live `ask_knowledge_base` reads and future `feedback` writes (write path deferred this change) do not surface `SQLITE_BUSY` as user-visible errors. The migration SHALL also create `knowledge_base_cursors` as `(config_context_id TEXT PRIMARY KEY, watermark_ts INTEGER NOT NULL, watermark_id TEXT NOT NULL)` holding one lexicographic watermark per group, and `knowledge_base_thread_archive` / `knowledge_base_feedback` per the Channel crawl and Feedback requirements. Writes per document SHALL be a single transaction `DELETE` by exact `config_context_id, source_type, source_ref` then `INSERT`s; an embedding count mismatch SHALL fail the document with an error.

#### Scenario: Batched embed respects limits
- **WHEN** a document yields 70 chunks
- **THEN** the system makes three embed calls (32, 32, 6) with concurrency bounded to 3 overall, not unbounded parallel calls

#### Scenario: Embedding count mismatch fails closed
- **WHEN** the embed provider returns fewer vectors than chunks for a document
- **THEN** the transaction is not committed and the document's prior chunks remain or are left for retry, with an error logged without chunk content

### Requirement: Scheduled reindex and distill jobs per eligible config-context
The system SHALL register two scheduled jobs `plugin:knowledge-base:reindex` (`intervalMs: 30*60*1000`) and `plugin:knowledge-base:distill` (`intervalMs: 15*60*1000` global per owner; per-context `distill_interval_ms` override is deferred — `PluginScheduledJob { intervalMs: number }` and `scheduler.register(owner, { interval: job.intervalMs })` register one interval per owner, not per config-context; any future per-context throttle SHALL be intra-sweep debounce (`lastDistillAt` per config-context) not a scheduler re-register; absent key means default 15 min; knowledge-base standalone `DISTILL_CRON` is not a papai `PluginScheduledJob` field — `src/plugins/runtime-types.ts:126` `intervalMs:number` and `src/plugins/contributions.ts:92` `scheduler.register` use intervals) that run only for contexts where the plugin is enabled and eligible (thread-isolated check against the group config-context; `defaultEnabled` contexts with `null` `task_instance_id` are not `configured` and are not scheduled by default per `src/plugins/scheduled-contexts.ts`, requiring explicit enable). The reindex job SHALL re-index `readme` and `curated_kb` (no external crawl); the distill job SHALL drain the distillation pipeline for `channel` tier. Both jobs SHALL be idempotent: repeating without new content produces no new chunks and leaves `cursors` unchanged. The scheduler SHALL process eligible contexts sequentially (`src/plugins/contributions.ts:172` reduce chain) with bounded embed concurrency (`p-limit` 3 within a context) and isolate per-context failures so one group's failure does not abort others. The scheduler SHALL enforce skip-if-running per job owner (plugin-owned in-flight guard checked at tick entry — `src/utils/scheduler.internal.ts:284` `setInterval` ticks `executeTask` without a cross-tick guard today — the plugin SHALL gate its own sweep with an `activeSweep` per-owner flag: if a previous sweep has not completed when the next `intervalMs` fires, the new tick SHALL be skipped with a structured `pino` info log, not queued concurrently, so at most one `reindex` and one `distill` sweep run at a time on the single `bun:sqlite` file even though the core scheduler does not itself skip overlapping interval ticks); per-context work SHALL have per-LLM-call timeouts so one slow context does not indefinitely block later contexts.

#### Scenario: 30-minute reindex is idempotent
- **WHEN** reindex runs twice with no source change
- **THEN** the second run performs hash/SHA comparisons, skips embedding, and chunk counts remain unchanged

#### Scenario: Distill runs independent of crawl
- **WHEN** a `JUDGE_VERSION` bump makes many threads pending re-judge but no new Mattermost posts arrived
- **THEN** the distill job alone drains the pending queue without requiring a crawl, and crawl outage does not block distillation of already-archived threads

### Requirement: Channel crawl, archive, and exclusion rules
The system SHALL ingest channel threads from locally persisted papai channel history (`message_metadata`/archived thread JSON) grouped by thread root derived via `replyToMessageId` chain traversal (`message_metadata` has no `root_id` column — `src/db/schema.ts:170` defines `replyToMessageId`, `groupContextId`; ingest reconstructs threads by batched `WHERE groupContextId = ?` load per `configContextId` (`groupContextId` is derived as `getConfigContextIdFromStorageContextId(storageContextId)` per `src/bot-message-caching.ts:22-29` — i.e. `groupContextId === configContextId`, no `known_group_contexts`/`context_settings` join; `WHERE groupContextId = ?` is served by `idx_message_metadata_group_ctx`; in-memory `replyToMessageId` walk is bounded: visited-set cycle guard, max depth 100, cross-batch missing parent treated as orphan thread root; `idx_message_metadata_reply_to` is on `(contextId, replyToMessageId)` (thread-scoped) and is not used for the group-scoped scan — the walk is an in-memory grouping of the batched group rows, not indexed point lookups by `groupContextId`) with `groupContextId` nullable — rows with `groupContextId IS NULL` (legacy pre-070 or DM context) are not returned by `WHERE groupContextId = ?` and are reaped by a periodic `WHERE groupContextId IS NULL` scan that backfills via `getScopeKey('group',...)` or skips with a per-run counter — owned by `plugin:knowledge-base:distill` sweep (piggybacked as first step of each `distill` tick before batched group ingestion, bounded `LIMIT 200` per tick, per-row failure isolated, `pino` info counter `{scanned, backfilled, skipped, durationMs}` and `plugin_runtime_events` per owner)) , orphan reply chains treated as own thread) and storing every non-excluded thread into `thread_archive` (composite PK `(config_context_id, thread_id)`, where `thread_id` is the thread's root `messageId`; for orphan reply chains without a resolvable root parent the orphan's own `messageId` serves as `thread_id` so PK is stable per-group and `source_ref` permalink prefix remains consistent, `root_created_at`, `last_post_at`, raw `raw_json`, `content_hash` over normalized message texts only, `score`, `judge_json`, `judged_hash`, `judge_version`, `judge_attempts`, `judged_at`, `reactions_checked_at`) partitioned by `config_context_id` — `channel_id` is not a separate column (pap​ai `message_metadata` has no `channel_id`; the group identity is `config_context_id`/`groupContextId` via `getScopeKey`) and `raw_json` is the JSON-serialized array of the thread's `message_metadata` rows (text, authorId, timestamp, replyToMessageId) for that `thread_id`, not an external Mattermost payload; `content_hash` is SHA-256 over scrubbed+normalized message texts only; `root_created_at`/`last_post_at` are min/max `timestamp` of the thread's rows; the migration SHALL also create a compound index `idx_message_metadata_group_ctx_ts_msg ON message_metadata(group_context_id, timestamp, message_id)` (`CREATE INDEX IF NOT EXISTS`) to back the watermark resume query — rerun/partial-apply does not error); `knowledge_base_cursors` holds the watermark as `(config_context_id TEXT PRIMARY KEY, watermark_ts INTEGER NOT NULL, watermark_id TEXT NOT NULL)` holding one row per `configContextId`; when no row exists the initial watermark SHALL be `(0, '')` (epoch `0` and empty `messageId` lexical minimum) so the first run resumes as `WHERE (timestamp, messageId) > (0, '')` and ingestion is bounded per tick (`LIMIT 200` per `configContextId` batch, sequential cursored paging — first run does not scan unbounded history in one transaction). The watermark SHALL advance transactionally only after successful `thread_archive` upsert batch commit — `UPDATE knowledge_base_cursors SET (watermark_ts, watermark_id)=MAX(timestamp,messageId)` is in the same `db.transaction()` as the archive writes; on mid-batch throw (`LLM timeout`, `SQLITE_BUSY`) the transaction rolls back and the watermark does not advance, so unarchived threads are re-scanned next tick (60s overlapping window covers clock skew, rollback covers failure). Knowledge-base standalone paging/pacing details (page size 60, pacing 200ms, retries on 429, cursor by id) apply to Mattermost REST crawling and are replaced in papai by batched local ingestion with a lexicographic tuple watermark `MAX(timestamp, messageId)` per `configContextId` — resume as `WHERE groupContextId = ? AND (timestamp, messageId) > (watermark_ts, watermark_id) ORDER BY timestamp ASC, messageId ASC` (`timestamp INTEGER`, `messageId TEXT` lexicographic tie-break matching `ORDER BY`; timestamp is the primary key and millisecond-granular insertion time so same-timestamp collisions are rare; `messageId` tie-break uses TEXT lexical compare consistent with the `ORDER BY`/`WHERE` tuple, which is a total order even when numeric provider IDs do not sort numerically — ordering remains consistent for resume, only delivery order within the same millisecond may be lexical rather than numeric; the `timestamp >= watermark_ts - 60 AND (timestamp, messageId) > (watermark_ts, watermark_id)` AND form does not re-scan `[watermark-60, watermark)` — the 60s clock-skew guard is a bounded overlapping re-scan `WHERE groupContextId = ? AND timestamp BETWEEN watermark_ts - 60 AND watermark_ts ORDER BY timestamp ASC, messageId ASC` merged in-memory and deduped via already-archived `thread_id`/`content_hash` so late inserts are not missed) — `ws` crawl of `helpChannelId` (`src/mm/client.ts`) is a non-goal. The ingestor SHALL make zero LLM calls and SHALL exclude exactly: root authored by the bot or `:no-bot:` in any message text (implementable from `message_metadata` columns `authorId`/`text`). `type` starting `system_` and `no-bot`/`no_bot` reactions require columns `type`/`reactions` that `message_metadata` (`src/db/schema.ts:170-186`) does not store — those standalone exclusions are not normative in pap​ai until such columns exist; retroactive reaction purge and `system_` filtering are deferred (no-op) and `reactions_checked_at` is reserved for that future. Those active exclusions SHALL stay in code, not in the judge prompt. Bot-authored replies SHALL be stripped at upsert time (unstripped thread is still checked for `:no-bot:`).

#### Scenario: Excluded thread never reaches archive — reaction deferred in this change
- **WHEN** a thread is rooted by the bot or contains `:no-bot:` (reactions require absent columns and are deferred — see Channel crawl Requirement)
- **THEN** no row is written to `thread_archive` for that thread id and its orphan replies that only belong to that root are also not archived; `no-bot`/`no_bot` reaction exclusion is no-op until `message_metadata` stores reactions

#### Scenario: Crawl without LLM calls collects regardless of quality
- **WHEN** a thread has no maintainer reply and no ✅ reaction
- **THEN** it is still upserted to `thread_archive` (quality is the judge's decision, not the crawler's)

#### Scenario: Cursor resumability
- **WHEN** batched ingestion from `message_metadata` is killed mid-batch and restarted
- **THEN** it resumes from the stored `cursors` watermark as lexicographic tuple `MAX(timestamp, messageId)` per `configContextId` (`WHERE (timestamp, messageId) > (COALESCE(watermark_ts,0), COALESCE(watermark_id,''))` — initial `(0, '')` when no row exists, bounded `LIMIT 200` per tick — ordered `timestamp ASC, messageId ASC` filtered by `groupContextId`) and does not duplicate already-archived threads; watermark advances only after successful batch commit in the same `db.transaction()` (mid-batch failure rolls back watermark so unarchived threads are re-scanned); paging cursor-by-id semantics apply only to the knowledge-base standalone Mattermost REST crawler, not to papai local ingestion

### Requirement: LLM judge, threshold, and distillation to channel chunks
The system SHALL judge each archived thread with one sequential LLM call (prompt demanding JSON `{score: 0..1, items: [{kind: 'qa'|'issue', text}]}` tolerant of fences/prose), using per-config-context LLM creds, and render authors as numbered `[1]/[2]` without usernames. Threads with `score` at or above `KB_MIN_VALUE_SCORE` (default 0.4) and at least one `item` SHALL produce one chunk per item via the shared pipeline with `source_type='channel'`, `source_ref='<permalink>#<n>'` (Mattermost fragment preserves permalink resolvability; answer tail dedupes before `#`), `kind` and `source_date` (from `root_created_at`). For papai local ingestion from `message_metadata`, `<permalink>` SHALL be the synthetic stable identifier `papai://thread/<config_context_id>/<thread_id>` where `thread_id` is the thread's root `messageId` (for orphan reply chains without a resolvable root, the orphan's own `messageId` is used as `thread_id`; see Channel crawl requirement for thread grouping), so the `LIKE '<escaped permalink>#%' ESCAPE '\'` purge and citation tail deduping before `#` remain correct; synthetic links are internal and not external Mattermost URLs but remain stable and resolvable within papai's history. The system SHALL unconditionally purge existing `channel` chunks for that thread (`DELETE ... LIKE '<escaped permalink>#%' ESCAPE '\'`) before inserting, so re-distillation yielding fewer items leaves no orphans. Threads below threshold SHALL be stamped with `score`/`judge_json`/`judged_hash`/`judge_version`/`judged_at` with no chunks, and remain candidates for future re-judge.

#### Scenario: High-score thread yields per-item chunks with kind and date
- **WHEN** a thread scores 0.85 with two `qa` items
- **THEN** two chunks appear with refs `<permalink>#1` and `<permalink>#2`, both carrying `kind='qa'` and `source_date` equal to the thread's root date

#### Scenario: Issue kind surfaces date outside item text
- **WHEN** an item is judged `kind='issue'`
- **THEN** the chunk is stored with `kind='issue'` and the answer renderer presents it as a known problem as of that `source_date`, without the date being baked into the item text itself

#### Scenario: Re-distillation leaves no orphans
- **WHEN** a thread previously produced 3 items is re-judged and now yields 1 item
- **THEN** exactly one chunk remains for that thread; the other two `#n` rows are gone

#### Scenario: Below-threshold thread is stamped not embedded
- **WHEN** a thread scores 0.3 against threshold 0.4
- **THEN** zero chunks are inserted for it but `thread_archive` is stamped with its score and version so it is not retried until content hash or judge version changes

### Requirement: Versioned re-judge without re-crawl
The system SHALL select pending threads as `judged_at IS NULL OR content_hash <> judged_hash OR judge_version <> :current` ordered by `root_created_at` limited by `DISTILL_BATCH_LIMIT` (SQL LIMIT, not LLM batch size, sequential calls one at a time). Bumping the code constant `JUDGE_VERSION` in lockstep with the prompt SHALL cause the next distill runs to re-judge the entire history with zero Mattermost traffic, allowing previously rejected threads to become indexed if they now pass. A bump does not require Mattermost connectivity.

#### Scenario: Judge version bump retroactively rescues a rejected thread
- **WHEN** `JUDGE_VERSION` is bumped and a thread previously stamped `score=0.1` under the old prompt is now judged `0.8` with items
- **THEN** chunks are now present for that thread without any new crawl or messages

#### Scenario: Content change re-selects thread without version bump
- **WHEN** an archived thread gains a new reply changing its `content_hash`
- **THEN** the thread becomes pending and is re-judged even though `JUDGE_VERSION` is unchanged

### Requirement: Distillation error handling and attempt cap
The system SHALL fail closed on judge errors: a judge throw, non-JSON, or contract violation (score out of range, unknown kind, items not array) SHALL be caught per thread, warned with threadId and response length only (never thread text), the row left unstamped for retry, and the batch loop continues to the next thread. Repeated failures SHALL increment `judge_attempts`; after 5 consecutive failures for the same `judge_version`/`content_hash` the row SHALL be stamped `score=0` with `judge_json={error: ...}` and not selected again until version or hash changes. An embed failure mid-item SHALL leave the thread unstamped so next tick re-deletes and redoes all its items; a failure during that retry SHALL purge partial writes before recording the terminal failure to avoid orphaned chunks.

#### Scenario: One thread's judge failure does not abort batch
- **WHEN** thread B's LLM call throws and threads A and C are pending in the same `DISTILL_BATCH_LIMIT` run
- **THEN** A and C are still judged and B remains unstamped for the next distill run

#### Scenario: Permanent un-judgeable thread stops consuming slots
- **WHEN** a thread fails 5 times consecutively
- **THEN** it is stamped `score=0` and no longer returned by `selectPending` until a `JUDGE_VERSION` bump resets the counter, and a warning notes `judge attempt cap reached`

#### Scenario: Partial embed failure cleans up
- **WHEN** a three-item thread fails on the third embed after two chunks were committed
- **THEN** the retry's unconditional purge removes the two partial chunks before the next attempt, and if the cap is reached the final purge removes any partial writes before terminal stamping

### Requirement: Settings UI for sources and thresholds and encrypted credentials
The system SHALL expose settings routes for knowledge-base context config (curated KB path/url, GitLab host/route config when enabled, `KB_MIN_VALUE_SCORE`, `DISTILL_BATCH_LIMIT`, `RETRIEVAL_MIN_SCORE`) validated with `zod` (curated KB path allowlisted/sandboxed with `bytesLimit`/`rateLimit` per the Curated KB source requirement), persisted per config-context id (group-shared) and re-evaluated for `config_missing` eligibility; `curated_kb_path`/`url` and GitLab host are optional (`required: false`) so `config_missing` does not gate eligibility on their absence, while any future required key when cleared via unset/Clear makes that group's contexts report `config_missing` and hide the tool/jobs. Sensitive values SHALL be stored encrypted-at-rest and masked on read. The UI SHALL support per-platform-instance admin defaults seeding into first-time contexts without overriding already customized prefs. All credential use for LLM and GitLab fetch SHALL happen via the encrypted config facade at job/tool execution time, not at activation time, so changes take effect on the next run without restart.

#### Scenario: Threshold change takes effect next distill without restart
- **WHEN** an operator changes `KB_MIN_VALUE_SCORE` from 0.4 to 0.6 in the settings UI
- **THEN** the next distill run judges against 0.6 with no process restart; threads scoring 0.5 are now stamped below threshold with zero chunks

#### Scenario: Unset required source config marks ineligible per-context
- **WHEN** a required context config key is cleared via the settings unset action for one group's config-context
- **THEN** that group's contexts report `config_missing` and hide the tool/jobs while other groups remain eligible

### Requirement: Observability without secret leakage and per-group counters
The system SHALL emit per-run counters (`threads` crawled, `judged`/`indexed`/`failed` distilled, `chunks_indexed` per `source_type`, `maxScore`) and scheduler events via `pino` structured logs and `plugin_runtime_events`, without including thread text, chunk content, embeddings, or secrets. Dimension mismatches and contract violations SHALL warn with counts/ids/lengths only. Metrics SHALL be per config-context (group-shared) not globally merged, preserving group isolation.

#### Scenario: Metrics and logs contain only safe fields
- **WHEN** retrieval drops a chunk for dimension mismatch during a live turn
- **THEN** the warning contains `id`, `sourceRef`, `dims`, `queryDims` and not the chunk's text or embedding bytes
