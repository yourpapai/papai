## Context

See `proposal.md` for motivation. This design explains how to provide grounded Q&A (README + curated-KB + LLM-judged channel threads, tiered retrieval, cited grounded answers) as a first-party plugin `plugins/knowledge-base/` without a second bot or standalone Mattermost/WebSocket crawl.

Current state and constraints shaping the approach:

- Papai plugin system (`docs/architecture/plugins.md`, `src/plugins/types.ts:151`): trusted in-process plugins only; `apiVersion: 1`, `storageScope: 'group'` opt-in keys `plugin_kv` by `configContextId`; `contributes.tools`/`jobs`/`configKeys` gated by `permissions: ['storage','scheduler','http']`; eligibility via `getPluginContextEligibility()` is per config-context, not global; `defaultEnabled` controls first-run.
- Papai DB is `bun:sqlite` + `drizzle-orm` (`drizzle.config.ts:9`, `src/db/schema.ts:8`); the plugin must add its own drizzle tables but cannot change the connection.
- Papai LLM is Vercel AI SDK (`ai` + `@ai-sdk/openai-compatible`, `src/llm/` pattern); papai tokenizer is `ai-tokenizer` (`package.json:74`). Embeddings reuse the per-config-context provider (central creds + `ByokLlmCredentials` override).
- Papai chat routing is `ChatRouter` fan-out over `platformInstanceId`s (`src/chat/router.ts`, `src/db/instance-schema.ts`); distillation input must come through papai surfaces (archived thread JSON stored via papai), not a standalone WebSocket client.
- Scope model (`src/chat/context-scope.ts:38`, `docs/architecture/behaviors.md`): `storageContextId` is thread-scoped in groups; `configContextId = getConfigContextIdFromStorageContextId(storageContextId)` is group-shared. Capability/tool-prefs gating lives in `src/tools/tool-preferences.ts` and `src/tools/index.ts`.

## Goals / Non-Goals

**Goals:**

- Provide grounded Q&A as a `storageScope: 'group'` plugin so sibling threads in the same group share one corpus and live turns stay thread-isolated.
- Implement deterministic pipelines: `normalize`, `scrub`, `chunk`, `pipeline`, `vec`, `retrieve`, `prompts`, `judge`, `distiller`, `archive`.
- Keep zero new runtime dependencies and preserve idempotent reindex/distill under papai's scheduler.

**Non-Goals:**

- Escalation, feedback-driven retuning and Wiki ingestion, `ws` mattermost crawl, and `processed_posts` reply-claim deduplication tied to the Mattermost bot loop — see `proposal.md` Non-goals.
- Horizontal SQLite scaling; single-writer SQLite limit (ADR-0005).
- Hot reload or npm-installed marketplace distribution.

## Decisions

### 1. Plugin shape: `plugins/knowledge-base/` with `storageScope: 'group'`

**Decision:** `plugin.json` declares `id: "knowledge-base"`, `apiVersion: 1` (`src/plugins/types.ts:44`), `storageScope: "group"`, `permissions: ["storage","scheduler","http"]`, `contributes: { tools: ["ask_knowledge_base"], jobs: ["reindex","distill"], configKeys: [...] }`, `providerAllowedHosts` + `providerAllowedHostsFromConfig` for optional GitLab README fetch and for `curated_kb_url` httpFetch (both subject to the same tiered `providerAllowedHosts` + public-URL checks per `specs/knowledge-base/indexing/spec.md` Curated KB requirement). `defaultEnabled: true` so eligible groups get the corpus without manual toggle; per-context disable still respected via `plugin_context_state` (`src/db/plugin-schema.ts:21`).

**Why:** Matches the spec `knowledge-base/spec.md:8` group-shared corpus + thread-isolated turns. `storageScope: 'group'` is the only mechanism that keys durable KB state (`chunks`) by `configContextId` while still delivering scheduled/proactive work to the originating thread (the tool runtime receives raw `storageContextId` even for group-scoped plugins — `docs/architecture/plugins.md:14`). `audio-transcribe` (`plugins/audio-transcribe/plugin.json:1`) and `context-vault` show the group-scoped durables vs thread-scoped turns and tool-permissions pattern.

**Alternatives considered:**
- `storageScope: 'context'` (default) + manual `plugin_kv` namespacing — rejected: would shard chunks per thread, breaking the sibling-thread sharing scenario.
- Separate drizzle schema outside papai's DB — rejected: would require a second connection, WAL conflicts, and duplicate backup story; drizzle migration in the single `bun:sqlite` file is operationally simpler.

### 2. DB ownership: four new tables in the main papai DB, prefixed `knowledge_base_`

**Decision:** Add drizzle tables `knowledge_base_chunks`, `knowledge_base_thread_archive`, `knowledge_base_cursors`, `knowledge_base_feedback` (columns `id, source_type, source_ref, content, embedding BLOB NOT NULL, content_hash, indexed_at, kind, source_date` + `(source_type, source_ref)` index; `thread_archive` with `thread_id, root_created_at, last_post_at, raw_json, content_hash, score, judge_json, judged_hash, judge_version, judge_attempts, judged_at, reactions_checked_at` + the two archive indexes; `cursors` as `(config_context_id TEXT PRIMARY KEY, watermark_ts INTEGER NOT NULL, watermark_id TEXT NOT NULL)`; `feedback (config_context_id, answer_id, voter) PK`). Add a `config_context_id TEXT NOT NULL` column on `chunks`, `thread_archive`, and `knowledge_base_feedback` (composite PK `(config_context_id, answer_id, voter)` for feedback and composite PK `(config_context_id, thread_id)` for `knowledge_base_thread_archive` so `thread_id` uniqueness is per-group not global; `knowledge_base_chunks` keeps `id` PK with unique index `(config_context_id, source_type, source_ref)`) plus `knowledge_base_cursors` as one watermark row per group `configContextId` `(config_context_id TEXT PRIMARY KEY, watermark_ts INTEGER NOT NULL, watermark_id TEXT NOT NULL)`. Create compound UNIQUE index `(config_context_id, source_type, source_ref)` on `knowledge_base_chunks` (enforces idempotent delete-then-insert) and compound index `(config_context_id, judged_at, root_created_at)` for `selectPending` tier fetch.

Scope model impact: `knowledge_base_chunks` / `knowledge_base_thread_archive` / `knowledge_base_cursors` / `knowledge_base_feedback` are **group**-scoped entities — keyed by `getScopeKey('group', { storageContextId, chatUserId, contextType })` i.e. `configContextId` (`src/chat/context-scope.ts:23`). `feedback`'s `voter` is per-user (`chatUserId`), but rows live per-group corpus (`configContextId, answer_id, voter`) per `spec.md:117`. They are added to `ENTITY_SCOPES` and the `context-scope` consistency test. Live retrieval query, prompt assembly, and `feedback` write are keyed thread-isolated via the `storageContextId` passed into the tool execution — the stored corpus lookup maps `storageContextId -> configContextId` first.

**Why not `plugin_kv`:** `plugin_kv` (`src/db/plugin-schema.ts:37`) stores `text value` JSON rows keyed by `(pluginId, contextId, key)` — unsuitable for 1000s of float32 BLOB embeddings with vector scans and indexed `source_type` lookups. A real table with typed indexes and `BLOB NOT NULL` is required for `retrieve.ts:49-95` brute-force scoring.

**Migration and backfill:** New hand-written `src/db/migrations/<seq>_knowledge_base.ts` (where `<seq>` is the next sequential number after the current max in `src/db/migrations/` — e.g. `079` when max is `078` — per `src/db/migrate.ts:validatePairwiseOrder`, which rejects duplicate/out-of-order numeric prefixes) exporting `Migration { id, up(db: Database) }` loaded via `src/db/migrate.ts` (not `drizzle-kit generate` nor `src/db/drizzle-migrations/`). `CREATE TABLE IF NOT EXISTS ...` with indexes; idempotent apply on startup alongside existing migrations. **Backfill:** no backfill needed — existing rows count is zero on deploy; every table derives from sources. If papai already had a legacy `pluginKnowledgeBase` experiment (none exists today), migration renames `LIKE` patterns that include the old key prefix; otherwise a no-op. Fresh deploy seeds `cursors` lazily on first `reindex` tick.

**Alternatives considered:**
- One JSON blob in `plugin_kv` with all chunks — rejected: indexing requires per-chunk random access and dimension guards.
- Shared global chunks without `config_context_id` — rejected: would leak one group's curated docs into another's answers.

### 3. Indexing pipeline: normalize / scrub / chunk / vec / pipeline

**Decision:** New module `plugins/knowledge-base/src/indexer/` (no existing papai module covers chunking — the search explicit "which existing module covers need or none does" check confirms none; `src/long-term-memory/` handles extractor/provisional records, not markdown chunking) providing:
- `normalize.ts` (`[REDACTED]` patterns handled in scrub, narrow patterns)
- `scrub.ts` (`[REDACTED]` patterns, narrow)
- `chunk.ts` (heading split + 500/50 target/overlap + `hardSplit` line-boundary snapping)
- `kb/vec.ts` (`toBlob`/`fromBlob`/`cosine`, buffer-copy note)
- `indexer/pipeline.ts` (`EMBED_BATCH=32`, delete-then-insert transaction, `content_hash` sha256)

Adaptations:
- Use papai's `ai-tokenizer` for `countTokens`/`encode`. **Justification for keeping the dependency if `ai-tokenizer` diverges:** chunk boundaries are prompt-contractual (judge prompt + `RETRIEVAL_MIN_SCORE` tuning built against `cl100k_base`). If `ai-tokenizer` token counts differ by >10% on the curated KB fixture (approximately >2 tokens per 500-token chunk), add `@dqbd/tiktoken` as a plugin-local dep — this is the only justified new dependency, because papai's existing `ai-tokenizer` cannot reproduce `cl100k_base` byte-level BPE needed by `chunk.ts:89` multi-byte safe `Array.from` hard-split. Default is to reuse `ai-tokenizer`; the golden-fixture test pins this gate.
- Use papai's `drizzle` client / `bun:sqlite` statement handles; keep synchronous `transaction(() => { DELETE ...; INSERTs })` semantics (`pipeline.ts:61`).

**Why new module:** deterministic pipeline stays co-located with the plugin; dual-scope constant `JUDGE_VERSION` stays co-located with the prompt so prompt/version lockstep is enforced.

### 4. Retrieval + synthesis: tiered `retrieve.ts` + `prompts/index.ts` as the tool body

**Decision:** `plugins/knowledge-base/src/kb/retrieve.ts` implements tiered retrieval with one change: every `SELECT ... FROM chunks WHERE <tierSql>` gains `AND config_context_id = ?` and the `log.warn` dimension path includes `configContextId`. Tier SQL kept identical (`HIGH_TIER_SQL`/`LOW_TIER_SQL` `source_type IN ('readme','curated_kb')`). Gate `highTierMinScore = RETRIEVAL_MIN_SCORE` applied; `maxScore` as best among served chunks.

Answer synthesis provides `buildAnswerMessages` / `renderContext` / `linkCitations` / `stripTrailingSourcesList` / citation regex `CITATION_MARKER`, truncation to 4k at paragraph boundary with `…(truncated)`, and tier labels `SOURCE_TIER_LABELS`. The tool's `execute` does: `embed(question)` via per-config-context LLM provider (central creds with BYOK override resolved via `contextConfig`/`adminConfig` at call time, Vercel AI SDK) -> tiered `retrieve` -> `buildAnswerMessages(question, chunks)` -> `generateText` via same per-config LLM provider -> `linkCitations(body, chunks)` -> `stripTrailingSourcesList` when canonical tail present -> truncate **body** to 4000 chars at paragraph boundary with `…(truncated)` **before** appending the canonical `Источники:` tail intact. Total delivered SHALL respect the calling platform's `maxMessageLength` — Telegram `4096` (`src/chat/telegram/metadata.ts:22`), Kontur Talk `4096`, Discord `2000` (`src/chat/discord/metadata.ts:20` via `chunkForDiscord` `src/chat/discord/format-chunking.ts:18`), Mattermost `16383`; default `4096` when platform unknown. Body budget is `min(4000, platformMax - 96)`; `body + tail` exceeding `platformMax` truncates tail only at complete `[n](url)` boundaries, never mid-URL/mid-bracket; Discord delivery may split `body+tail` via `chunkForDiscord` but truncation still respects link validity per `spec.md` Grounded answer synthesis truncation scenario (no platform branch in prompt/retrieval beyond delivery cap/chunking) -> mint stable `answerId` as `sha256(configContextId + '|' + Date.now() + '|' + answerHash)` (64-char lowercase hex; returned alongside answer and persisted as `knowledge_base_feedback.answer_id` for feedback joins; stable per tool-call, not per regeneration). `answerHash` is the lowercase hex `sha256` of the final delivered answer string after truncation/tail (or literal fallback text when no context supports an answer; `sha256("")` if empty); `Date.now()` is stringified decimal milliseconds at mint time -> return `{ answer, answerId, sources, maxScore }`. `providerRuntime` is used only for `httpFetch` (GitLab README), not LLM. Curated-KB and GitLab README `configRequirements` are optional (`required: false`), so `config_missing` does not gate eligibility on their absence — reindex simply skips an unset source and retrieval may serve an empty corpus until admin sets a path; only future required keys would gate `eligible`.

**Capability / tool_prefs impact:** New capability `knowledge-base` (and sub `knowledge-base/indexing`) per `proposal.md` Capabilities. Tool registered as `ask_knowledge_base` (runtime `plugin_knowledge_base__ask_knowledge_base` via `src/plugins/runtime-types.ts` naming, `docs/architecture/plugins.md:16`); classified `read` risk, domain `plugin` (explicit `TOOL_METADATA['plugin_knowledge_base__ask_knowledge_base'] = read('plugin')` overriding `plugin_` open-world fallback, so `riskDefaults[read]`/`domainDefaults[plugin]` govern it — `knowledge-base` is the capability, not a `TOOL_DOMAINS` entry) (`docs/architecture/tools.md:14`, `src/tools/tool-metadata.ts:197`). Resolution order per `spec.md:22` (`toolOverrides` → `domainDefaults[plugin]` → `riskDefaults[read]` → implicit `allow`). `allow`/`ask`/`deny` semantics as specified; `ask` wraps schema with `_permission_reason` and gates execution — handled by `src/tools/tool-preferences.ts:resolveToolPermission` and `wrapTool` pipeline, no plugin-side branching. Guest mode (`guest_mode` on `authorized_groups`, `docs/architecture/behaviors.md`) maps to `actorRole: 'guest'`; plugin does not provision members — `ask_knowledge_base` as `read` is included in guest read-only sets via `applyGuestReadOnlyFilter` (which allows only `risk: 'read'` tools), still subject to `allow`/`ask`/`deny`.

### 5. Distillation / crawling replacement

**Decision:** The plugin ingests channel threads from two papai-native sources (no standalone WebSocket crawl):
- Curated-KB + optional GitLab README reindex: on `plugin:knowledge-base:reindex` tick read `contextConfig.get('curated_kb_path')`/`url` (path validated: allowlisted, no traversal, sandboxed to configured data dir `KNOWLEDGE_BASE_DATA_DIR` (optional env, default `./data/knowledge-base` resolved to absolute once at startup via cached `path.resolve(process.cwd(), KNOWLEDGE_BASE_DATA_DIR)` — if env value is already absolute it is used directly without `process.cwd()`; relative values are anchored to startup WorkingDirectory and cached, not re-resolved per tick — before jail checks, created on demand 0755 (mkdir respects umask; failure on read-only volume handled per Decision 6); jail via `path.resolve` + `startsWith` with directory-boundary check (`resolved === dataDir || resolved.startsWith(dataDir + path.sep)`) then `realpath` + `startsWith` re-check with same boundary, then atomic `open` + `fstat` size check; check order `resolve→startsWith(+sep||===)→realpath→startsWith(+sep||===)→open→fstat` with `O_NOFOLLOW` (fallback only when platform lacks O_NOFOLLOW support; on ELOOP/EPERM from symlink do not retry without flag — fail closed — fd `realpath` re-verify still required) for TOCTOU; traversal outside is refused; if dir missing creation attempted else source skipped with warning); `bytesLimit: 5_242_880` (5 MiB) enforced as file-size pre-check via `fstat` plus byte-counted streaming read cap for local `fs` reads (read loop aborts at cap even if file grew after `fstat` or is sparse/pipe; unbounded `fs.readFile` does not satisfy the spec) and as `httpFetch` `bytesLimit`, `rateLimit` only for `httpFetch` per `src/web/` conventions; `fstat > limit` skips source with warning and leaves prior chunks intact (not an empty-doc purge), GitLab `httpFetch` also enforces `bytesLimit: 5_242_880` + `rateLimit`) and, when `providerRuntime.httpFetch` is authorized (`providerAllowedHosts` + `buildContextDynamicHosts` tiered admin/context checks, `docs/architecture/plugins.md:15`), fetch via `providerRuntime.httpFetch` with `bytesLimit/rateLimit` matching `src/web/` conventions. Hash/SHA skip (`pipeline.ts:97` `chunksExist`) preserved.
- Distilled threads (`channel` tier): `archive`, `judge`, `distiller` with `JUDGE_VERSION` constant and `MAX_JUDGE_ATTEMPTS=5`. Ingest path: papai ingests from persisted channel history already stored via `src/chat/`/`message_metadata` (not an external Mattermost REST crawl) grouped by thread root derived via `replyToMessageId` chain traversal — `message_metadata` has no `root_id` column (`src/db/schema.ts:170` defines `replyToMessageId`, `groupContextId`), so ingestion reconstructs threads by batched `WHERE groupContextId = ?` (`groupContextId === configContextId` via `getScopeKey('group', {storageContextId, chatUserId, contextType})` per `src/bot-message-caching.ts:22-29`, no `known_group_contexts`/`context_settings` join; served by `idx_message_metadata_group_ctx` plus new `idx_message_metadata_group_ctx_ts_msg ON message_metadata(group_context_id, timestamp, message_id)` (`CREATE INDEX IF NOT EXISTS`) for the watermark resume query — rerun/partial-apply does not error; `groupContextId` nullable — `NULL` rows from pre-070 or DM contexts are reaped by a periodic `WHERE groupContextId IS NULL` backfill piggybacked on `plugin:knowledge-base:distill` (first step of each distill sweep before batched group ingestion, bounded `LIMIT 200` per tick, per-row failure isolated, `pino` info + `plugin_runtime_events` counter `{scanned, backfilled, skipped}`)) load per `configContextId` with in-memory `replyToMessageId` walk (bounded: visited-set cycle guard, max depth 100; `idx_message_metadata_reply_to` is on `(contextId, replyToMessageId)` thread-scoped and is not used for the group scan — the walk is an in-memory grouping of the batched group rows; cross-batch missing parent treated as orphan thread root; orphan reply chains treated as own thread); paging/pacing (page size 60, 200ms, retries on 429) and cursor resumption in `specs/knowledge-base/indexing/spec.md:59` describe the standalone crawler and are not used in papaid in papai by batched local ingestion from `message_metadata` with a `knowledge_base_cursors` watermark as lexicographic tuple `MAX(timestamp, messageId)` per `configContextId` (`knowledge_base_cursors` row `(config_context_id TEXT PRIMARY KEY, watermark_ts INTEGER NOT NULL, watermark_id TEXT NOT NULL)`, initial `(0, '')` when absent) — resume query `WHERE groupContextId = ? AND (timestamp, messageId) > (COALESCE(watermark_ts,0), COALESCE(watermark_id,'')) ORDER BY timestamp ASC, messageId ASC` — ingestion is bounded per tick (`LIMIT 200` per `configContextId`, cursored paging; first run does not unbounded-scan `message_metadata`). Watermark UPSERT is transactionally after successful `thread_archive` batch commit within the same `db.transaction()`; on mid-batch failure the transaction rolls back and watermark does not advance (next tick re-scans), so no threads are lost (`timestamp INTEGER`, `messageId TEXT` lexicographic tie-break matching `ORDER BY` — timestamp is primary ordering, same-millisecond ties are rare given `Date.now()` granularity; lexical compare is a total order consistent for resume even when numeric provider IDs (Telegram int, Discord snowflake) do not sort numerically — delivery order within same millisecond may be lexical not numeric; the `timestamp >= watermark_ts - 60 AND (timestamp, messageId) > (watermark_ts, watermark_id)` AND form does not re-scan `[watermark-60, watermark)` — the 60s clock-skew guard is a separate bounded overlapping re-scan `WHERE groupContextId = ? AND timestamp BETWEEN watermark_ts - 60 AND watermark_ts ORDER BY timestamp ASC, messageId ASC` merged in-memory and deduped via already-archived `thread_id`/`content_hash`) — the distiller's `selectPending`/`judgeThread`/`purgeThreadChunks`/`stampVerdict`/`recordJudgeFailure` loop is unchanged except `thread_id -> permalink` maps through `configContextId` and `source_type='channel'`/`source_ref='<permalink>#<n>'` LIKE-escape (`distiller.ts:33`) is preserved. Opt-out: `:no-bot:` text (active in this change, via `message_metadata.text`) + `no-bot`/`no_bot` reaction and `type` starting `system_` (deferred — require absent `message_metadata` columns `reactions`/`type` `src/db/schema.ts:170-186`, no-op in this change, `reactions_checked_at` reserved; see `specs/knowledge-base/indexing/spec.md` Channel crawl deferral) + bot-self exclusion (`withoutBotPosts`, `spec.md:99`) stay in code, not the judge prompt. Retroactive purge (`spec.md:86` `LIKE '<escaped permalink>#%' ESCAPE '\'` in one transaction) is synchronous inside `db.transaction()` as in knowledge-base; reaction-triggered retroactive purge is deferred until reaction storage exists.

**Why:** Papai's `ChatRouter` replaces the per-channel `ws` loop; `providerRuntime.httpFetch` + allowlist is the only papai-approved network egress. Zero LLM calls during crawl is preserved; judging remains one sequential `llm.chat` per thread with `p-limit(3)`-bounded embed batching (`proposal.md:38` `EMBED_BATCH=32`), reusing the per-config `LLM_CHAT_MODEL`/`LLM_EMBED_MODEL` resolved at job time.

### 6. Scheduling: two plugin jobs per eligible config-context

**Decision:** `contributes.jobs: ["reindex","distill"]` → runtime owners `plugin:knowledge-base:reindex` / `plugin:knowledge-base:distill` (`docs/architecture/plugins.md:16` `plugin:<id>:<job>`, `PluginScheduledJob { name, intervalMs }` in `src/plugins/runtime-types.ts:126`, `scheduler.register(owner, { interval: job.intervalMs })` in `src/plugins/contributions.ts:92`). In `src/scheduler/` terms (or the plugin-scheduler shim), each job handler:
- Enumerates `getScheduledJobContextIds("knowledge-base", manifest)` (two-arg signature, `src/plugins/scheduled-contexts.ts:10`) filtered to `eligible` and `enabled`. For `defaultEnabled` plugins, `configuredDefaults` filters `listContextSettings().filter(s => s.taskInstanceId !== null)` — contexts with `null` `task_instance_id` (pre-config) are not `configured` and are not scheduled by default; they become scheduled only when explicitly enabled in `plugin_context_state` (`src/db/plugin-schema.ts:21`). Tool eligibility (`getPluginContextEligibility`) remains true for null task instances (spec `knowledge-base/spec.md:15` `eligible` check), so `ask_knowledge_base` is still available live; scheduled indexing for those groups requires explicit enable.
- For each `configContextId`, resolves LLM creds via BYOK facade at execution time, runs pipeline, emits `pino` structured counters (`threads`, `judged/indexed/failed`, `chunks_indexed per source_type`, `maxScore`) and `plugin_runtime_events` (`src/db/plugin-schema.ts:58`) scoped `pluginId: 'knowledge-base'`.
- Schedules: `reindex` every 30 min (`intervalMs: 30*60*1000`), `distill` every 15 min (`intervalMs: 15*60*1000` global per owner `plugin:knowledge-base:distill`; per-context `distill_interval_ms` override is deferred — `PluginScheduledJob { intervalMs: number }` and `scheduler.register(owner, { interval: job.intervalMs })` register one interval per owner, not per config-context, and `getScheduledJobContextIds`/`runPluginScheduledJob` iterate contexts within that single sweep; no `contextConfig.get('distill_interval_ms')` is read at registration and no per-context re-register is performed — if a future throttle is introduced it SHALL be intra-sweep debounce (`lastDistillAt` per `configContextId`, skip context if `now - last < distill_interval_ms`) not a scheduler interval override; absent key means default 15 min; `DISTILL_CRON` is the knowledge-base standalone cron concept, `PluginScheduledJob` has no cron field). Concurrency is sequential per `runPluginScheduledJob` reduce chain (`src/plugins/contributions.ts:172`) with per-context failure isolation (try/catch per `contextId`, one group's embed error does not abort others); skip-if-running per owner is a **plugin-owned** guard (core `src/utils/scheduler.internal.ts:284` `setInterval` does not skip overlapping ticks — the handler SHALL check an `activeSweep` flag at entry: if a previous sweep has not completed when next `intervalMs` fires, the new tick is skipped with `pino` info log, not queued concurrently, so at most one sweep per job runs on the single `bun:sqlite` file even though the core scheduler would otherwise overlap); per-LLM-call timeout bounds one slow context; embed batching within a context remains `EMBED_BATCH=32` + `p-limit(3)`. Idempotency via `content_hash`/`judged_hash`/`cursors` exactly as `specs/knowledge-base/indexing/spec.md:48`. Curated-KB `KNOWLEDGE_BASE_DATA_DIR` (env-optional, default `./data/knowledge-base`) creation: if `fs.mkdir(..., {recursive:true})` fails (`EACCES`/`EROFS` on read-only container volume), the reindex tick SHALL emit a `plugin_runtime_events` warning + `pino.warn` (`code`, `dataDir`, `configContextId`) and skip that source for that tick — not just a `pino.warn` — so admin settings save can surface the validation error (see spec Curated KB requirement) and the corpus-empty state is observable; `ask_knowledge_base` remains `eligible` (`required:false`) but will return empty/low-confidence until the data dir is writable.

Settings UI (`client/settings/`, `src/settings/`): plugin config via `configRequirements` (generic `GET/POST /settings/api/plugins/config` and `/settings/api/admin/plugin-config` — `src/plugins/store.ts`, `src/debug/settings/plugins-routes.ts` — not custom `/settings/api/knowledge-base/*` routes; `synthetic-web-search` is a core feature and not a plugin precedent). Fields `curated_kb_path`, `curated_kb_url`, `gitlab_host`/`gitlab_project`/`gitlab_ref`, `kb_min_value_score`, `retrieval_min_score`, `distill_batch_limit` (`spec.md:75` `DISTILL_BATCH_LIMIT` LIMIT, not LLM batch; `configKeySchema` `/^[a-z][a-z0-9_]*$/` — snake_case lower, `src/plugins/manifest-validation.ts:36`) and reserved `distill_interval_ms` (optional; default `15*60*1000` — reserved key, global schedule only in this change; per-context override deferred — see Schedules above) declared in `configRequirements` (`scope: context`, `required: false` for curated KB/GitLab); rendered in the generic Plugins section (`PluginsSection.svelte`/`AdminPluginsConfigSection.svelte`) via the `adminConfig`/`contextConfig` facade (`docs/architecture/plugins.md:19`). Reindex reads via `contextConfig.get('curated_kb_path')`/`get('curated_kb_url')` consistent with snake_case keys. Sensitive tokens (`gitlab_token`, LLM BYOK) `sensitive: true`, `scope: context`/`admin`, encrypted-at-rest via papai's config encryption facade, masked on read, `unset/Clear` supported.

### 7. Secrets, observability, and cross-platform parity

- Scrubbing (patterns for Bearer, `key=value`, `glpat`/`ghp`/`xox`, `AKIA`, 32-hex, JWT) runs **before** `normalizeMarkdown` so redacted regions are never tokenized as secrets. Pipeline logs contain only `configContextId`, `sourceType/sourceRef`, `dims/queryDims`, `threadId` — never chunk text, embeddings, tokens (`spec.md:101`).
- `providerRuntime.httpFetch` enforces `providerAllowedHosts` (static) + `providerAllowedHostsFromConfig` dynamic hosts: admin-sourced bypasses public-IP restriction, context-sourced requires HTTPS + public-IP (`ipaddr.js`) validation — matching `mcp-gitlab` tiering.
- `ChatRouter` fan-out (`src/chat/router.ts`) guarantees identical `StorageContextId -> configContextId -> chunks` resolution across Telegram/Mattermost/Discord/Kontur Talk; no platform branch in retrieval or prompt code.

## Risks / Trade-offs

- [Single-writer SQLite under concurrent reindex/distill + live writes] → `bun:sqlite` `WAL` (`PRAGMA journal_mode=WAL` set in `src/db/index.ts:111` and `src/db/drizzle.ts:21`) retained; papai's DB open path SHALL set `PRAGMA busy_timeout=5000` (and per-transaction retry on `SQLITE_BUSY`) because live `ask_knowledge_base` reads (and future `knowledge_base_feedback` INSERTs once the deferred feedback trigger is wired) run concurrently with the 30/15-min scheduled `DELETE+INSERT` transactions on the same `bun:sqlite` file; jobs serialize per `configContextId` via sequential `runPluginScheduledJob` reduce chain, and cross-group sequential execution reduces contention but does not isolate live writes. Mitigation is process-level; document the same ADR-0005 single-writer limit; `busy_timeout` is required before first `knowledge_base` migration ships, not only if concurrent jobs are introduced.
- [Embedding dimension drift after model change] → `retrieve.ts:69` dimension guard `row.embedding.byteLength !== queryDims * 4` drop+warn; stale chunks naturally age out on next `reindex`'s delete-then-insert. Large model swap still needs a one-time full reindex.
- [All-zero / non-finite query vectors] → `retrieve.ts:35-43` fail-closed with structured error, no fabricated citations (`spec.md:64`).
- [Framing / prompt injection via retrieved chunks] → synthesis prompt explicitly marks context/tool outputs as untrusted data (`prompts/index.ts:18`), `CITATION_MARKER` `(?!\()` prevents model-wrapped link laundering, and `stripTrailingSourcesList` only strips when canonical tail exists.
- [Secret-shaped strings over-redacting ticket IDs] → keep narrow scrub patterns (`scrub.ts:14` requiring prefix/length), verification step asserts `ISSUE-123`/tracker URLs survive (`spec.md:14-16`). No log passes through scrubbed values.
- [Bun vs `better-sqlite3` transaction semantics] → verify `db.transaction(() => { ... })` rollback-on-throw parity (`pipeline.ts:61` note); add integration test that kills mid-`DELETE+INSERT` and asserts no partial chunks.
- [`tiktoken` vs `ai-tokenizer` drift] → pin chunk-boundary golden-fixture test against `cl100k_base` fixture; if `ai-tokenizer` count diverges by >10% on the curated KB fixture (≈ >2 tokens per 500-token chunk), vendor `@dqbd/tiktoken` locally — the only new dep, justified by WASM integrity for CJK/multi-byte hard-split (`chunk.ts:89`).
- [Retroactive opt-out sweep cost] → `revalidate` equivalent **deferred in this change** (requires `reactions` column — `reactions_checked_at` reserved); when enabled it runs via scheduled job with `intervalMs: 24h` (cron → `intervalMs`; papai's scheduler uses `intervalMs`) covering `thread_archive.reactions_checked_at IS NULL` batch, not on every distill tick. See Channel crawl deferral in `specs/knowledge-base/indexing/spec.md`; `spec.md:86` retroactive reaction purge is non-normative until columns exist.
- [LLM proxy fan-out amplification] → bounded by `EMBED_BATCH=32` + `p-limit(3)` within a context and sequential across contexts (`runPluginScheduledJob`); BYOK per group avoids cross-group rate-limit coupling; `defaultEnabled: true` blast radius is bounded by this sequential spread and bounded embed batching, but total cost scales with N groups — staged rollout and per-group quotas/BYOK budget checks mitigate first-hour N*embed burst. Usage rows `llm_usage_events` (`src/db/schema.ts:8` export) still recorded.
- [Brute-force retrieval scan] → `retrieve.ts:49-95` loads every `config_context_id`-scoped embedding BLOB and scores cosine in JS; indexes `(config_context_id, source_type, source_ref)` filter tiers but do not avoid full partition scan. Mitigated by expected small corpus (curated KB + bounded distilled items); no normative per-group chunk quota/eviction in this change — operational guard only: emit `maxScore`/`count` observability and paginated scan warning if `chunks` per `config_context_id` exceeds 10k, deferring hard quota/LRU eviction to a future change.
- [Curated KB path traversal] → `curated_kb_path` is a context-config string; without validation it could read arbitrary files. Require allowlisted, sandboxed path validation analogous to `providerAllowedHosts` (reject traversal, jail to `KNOWLEDGE_BASE_DATA_DIR` via `realpath` + `startsWith`) before `fs` read, with `bytesLimit` as file-size check and `rateLimit` only for `httpFetch` matching `src/web/` conventions. This is enforced normatively in `specs/knowledge-base/indexing/spec.md` Curated KB requirement, not only as a design note.

## Migration Plan

1. **Migration `<seq>_knowledge_base.ts` (`<seq>` = next sequential number after current max, e.g. `079` when max is `078` — `src/db/migrate.ts:validatePairwiseOrder` rejects duplicates/out-of-order)** — hand-written `src/db/migrations/<seq>_knowledge_base.ts` exporting `Migration { id, up(db: Database) }` for `src/db/migrate.ts` (not `drizzle-kit generate`). Declare `sqliteTable` entries in `src/db/schema.ts` and create tables in migration: `knowledge_base_chunks`, `knowledge_base_thread_archive`, `knowledge_base_cursors`, `knowledge_base_feedback` (with `config_context_id TEXT NOT NULL` partition, `knowledge_base_feedback` PK `(config_context_id, answer_id, voter)`, `knowledge_base_thread_archive` PK `(config_context_id, thread_id)`) and compound indexes `(config_context_id, source_type, source_ref)` / `(config_context_id, judged_at, root_created_at)` plus `idx_message_metadata_group_ctx_ts_msg ON message_metadata(group_context_id, timestamp, message_id)` (`CREATE INDEX IF NOT EXISTS`) for the watermark resume query — rerun/partial-apply does not error. `PRAGMA busy_timeout=5000` SHALL be set at DB connection open in `src/db/index.ts` and `src/db/drizzle.ts` (not inside the migration transaction — see `src/db/migrate.ts:114` PRAGMAs inside transactions are silently ignored). Ship as a single forward migration; no down-migration needed because tables are empty on deploy.
2. **ENTITY_SCOPES registration** — add the four tables to `src/chat/context-scope.ts:38` + the `CONTEXT_OWNED_COLUMNS` consistency guard so `getScopeKey` maps correctly; land before plugin activation or group sharing will mis-key `plugin_kv`-style lookups.
3. **Plugin delivery** — commit `plugins/knowledge-base/` (`plugin.json`, `src/*.ts`, `worker/` if needed). On next startup discovery approves `knowledge-base` (`plugin_admin_state` `approvedManifestHash`), then per-context enable (`defaultEnabled: true`). No env var required; `task_instance_id: null` contexts remain `eligible` for the tool (`getPluginContextEligibility` per `spec.md:15`), but scheduled jobs for `null` contexts require explicit `plugin_context_state` enable (see Decision 6).
4. **First-run indexing** — `plugin:knowledge-base:reindex` runs on first 30-min tick (`intervalMs: 30*60*1000`); `activate()` does only a lightweight `cursors` existence check and never triggers heavy embed/index work (would exceed `activationTimeoutMs=5000` in `src/plugins/types.ts:198`). Curated KB hashes and GitLab ETags/SHA populate `cursors` on that first tick; chunks are `float32 BLOB` via Vercel AI SDK `embed`.
5. **Scheduling** — two jobs registered via `contributionRegistry.register` / `scheduler.register(owner, { interval: job.intervalMs })`; `runPluginScheduledJob` processes eligible contexts sequentially with per-context isolation.
6. **Rollback** — disable via settings per-group, or reject `knowledge-base` in admin plugin state (approve→rejected): plugin stops scheduling and `makeTools` stops exposing `ask_knowledge_base`. Tables stay dormant; no data deletion on rollback (idempotent). Hard rollback is `DROP TABLE IF EXISTS knowledge_base_*` plus `DELETE FROM migrations WHERE id='<seq>_knowledge_base'` (required because `src/db/migrate.ts` never deletes `migrations` rows on downgrade and `runMigrations` skips already-applied ids — without deleting the row, re-migration would skip `CREATE TABLE IF NOT EXISTS` and leave the plugin without tables); hard rollback is only for abandonment — if the `message_metadata` resume index `idx_message_metadata_group_ctx_ts_msg` was created in the same migration, the rollback SHALL leave that index intact (hard rollback is `DROP TABLE IF EXISTS knowledge_base_*` only — do not `DROP INDEX idx_message_metadata_group_ctx_ts_msg`) or, if the operator batched drops, SHALL recreate it (`CREATE INDEX IF NOT EXISTS idx_message_metadata_group_ctx_ts_msg ON message_metadata(group_context_id, timestamp, message_id)`), since the watermark resume query and potentially other history-search features depend on it; single-command supported rollback is the knowledge_base table drops plus `DELETE FROM migrations` without touching that index.
