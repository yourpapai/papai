# Design: opencode-agent-fix-command

## Context

See `proposal.md` — Why for the motivation; `specs/agent-fix-command/spec.md` for the requirements. This design covers how the command is wired into the existing trigger machinery, plus the one handler-side seam a command-bought round needs: learning what is red without a `workflow_run` event to read (D7).

The pieces this change joins already exist; all but the handler's discovery prelude are not touched:

- **The move.** `CI_FAILED` names two rows in `TRANSITIONS` (`transitions.ts:104,109`): `COMPLETE` and `PR_DELIVERY`. `forwardTransition` increments `ciAttempts` on that signal (`transitions.ts:201`), and the cascade already has the `CI_FIX` handler, its budget stops and its presentation row. A repair run is a solved problem *given a run to read*: `discoverFailures` (`phases/ci-fix.ts:186`) returns no jobs for every `trigger.kind !== 'ci'`, because no other door could buy the round. What is missing is a second way in — and that way arrives as `kind: 'pull-request'`, carrying no `runId`, so the discovery prelude is the one piece of repair plumbing this change must extend.
- **The command seams.** `commands.ts` owns the vocabulary: `SLASH_COMMANDS`, `COMMAND_SIGNALS`, and `COMMAND_APPLIES` — one predicate table with two readers (`acceptedCommands` builds the offered list, `applyCommand` enforces it), so the offer and the gate cannot drift. `applyCommand` in `triggers.ts` already refuses two budgets *before* applying their signals (`refuseExhausted`, `refuseReviews` in `command-refusals.ts`), each gated on `canTransition` so a wrong-phase command is a wrong-command refusal, not a spent one.
- **The door.** A comment typed on the pull request arrives as `kind: 'pull-request'` → `applyPullRequestCommand` → `applyCommand` — deliberately the same seam as the issue, so both doors get one answer to "which commands does this state accept". The door's own guardrails (`pr-trigger.ts`) already check fork, open and `agent/issue-<n>` head before a command is ever applied. `commandSurface` already refuses commands typed on the issue once a pull request exists.
- **The automatic door's gates.** `applyCiTrigger` (`ci-trigger.ts`) runs four checks for a red `workflow_run`: phase admission, the `ciAttempts` ceiling (with the once-per-PR `ciBudgetReported` notice), a settled-pull-request lookup, and the transition itself. Its silence properties are tuned for an event nobody typed.

Constraint that shapes the whole design: a `/fix` round must be *indistinguishable*, in state effects and repair behavior — same diagnosis protocol, same repair branches, same report — from a round the red-run door bought (the spec's "one budget shared by both doors" requirement; the discovery *source* necessarily differs, D7, because a command-bought round names no run), while its *refusals* must behave like a typed command's (answered, repeated, naming remedies), not like an asynchronous event's (quiet).

## Goals / Non-Goals

**Goals:**

- `/fix` reaches the existing `CI_FIX` machinery through the existing `CI_FAILED` transition. No second repair path, no second diagnosis protocol, no second spelling of anything the CI path already decides — the one repair-adjacent addition is a discovery branch in the handler (D7): where a red-run round reads the run that bought it, a command-bought round reads the check runs of the pull request's head.
- One per-pull-request CI budget across both doors, enforced at one increment site (`forwardTransition`).
- Refusals follow the three existing refusal families exactly: wrong-command (lists what applies), surface (names where to type it), spent-budget (names the ceiling and the remedies, repeats with the question, leaves persisted state byte-identical).
- The workflow's pull-request arm admits the command in lockstep with `SLASH_COMMANDS`, enforced by the existing `workflow.test.ts` check.

**Non-Goals** (design-level, beyond the proposal's):

- No change to which phases admit `CI_FAILED`, to the transition table, to `AgentState`, or to `STATE_VERSION` — the door changes, not the machine.
- No gate-time check-state lookup. Whether anything is red is discovered by the round itself from the check runs of the head commit (spec, "The round addresses the pull request's own checks"); the gate reads only persisted state.
- No interaction with `ciBudgetReported`: the automatic door's once-per-PR silence and the typed refusal's repetition are separate answers to separate doors.

## Decisions

### D1 — `/fix` is a signal-carrying command, not a `/sync`-shaped side operation

`COMMAND_SIGNALS` gains `'/fix': 'CI_FAILED'`. The command goes through `applyCommand` → `moveOrSkip(state, 'CI_FAILED')` like `/review` goes through `REVIEW_REQUESTED`.

Alternative considered: the `/sync` shape — a side operation dispatched before the signal lookup, running a repair directly without moving the phase. Rejected: `/sync`'s entire doctrine is "moves nothing", and a CI-fix round is the opposite — it must consume an attempt, occupy `CI_FIX` (so the cascade's budget stops, failure parks and presentation apply), and report as a repair run. A side operation would have to re-implement the attempt increment (or skip it, breaking the shared budget), invent its own phase admission, and duplicate the handler's entry conditions. The one-liner: `/sync` is the precedent for commands that move nothing; `/fix` moves the machine, so it is `/review`-shaped.

### D2 — applicability is the shared `prNumber` predicate; phase admission stays in the table

`COMMAND_APPLIES['/fix'] = (state) => state.prNumber !== null` — the same predicate `/review` and `/sync` read. Phase admission needs no new rule: `accepts` already consults `canTransition(phase, signal)`, so `/fix` is offered by `acceptedCommands` exactly in `COMPLETE` and `PR_DELIVERY` with a pull request named, and refused everywhere else through the ordinary wrong-command door that lists what does apply. The spec's "the offer and the gate cannot disagree" holds by construction — one predicate table, one transition table, two readers.

Alternative considered: a `/fix`-specific predicate that also asks whether checks are red. Rejected: check state is not persisted state, the lookup costs an API call on every offered-list render, and re-deciding the round's premise at the gate duplicates what the round itself discovers from the Checks API. A green-check `/fix` is an outcome ("no failed check run found", nothing pushed — spec scenario), not a gate error.

### D3 — the spent budget is refused by a third refusal function, checked in `applyCommand` gated on the table

`refuseFix` in `command-refusals.ts`, beside `refuseExhausted` and `refuseReviews`; the check sits in `applyCommand` after the `commandApplies` check and gated on `canTransition(state.phase, 'CI_FAILED')`, exactly the `REVIEW_REQUESTED` ordering. This keeps the refusal families straight: a `/fix` with no pull request, or in a phase that refuses `CI_FAILED`, is a *wrong-command* refusal listing what applies; only a `/fix` that would have run is answered with the ceiling.

Refused before the signal is applied (the `refuseExhausted` doctrine): applying `CI_FAILED` and then regretting it moves `COMPLETE → CI_FIX`, increments `ciAttempts` past the ceiling and parks the issue in a handler phase under a notice inviting the very command the ceiling just refused — while the honest remedy, raising `AGENT_MAX_CI_ATTEMPTS` and replying `/fix` again, requires the state to be exactly what it was. The refusal returns `{ status: 'failed', reported: true }` with the state untouched, and — unlike the automatic door's `ciBudgetReported` short-circuit — posts every time it is typed, because it answers a command somebody asked (the `renderReviewsExhausted` argument, applied to this ceiling).

Its own function rather than a branch in `refuseReviews` because the remedy differs: nothing is parked, so `/retry` cannot help; the notice names `AGENT_MAX_CI_ATTEMPTS` and the fresh budget a new pull request earns (`FRESH_PR_BUDGETS` clears the CI pair on a genuinely new PR — the existing reset, no new one).

The notice is a new renderer, `renderFixExhausted`, in `budget-notices.ts` beside `renderReviewsExhausted`, over a new `CI_SPENT: '⛔'` outcome key in `outcomes.ts`. Alternative — reuse the automatic door's `renderCiExhausted` / `CI_GAVE_UP`: rejected on both halves. The text is wrong (that notice announces a *give-up*, once per PR, and offers no raise-the-ceiling remedy), and the glyph is wrong: 🚑 says the repair story ended, ⛔ says a bound refused a command — the exact distinction the ⛔ family (`RETRIES_SPENT`, `REVIEWS_SPENT`, `TOKENS_SPENT`) exists to draw.

### D4 — the accepted path rides `applyCommand` end to end; the CI trigger's event gates are not re-run

A typed `/fix` never reaches `applyCiTrigger` (that function serves `trigger.kind === 'ci'`). Of its four gates, three are already answered upstream on the command path and are deliberately not duplicated:

- *Phase admission* — `moveOrSkip`'s `canTransition`, which for a command refusal surfaces as a wrong-command comment rather than the CI door's quiet skip. Right for a typed command: a maintainer asked, so the run answers.
- *Settled pull request* — the PR door itself resolves only open pull requests on the agent's own branch (`PR_NOT_OPEN`, `PR_FOREIGN_REPOSITORY`, `PR_NOT_AGENT_BRANCH` guardrails), and the `commandApplies` predicate guarantees a PR is named. A second `findPullRequest` lookup would buy nothing.
- *`ciBudgetReported` short-circuit* — not consulted (D3). This is the load-bearing omission: routing `/fix` into `applyCiTrigger` would silently drop the command on a pull request whose automatic notice already fired — the exact silence the command exists to end.

What remains is `moveOrSkip` applying the same transition `enterCiFix` applies, with `ciAttempts` incremented by `forwardTransition` at its single site — the shared budget is shared by construction, not by a second counter. Alternative considered: routing the accepted command into `applyCiTrigger` for "one CI entry point". Rejected for the three gates above; one *transition* is the invariant worth keeping, and it already has one home.

### D5 — the workflow grows one `contains` and one permission line

`agent-pipeline.yml`'s third arm (`.github/workflows/agent-pipeline.yml:146-158`) adds `contains(github.event.comment.body, '/fix')`; `workflow.test.ts` already asserts that arm against `SLASH_COMMANDS`, so the vocabulary entry and the arm cannot drift. `/fix` is not a substring of, nor prefixed by, any existing command, so no comment containing an existing command changes arm behavior — the only bodies the edit newly admits are those mentioning `/fix`, which is the point (the boot cost the risk below budgets). The arm's job join lands in the same `opencode-agent-<branch>` concurrency group as every other pull-request command and red run, so a `/fix` job serializes with an in-flight repair rather than racing it — no workflow change needed for that.

The workflow-level `permissions:` block also gains `checks: read` beside `actions: read` (`.github/workflows/agent-pipeline.yml:38-45`). D7's discovery read is the Checks API (`checks.listForRef`), which sits in the Checks permission class: `actions: read` covers workflow runs and their jobs, not check runs, and because the block exists at all, every scope it does not name is `none` for the default `GITHUB_TOKEN`. Without the grant, every command-bought round would 403 into the `readError` path and spend its attempt for nothing — on a refusal the workflow itself controls. The block's own `actions: read` comment is the precedent being followed exactly: grant the read a phase needs, because "without it the round degrades to a needs-human report naming the 403, which is the honest answer but not the useful one". A repository that overrides with an `AGENT_GITHUB_TOKEN` keeps whatever rights that token carries; the grant is what makes the default token sufficient.

`opencode-agent/CLAUDE.md` gains the command in its command-surface doctrine, and its CI-fix doctrine bullet — "`handleCiFix` reads the run it was asked to repair: `listRunJobs`/`jobLog` (the `actions: read` token)" — learns the second door D7 adds: a command-bought round reads the head's check runs through `listCheckRunsForRef` under `checks: read`. The `permissions:` block's own comment ("What a CI-fix round reads: …") widens with the grant for the same reason — it describes the reads a round makes, and this change adds one. `docs/architecture/` needs nothing (the agent is documented in its workspace) — and that workspace's own `README.md` is made stale by the change, so it lands in the same edit: the command table gains the `/fix` row, the phases table's `CI_FIX` trigger names the second door, and the budget section's once-per-PR silence passage learns the repeating typed refusal beside it.

### D6 — no persisted-shape change, no guardrail change

No `AgentState` field, no `STATE_VERSION` bump, no migration, no new `PHASES` member or presentation row — a `/fix` round writes exactly the fields a red-run round writes (`phase`, `ciAttempts`, spend), through the same block channel, on the same surface (`feedbackTarget` → the pull request, since `prNumber` is non-null by the gate). The fork look-alike, closed-PR and non-agent-branch refusals answer before any command logic runs, so the spec's guardrail requirement holds with zero new code; the design relies on that ordering rather than restating any check.

### D7 — a command-bought round discovers what is red from the pull request's head check runs

`handleCiFix`'s discovery prelude is keyed to the trigger: `discoverFailures` (`phases/ci-fix.ts:184-194`) reads `listRunJobs(trigger.runId)` and returns `{ jobs: [], readError: null }` for every `trigger.kind !== 'ci'` — correct today, because `CI_FIX` is unreachable any other way, and exactly wrong once a command can buy the round: a `/fix` round arrives as `kind: 'pull-request'` (`pr-trigger.ts:81`) with no `runId` to read, and would consume its `ciAttempts` entry (already incremented by `forwardTransition`) rendering "no failed job could be found" on a genuinely red pull request. No head-commit seam exists to save it: `ActionsApi` exposes only `listRunJobs`/`jobLog` (`github-actions.ts:41,47`).

The fix is one branch in that function, not a second repair path: a trigger that is not the red run asks the Checks API for the check runs of the branch the handler already resolves — `branchNameFor(state.issueId)`, computed at the top of the handler (`phases/ci-fix.ts:55`), so no new lookup — through one new `ActionsApi` member beside `listRunJobs`: `listCheckRunsForRef(ref)` — a read the workflow's `GITHUB_TOKEN` can only make once D5's `checks: read` grant lands beside `actions: read`, since the Checks API is its own permission class.

Which check runs count as failed is pinned here, not inherited from the job side: conclusion `failure` or `timed_out` — the terminal conclusions that mean the check ran and ended red with a verdict to fix. Copying `red-run.ts:43` (which accepts only `failure`, and whose rationale argues about cancelled and running jobs, not about a timed-out one) would read a timed-out head — a runner that hit its deadline, red on the pull request and addressable — as green, and the round would spend its `ciAttempts` entry answering "nothing found" on a red pull request. `cancelled`, `skipped`, `stale`, `neutral`, `action_required` and `success` stay out for the reason `red-run.ts`'s own rationale gives: a cancelled or skipped check has no verdict to fix, and treating one as failed sends the diagnosis after a failure that does not exist.

Failed check runs map into the existing `FailedJob` shape — name from the check run, log from its output summary (tail-clipped by the same `red-run.ts` budget), `failedSteps` empty, which the report already renders as "no step failed" — and everything downstream is untouched but one wording: same `FailedJob` in, same diagnosis turn, same repair branches, same report shape. Degradation rides the existing `readError` path: a refused read is an honest round naming the error, not a crash. A head with no failed check run is the spec's "Nothing red on the head" outcome, rendered by the existing `undiagnosedRound` path — whose wrong-door wording becomes door-aware in this change, all four lines of it, because as written they assert facts only the red-run door knows. Two zero-failure lines: `ci-report.ts` renders "CI failures: none — the run is red but no failed job could be found" (`ci-report.ts:53`) and "Diagnosis: the run could not be read; nothing was attempted" (`ci-report.ts:80`) whenever nothing is discovered, and a command-bought round on a green head — or a still-pending one: a `/fix` serialized behind an in-flight repair whose push restarted the checks discovers only `in_progress` check runs — would be told "the run is red" and "could not be read" about checks it read fine. Two read-error lines: the same renderer renders "CI failures: unknown — the red run could not be read (…)" (`ci-report.ts:52`) and "Verdict: this failure needs you — the red run could not be read" (`ci-report.ts:70`) whenever the read is refused, and a command-bought round can reach that path — an `AGENT_GITHUB_TOKEN` deployment whose token lacks the scope (D5: such deployments keep whatever rights the token carries), or a GHES host without the endpoint — so the degradation sentence would name "the red run" about head check runs the round tried and failed to read: the same wrong-door assertion, on the sibling lines of the same renderer, reachable by the same door. The `redRunUrl` branch (`ci-report.ts:43`), which already omits the red-run bullet for non-`ci` triggers, is the precedent for all four: keyed to `trigger.kind`, a command-bought round's zero-failure lines say that no failed check run could be found on the head, and its read-error lines say the head's check runs could not be read — wording only, report shape untouched.

Alternative considered: synthesize the automatic door's input at accept time — look up the newest failed `workflow_run` for the branch and hand the handler a `ci`-shaped trigger with its `runId`. Rejected: it is a second spelling of the event contract (a lie about the trigger's kind, or a new wrapper `TriggerEvent` grows), and it narrows discovery to what one workflow reported when the spec names the head commit's check runs as the source — the human-push-mid-review case the Why opens with is precisely a red head whose triggering event never reached this pipeline.

### Repo-rule impact statements

- **Capability/tool-prefs gating:** none. `opencode-agent/` is a standalone workspace, not a papai runtime dependency; no papai tool surface, `tool_prefs` entry or preset is touched.
- **Scope model:** no new persisted state of any kind, so no new storage-context, config-context, platform-instance or user keys. The round rides the existing `AGENT_STATE` block on the issue/PR conversation; the per-PR budget identity is the existing one (`FRESH_PR_BUDGETS` clears it when `handleDeliver` opens a new PR).
- **DB/drizzle:** no database change — agent state lives in hidden comment blocks, not SQLite; no migration or backfill exists to plan.
- **New dependencies:** none. Command parsing (`commands.ts`), the transition table, the refusal family, the notice renderers and the workflow arm all exist; the discovery branch rides the same `@octokit/rest` client (Checks API `checks.listForRef`), so nothing in the AI SDK / Grammy / Zod / drizzle stack is asked anything new — but the Checks API sits in its own `GITHUB_TOKEN` permission class, so the one non-code line in the plan is `checks: read` in the workflow's `permissions:` block (D5).
- **New module:** none. `command-refusals.ts` covers the refusal (three functions today, room under `max-lines`), `budget-notices.ts` the notice, `commands.ts` the vocabulary, `outcomes.ts` the glyph key, `github-actions.ts` the one `listCheckRunsForRef` member, `phases/ci-fix.ts` the one discovery branch and `phases/ci-report.ts` the door-aware zero-failure and read-error wording — each change lands in the module whose stated job it is.
- **Hook/TDD interactions:** nothing in the TDD hook pipeline gates these edits. The hook's gateable scope is `src/`, `client/`, `plugins/`, `review-loop/src/` and `sdd-runner/src/` (`test-resolver.mjs`'s `isGateableImplFile`; documented in `docs/architecture/commands.md`), so the TS edits under `opencode-agent/src/` pass through ungated — and the tests under `tests/opencode-agent/` are ungated too: the import gate maps a `tests/` file to `src/<same-path>` and skips when no such impl exists, and the old targeted `verifyTestsPass` run has been removed from the pipeline. The test-first order below and the apply-stage TDD guidance carry it, not the hook; what still binds is `bun test tests/opencode-agent/` itself, plus for the YAML (never hook-gated) `workflow.test.ts` (the arm) and `bun workflows:lint` (the whole file, the `checks: read` grant included). Test-first order: (1) `commands.test.ts` — `/fix` parses, `acceptedCommands` offers it exactly in `COMPLETE`/`PR_DELIVERY` with a PR named and nowhere else — together with `guardrails.test.ts`'s "exposes exactly the documented command surface", which pins `[...SLASH_COMMANDS]` against a literal list and so mutates in the same step as the vocabulary entry (the other `SLASH_COMMANDS` readers iterate the array or assert membership and adapt for free); (2) trigger/refusal tests — spent budget refused before the signal, persisted state byte-identical, notice repeated and naming `AGENT_MAX_CI_ATTEMPTS` — together with the `CI_SPENT` row in `markdown.test.ts`'s `OUTCOME_COMMENTS` table, whose own comment declares "one entry per renderer that speaks about an outcome, with its key" (not a gate: the table does not self-verify completeness, but the row is the declared contract and lands with the renderer); (3) transition test — accepted `/fix` produces the same state move and the same `ciAttempts + 1` as the red-run door; (4) handler test — a command-bought round (`kind: 'pull-request'`) discovers failed check runs through `listCheckRunsForRef` — a `timed_out` check run among them, a `cancelled` one not — runs the ordinary diagnosis/repair path, and a head with no failed check run reports "no failed check run could be found on the head" (the door-aware wording, with no "the run is red" claim) with nothing pushed, and a refused head-check read renders the door-aware read-error lines (naming the head's check runs, never "the red run") — the step that keeps (3) honest, since a state move that repairs nothing would otherwise pass; (5) `workflow.test.ts` failure drives the arm edit; (6) guardrail test — fork look-alike refused with no attempt spent.

## Risks / Trade-offs

- [A maintainer may not realize `/fix` draws on the same budget the automatic door already spent] → the refusal names the spent count and the ceiling (`N of AGENT_MAX_CI_ATTEMPTS`), and the fresh-PR remedy; the automatic door's notice does the same in its own vocabulary.
- [`/fix` on green checks still spends a round] → accepted trade-off, stated in the spec: the round reports that no failed check run could be found and pushes nothing, and the gate cannot cheaply know better (D2). One round of `AGENT_MAX_CI_ATTEMPTS` is the price of the command never silently refusing.
- [A check run's output summary is thinner evidence than a job log, so a command-bought diagnosis starts from less] → the round's doctrine already handles thin evidence: the reproduction rule sends the model to the repository's own CI configuration before any edit, and a needs-human verdict is a legitimate answer that consumes no more than its round. If summaries prove too thin in practice, the `listCheckRunsForRef` member grows a log fetch without any other shape changing.
- [The arm's `contains` first pass boots a runner for prose that merely mentions `/fix`] → pre-existing property of every command; `parseSlashCommand` re-parses line-start and fences, and the resulting refusal costs no model turn.
- [A `/fix` queued behind an in-flight repair re-checks the budget against a stale pre-queue count] → the concurrency group serializes the jobs and the restore scan reads the newest block, so the second run sees the `ciAttempts` the first spent and refuses with the honest count — the same sequencing every pull-request command already accepts.
- [Two budget notices now exist for one ceiling (automatic give-up, typed refusal) and could drift in wording] → both renderers live in `budget-notices.ts` beside their siblings, and the ⛔/🚑 glyph split documents which door each answers; drift is a wording bug, not a state bug.

## Migration Plan

One pull request, deployable by merge — tasks.md sections land as their own commits per the apply guidance, and the no-window guarantee is a property of the merged unit: the `SLASH_COMMANDS` entry, the refusal, the notice, the discovery branch, the workflow arm and its `checks: read` grant reach production together, so there is no window where the arm admits a command the parser refuses (or the reverse — `workflow.test.ts` would fail the branch) and none where a command-bought round boots on a token that cannot read what it was asked to repair. No backfill, no state migration, nothing in flight to strand: pre-existing issues carry no shape this change reads that they did not already carry.

Rollback is revert. Older code never parses `/fix` — it falls out of `parseSlashCommand` as no command and the PR door drops it at the free filter — so a reverted agent leaves a typed `/fix` quietly unanswered (the pre-change status quo), never misparsed.
