# Alert activity condition (Session 3)

## Goal
Add an activity-based alert condition kind — `{ kind: 'activity', taskId: string, categories?: string[] }` — so alerts can fire on new task-history entries (comments, description edits) for a specific task, evaluated by polling the provider's existing optional `getTaskHistory` (gated by the existing `activities.read` capability). Prior sessions' behavior must not regress: `alert_prompts.task_instance_id` pinning and the pure-watch `task.id` eq condition with targeted `getTask` polling stay intact. No webhooks, no new `TaskCapability` values, no provider changes — polling only.

## Intended behavior change
- Schema: activity leaf accepted with/without categories, missing `taskId` rejected, nests under and/or with other activity leaves; `describeCondition` renders it.
- Polling semantics: first poll = baseline — store the newest activity timestamp as `last_activity_cursor`, fire nothing. Later polls fire when entries newer than the cursor appear (categories passed through); after successful delivery, cursor advances to newest seen and `lastTriggeredAt` is set (cooldown reuses the existing `getEligibleAlertPrompts` filter); entries at/below the cursor never refire. Multi-leaf activity trees watch the union of their taskIds with the single per-alert cursor = max newest timestamp seen.
- Creation gating: activity conditions are only accepted when the context's pinned task provider exposes `activities.read` + `getTaskHistory` and a task instance is configured; otherwise a guidance error result (same shape as other tool errors).
- Assumption (stated, cheap to veto): mixing activity leaves with field-value leaves in one condition tree is refused at creation with a guidance error — only pure-activity or pure-field trees are pollable this session — while the schema itself still nests activity leaves under and/or, and evaluation walkers treat stray activity leaves as non-matching rather than crashing.
