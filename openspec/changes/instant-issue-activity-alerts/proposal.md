# Instant notifications for issue activity (#418)

## Goal
Make GitHub issue-activity notifications arrive within the existing 5-minute alert-poll cycle instead of the 2-hour reminder workaround, and make them creatable at all. Codebase evidence:

- **The alert engine already fires in minutes**: `ALERT_POLL_MS = 5 * 60_000` (`src/deferred-prompts/poller-lifecycle.ts:15`) drives `pollAlertsOnce`. The issue's "2-hour polling" is the *reminder-based* watchlist workaround, not the alert path. Item 3 is therefore verification + docs, not a cadence change.
- **Blocker (item 1)**: `create_alert` is unusable. `alertConditionSchema` (`src/deferred-prompts/condition-schema.ts:80`) is a `z.union` of four object shapes; AI SDK v7 (`ai@^7.0.79`, zod `^4.4.3`) validates model tool-call args against this zod schema before `execute`, and when the model emits `condition` as a JSON *string* (common against `anyOf` positions), validation fails with the observed `AI_InvalidToolInputError` → `path ["condition"], "expected object, received string"`. `create_reminder`'s `schedule` (plain object schema) parses fine — consistent. The repair seam deliberately returns null for `InvalidToolInputError` (`src/tools/disclosure/repair-tool-call.ts:15`). Both `create_alert` (`src/tools/create-alert.ts`) and `update_reminder` (`src/tools/update-reminder.ts:30`) embed this schema, so one schema-level fix covers both.
- **Comment alerts can never fire on GitHub (item 2)**: sessions 1–3 landed the full activity engine (cursor baseline/edge, categories, cooldown, capability gating — `src/deferred-prompts/poller-alerts-activity.ts`), but the GitHub provider's `getTaskHistory` fetches only `/repos/{repo}/issues/{n}/events` (`plugins/task-provider-github/operations/activities.ts:68`), which never contains `commented` events — the `case 'commented'` mapping is dead code. Comments must be merged in from the comments endpoint.
- **New-issue alerts would replay the backlog**: a filter alert `{"field":"task.project","op":"eq","value":"<repo>"}` fires on the match edge (`collectFieldFirings`, `src/deferred-prompts/poller-alerts-watch.ts:65`), so newly created issues do fire — but `matchedTaskIds` starts `[]`, so the first poll fires for every pre-existing match. This is exactly the pending "#401 bug 3, lane b" decision (`openspec/changes/deferred-prompt-proof-checks/proposal.md:64`); the issue instructs: adopt baseline-on-create, do not change pure-watch semantics.
- **Close semantics are mostly sound**: `foldStatus` (`plugins/task-provider-github/mappers.ts:28`) keeps `closed` vs `closed (not_planned)` distinct, so a not_planned close is never reported as `closed`-completed; targeted per-task watches (`getTask`) see closed issues; GitHub events map `closed` → activity category `status` (`operations/activities.ts:43`). Note the whole-list path fetches only open issues (GitHub `listTasks` default), so `task.status changed_to "closed"` via the field path is unreliable on GitHub — close coverage comes from per-task watches/activity, which is what the watchlist needs. Document; don't change fetch semantics.

## Intended behaviour change
- `create_alert`/`update_reminder` accept a condition sent as a JSON-encoded string (and still reject invalid ones) — the union-typed param no longer fails tool-input validation.
- GitHub `getTaskHistory` now emits `comment` activity entries, so per-issue comment alerts fire on GitHub within the 5-minute poll cycle.
- Filter (project/field) alerts baseline on their first evaluation cycle instead of firing for the pre-existing backlog — resolves the pending #401 bug-3 lane-b decision as directed by the issue; pure-watch and activity semantics unchanged.
- No delivery-path changes (#417 consistency): `sendProactiveMessage`, batching, and cooldown behavior are untouched; no cadence change.

## Non-goals
Webhooks or any event-push integration; per-project comment watching (activity conditions stay per-task); changing pure-watch semantics, the 5-minute poll cadence, or the proactive delivery path; any provider change beyond the GitHub activity merge; the watchlist migration itself (ops).

## Capability
`issue-activity-notifications` (new — nothing archived under `openspec/specs/` for this domain): tool-surface acceptance of stringified alert conditions, GitHub comment visibility in task-history activity, and baseline-on-create semantics for filter alerts so instant new-issue/comment/close notifications behave without backlog replay.
