# Design — sdd-runner-decomposition (part 1 of 3)

## Context

See `proposal.md` for motivation and the maintainer revisions (no child cap; `PLAN_REPLAN_PASSES` semantics). This part is a pure data layer: schemas, pure functions, and additive persisted-state/event surface — no producer or consumer of the new shapes runs at pipeline time.

Current state that constrains the approach:

- `sdd-runner/src/events.ts` keeps every event as a Zod input variant plus a stamped variant in `EventInputSchema`/`SddEventSchema`; `events.ndjson` is append-only and replay-sufficient (`docs/architecture/sdd-pipeline.md`, Event model). New event types must join **both** unions or `appendEvent`/`readEvents` disagree.
- `PersistedRunStateSchema` (`run-state.ts`) has an established additive-field precedent (`roundCap`, `gateDeadlineAt` with `.default(null))` — old `state.json` files must keep parsing, which every addition here follows.
- The `'early' | 'final'` gate-mode literal is mirrored in plain TS types beyond `events.ts`/`run-state.ts`: `PendingGateEntry.gateMode` (`run-state.ts:138`), `ReplayState.gate.mode` (`replay.ts:33`), `latestSettledGate` (`gate.ts:216`), and narrow consumers (`deadline-waiter.ts`, `extend-round.ts`, `gate-resume-tail.ts`). Widening the enum ripples at type level; see D8.
- `deriveChangeName` (`config.ts:123`) owns the slug transform; `materialize.ts` owns the `<!-- GENERATED by sdd-runner ... -->` marker convention. Both are reused, not reinvented (the repo runs a duplicates gate).
- Repo rules that bind the implementation: DI-first testing (prefer injected seams over `mock.module()`), no lint-disable/type-ignore comments, strict TypeScript with `.js` import extensions, `max-lines` as a design signal, and the Write/Edit TDD hook pipeline — which **does** gate `sdd-runner/src/` (`sdd-runner/src/foo.ts` maps to `tests/sdd-runner/foo.test.ts` in `.hooks/tdd/test-resolver.mjs`).

## Goals / Non-Goals

**Goals:**

- A hermetic, deterministic plan data layer: validate → topo-sort → digest → materialize, all pure or fs-injected, fully testable without a real filesystem.
- Old `state.json`, `events.ndjson`, and depth-classification sidecars parse identically after the change (pinned by tests, not by hope).
- A contained, behavior-preserving type-level accommodation for the `'plan'` gate mode so parts 2–3 can emit/persist it without another schema edit.
- Resume/replay semantics that recognize a materialized plan without changing any decision a non-parent run receives.

**Non-Goals:**

- Anything observable at runtime: no event emitter, no state writer, no planner spawn, no CLI surface in this part.
- Defining what a `'plan'` gate *renders* or how it is decided — part 3.
- Child-run spawning, scheduling, concurrency, or budget accounting — parts 2–3.
- Chat-bot surfaces: this change adds **no chat tool**, so capability gating and `tool_prefs` are untouched (no tool surface exists to gate; `sdd-runner/` is an offline workspace, not the bot).
- **Scope model:** no new persisted state is keyed by storage context, config context, platform instance, or user. All new persisted state lives in the sdd-runner workdir keyed by **run id** (`runs/<parent-runId>/children/` files; `plan`/`children` fields inside `runs/<runId>/state.json`).
- **DB:** no drizzle migration, no backfill — SQLite is untouched.

## Decisions

### D1 — New module `sdd-runner/src/plan.ts`; no existing module covers the need

Checked: `decompose.ts` is stage *agent orchestration* over `tasks.md` (prompt + spawn + rewrite), not a data model; `materialize.ts` renders review/assumptions from round sidecars; `config.ts` is runner configuration; `stage-machine.ts`/`orchestrator.ts` are control flow. None validates a graph, topologically sorts, or writes per-child task files — `plan.ts` is new because nothing does this. Alternative rejected: folding into `decompose.ts` (wrong altitude, and it would push an already-large orchestration file into `max-lines` territory).

### D2 — Two-layer validation: Zod shape, then one error listing *all* structural violations

```ts
const PlanChildSchema = z.object({
  id: z.string().min(1),
  instruction: z.string().min(1),
  deps: z.array(z.string().min(1)).default([]),
  capabilities: z.array(z.string().min(1)).optional(),
})
const PlanSchema = z.object({ children: z.array(PlanChildSchema).min(1) })
```

`validatePlan(input)` parses, then runs structural checks — unique ids, every dep resolves, no self-dependency — and throws a **single** error enumerating every offending id. Rationale: the part-2 replan loop feeds this message back to the planner agent (the `PLAN_REPLAN_PASSES` mechanism); fail-fast would burn a replan pass per violation. Alternative rejected: `.superRefine` on the schema — workable, but couples graph checks to the shape schema and makes multi-id diagnostics awkward; cycles additionally don't belong there because they are a sort-time property (D3).

`children.min(1)` is the only cardinality constraint — a structural floor (zero children is not a plan), explicitly **not** a cap; an 8-child regression test pins that no ceiling can be silently reintroduced (maintainer revision 1).

### D3 — Deterministic Kahn topological sort; cycle diagnostics via the leftover set

`topoSortChildren(plan)` runs Kahn's algorithm with the ready-queue ordered by **declaration index**, so output is a pure function of (declaration order, dep edges). That determinism is load-bearing: stable `<n>-<name>.md` file numbering, stable digest (D4), stable `plan.childIds` in persisted state, stable replay. Alternatives rejected: DFS post-order (no canonical tie-break), no sort in part 1 (materialization needs a stable order now).

`validatePlan` has already rejected unknown/self deps, so Kahn can only fail on cycles. On failure the leftover node set (cycle members **plus** their transitive dependents) is named: `dependency cycle among: a, b, c`. Alternative rejected: Tarjan SCC for exact cycle membership — extra machinery for a diagnostic string; the superset is precisely the set the planner must be shown because every node in it is stuck.

### D4 — Digest = sha-256 over the topo-ordered child-id array

`createHash('sha256')` (`node:crypto`, no new dependency) over `JSON.stringify(childIdsInTopoOrder)`, sliced to a 16-hex prefix. Part 1 only computes and records it (event `plan`, `state.plan.digest`); parts 2–3 consume it to detect plan-vs-state drift on resume/regeneration. It is order-sensitive **by design** — declaration order is part of plan identity, so a re-declared plan digests differently and is treated as a new plan.

### D5 — Materialization: marker + slug reuse + injected fs seam

One file per child at `runs/<parent-runId>/children/<n>-<name>.md` (n = 1-based topo index, name = slug of the child id), headed by the `materialize.ts`-style `<!-- GENERATED by sdd-runner ... -->` marker, then the child id, instruction, deps, and capabilities. Three sub-decisions:

- **Slug:** extract the transform inside `deriveChangeName` into an exported `slugify()` in `config.ts` and call it from both sites. Duplicating the regex chain in `plan.ts` would trip the repo's duplicates gate and drift. (`config.ts`'s diff grows by one export beyond the proposal's role/constant — accepted; it is the same module the proposal already touches.)
- **fs seam:** `materializeChildFiles(plan, runDir, deps?)` takes `{ mkdir, writeFile }` defaulting to `node:fs/promises` — DI-first per `tests/CLAUDE.md`; hermetic tests use a fake; one default-seam smoke test against a tmpdir keeps the real-path integration honest. Alternative rejected: `mock.module()` of `node:fs/promises` — the repo prefers DI where the module supports it.
- **Idempotence:** wholesale rewrite of the `children/` files per call (the `decompose`-rewrites-`tasks.md` doctrine) — a re-materialize after a crash is wasted bytes, never corruption.

### D6 — `PLAN_REPLAN_PASSES = 1` as a compiled constant; five-key config untouched

Exported from `config.ts` beside `WALL_CLOCK_TIMEOUT_MS`/`INACTIVITY_TIMEOUT_MS`. Alternatives rejected: a sixth config key (the strict `RunnerConfigSchema` and its removed-key error surface are a deliberate contract; a bound this internal is not an operator knob); folding into `MAX_VALIDATION_ATTEMPTS` (different failure class — that constant bounds JSON-shape retries inside `runStageAgent`; this one bounds structural replan passes outside it). Part 1 defines it; part 2 is its sole consumer; deleting it before part 2 lands is a one-line change.

### D7 — Three L2 event variants follow the existing convention

```ts
{ altitude: 'L2', type: 'plan',          childCount: number, digest: string }
{ altitude: 'L2', type: 'child_spawned', child: string }
{ altitude: 'L2', type: 'child_done',    child: string, outcome: 'done' | 'failed' }
```

Each is added to `EVENT_VARIANTS` (→ `EventInputSchema`) and, with `StampShape`, to `SddEventSchema` — the two-union convention every existing variant follows. Payloads stay minimal (proposal: "child count + digest", "child id", "child id + outcome"); anything richer is a part-2/3 need and lands then. `child_done.outcome` starts two-valued; widening an emitted-value enum later is additive in the same way `done.model` was.

### D8 — Gate-mode widening: widen mirrors, keep behavior surfaces narrow

`GateEvent.mode` becomes `z.enum(['early', 'final', 'plan'])` and `PersistedRunStateSchema`'s inline gate object aligns. The rule for the ripple: **pure mirrors of the enum widen; behavioral consumers stay narrow.**

- Widen (type mirrors only): `PendingGateEntry.gateMode`, `ReplayState.gate.mode`, `latestSettledGate`'s parameter/return type in `gate.ts`.
- Stay narrow: decision/presentation surfaces (`gate-prelude.ts` ladder, `gate-render.ts` mode-conditional phrases, `translateSteer`, `prepareResumeInput`). They already branch on `mode === 'early'`; call sites whose argument is now typed wider get an unreachable-in-part-1 narrowing guard. No `'plan'` value is ever emitted or persisted in part 1, so every guard is compile-time scaffolding with zero runtime effect — and strict TypeScript surfaces exactly the sites that need it, which is how the ripple set was found.

Alternative rejected: widening every `'early' | 'final'` annotation repo-wide — that would silently grant `'plan'` to surfaces that cannot render or decide it. Part 3 wires the plan gate's real consumers.

### D9 — Additive state fields and a total children fold

```ts
plan:     z.object({ childIds: z.array(z.string().min(1)).min(1), digest: z.string().min(1) }).optional()
children: z.record(z.string(), z.object({ status: z.enum(['pending', 'running', 'done', 'failed']) })).optional()
```

Both optional, matching the `gateDeadlineAt` precedent — old files parse unchanged (pinned). In `replay.ts`, `ReplayState.children` starts `{}`; the `plan` event seeds every child id as `pending`; `child_spawned`/`child_done` transition status, and a mention of an unseeded id creates its entry rather than erroring — the fold stays total over any valid event sequence, so logs from part-2 code replay under part-1 rules without special cases. Logs without the new events fold to today's state plus the empty `children` field (pinned byte-for-byte on the fields that exist today).

### D10 — `deriveResumePoint` parent branch: after gate-pending, before the cascade

Placement: immediately after the `state.gate !== null` check — a pending gate (including a future `'plan'` gate) still wins, because answering it is always the next action. The parent branch fires only when `state.plan` exists **and** at least one `plan.childIds` entry lacks `children[id].status === 'done'` (a missing `children` map counts as all-pending); it returns `{ stage: 'decompose', round: state.round, reason: 'children pending: next <id> (k of n)' }` — the next pending child in topo order. When every child is done it falls through to the existing cascade (part 3 owns the parent tail). `StageIdSchema`/`STAGE_ORDER` are untouched, per the proposal; `'decompose'` is the honest existing vocabulary for "executing this run's decomposition". Alternative rejected: a new stage id — rejected precisely because it would ripple `STAGE_ORDER`, the stage map views, and the resume vocabulary that the proposal pins as unchanged. Non-parent states take the identical branches as today (pinned).

### D11 — No new dependencies; stack sufficiency

Zod v4 covers all validation; `node:crypto` the digest; `node:fs/promises` (injected) the IO. Nothing in the installed stack — or the chat-side stack (AI SDK, Grammy, discord.js, drizzle), which `sdd-runner/` does not even import — offers graph validation or topological sorting that would justify an addition.

## Hook / TDD interaction

The Write/Edit hook pipeline gates every implementation file this change touches, mapping `sdd-runner/src/<x>.ts` → `tests/sdd-runner/<x>.test.ts`. Red-first order of work, one task per green step:

1. `tests/sdd-runner/plan.test.ts` red (schema, `validatePlan` full-error-list, topo determinism, cycle leftover-set message, 8-child no-cap, fs-fake materialization, tmpdir smoke) → `sdd-runner/src/plan.ts` green (tasks 1.1–1.2).
2. `config.test.ts` red (`'planner'` role parses; `slugify` shared-shape pins; `PLAN_REPLAN_PASSES` exported) → `config.ts` green (task 2.1).
3. `agent-layer.test.ts` red (`DepthClassificationSchema` with and without `capabilities`) → `agent-layer.ts` green (task 2.2).
4. `events.test.ts` red (three new variants stamp + round-trip through `appendEvent`/`readEvents`; `mode: 'plan'` gate event parses; old lines unchanged) → `events.ts` green (task 3.1).
5. `run-state.test.ts` red (old `state.json` fixtures parse; `plan`-bearing state round-trips; parent-branch resume points; non-parent decisions byte-identical) → `run-state.ts` green (task 3.2).
6. `replay.test.ts` red (old logs fold to today's state + empty `children`; plan-seeded transitions; first-mention creation) → `replay.ts` green (task 3.3).

D8's narrowing guards land with step 4/5 as typecheck demands them; each is covered by the surrounding suites' existing behavior pins. Edit loop uses `bun run test:affected`; one full `bun run test` + `typecheck` + `lint` before finishing (never two full suites concurrently).

## Risks / Trade-offs

- [Enum widening ripples into modules outside the proposal's file list (`gate.ts`, `deadline-waiter.ts`, `extend-round.ts`, `gate-resume-tail.ts`)] → D8's mirrors-only rule keeps each accommodation mechanical and behavior-free; strict typecheck enumerates the sites; existing suites pin behavior; part 1 never produces a `'plan'` value at runtime.
- [`children` status/outcome enums may need new members in parts 2–3 (e.g. skipped)] → additive enum growth is the established compat pattern (`done.model`, `gateDeadlineAt`); writers and readers ship in the same repo, so no version skew exists.
- [Digest is order-sensitive — a semantically identical re-declared plan digests differently] → intentional: declaration order is part of plan identity, and false "same plan" on regeneration would be the worse failure; a mismatch is handled by parts 2–3 as a new plan.
- [Cycle diagnostic names dependents of cycles, not just cycle members] → the message scopes itself ("cycle among"); the superset is exactly the stuck set the planner must see.
- [Injected fs seam can drift from real fs behavior] → one default-seam smoke test writes through `node:fs/promises` to a tmpdir.
- [Part 1 ships code with no runtime consumer — dead-code and mutation-score risk] → every export is exercised by exhaustive pure-function tests (cheap for validators/sorts), which is also what the Stryker per-file ratchet measures; the `knip` gate is satisfied because parts 2–3 import these symbols from this change's own task list, and the symbols are consumed by tests now.

## Migration Plan

No database, no drizzle migration, no backfill. Deployment is the commit `sdd-runner-decomposition(1/3)`. Because part 1 adds no producer, no existing run directory changes shape on disk after deployment — new fields/files appear only when parts 2–3 run. Rollback is reverting the commit; state written by part-1 code is indistinguishable from pre-part-1 state, so an older checkout resumes any run without special handling.
