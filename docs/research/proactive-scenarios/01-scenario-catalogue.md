# Proactive Scenario Catalogue and Taxonomy

> **Workstream:** WS-A — Scenario catalogue and taxonomy
> **Status:** Research artifact; not an implementation commitment
> **As of:** 2026-07-19
> **Scope:** Ways papai may communicate or act without a new user request, plus reactive/control
> behaviors that define the boundary of that product space.

## 1. Executive findings

The mined sources describe **50 distinct records**: 39 content/automation candidates (including one
currently silent automation boundary), eight delivery-control behaviors, and three contextual or
configuration boundary records. They are not all equally real. papai currently ships a capable
_user-authored automation substrate_ (one-shot/recurring
scheduled prompts, field predicates and `changed_to`/`overdue` alerts), several direct operational
notification paths, and reviewed announcements. It does **not** yet ship the opinionated task-health,
briefing, planning, calendar, or general notification-control product described by Phases 9–11.

The main distinctions later workstreams must preserve are:

1. **A trigger is not a reason to interrupt.** Current deferred alerts send whenever their predicate
   matches and the cooldown allows it. Product scenarios need a separate send-now/batch/drop decision.
2. **Time and state scenarios are usually compound.** “Overdue”, “stale”, “one day before”, workload
   overload, and plan reviews all require both passage of time and current state. Calling them merely
   “scheduled” hides their data and dedup requirements.
3. **Conversation-aware planning is mostly reactive today.** “What next?”, structured morning
   planning, gap-aware recommendations, and end-of-day review are valuable but do not become
   proactive merely because an assistant generates them. The catalogue marks them
   `contextual-only` until a separate opt-in trigger exists.
4. **Audience is a product decision, not a transport detail.** Current deferred prompts can target a
   DM, group main context, or the originating group thread and can mention the requester, named users,
   or nobody. Task-health stories generally say “me” and leave group/thread ownership ambiguous.
5. **Controls are gating requirements.** Quiet hours, working days, digest/mute, feature toggles, and
   snooze/dismiss are documented but unimplemented. Scaling beyond explicit user-created reminders
   before at least quiet hours and a master mute would violate the research plan's opt-in bias.
6. **Several old usage scenarios are catalogue intent, not current behavior.** In particular,
   `configure_briefing`, `configure_alerts`, missed-briefing catch-up, and automatic startup fan-out
   are not evidenced in current symbols. Current release announcements are reviewed and opt-in.

## 2. Taxonomy

### 2.1 Unit of catalogue

A **scenario** is a user-observable message or automated action with a distinct firing condition,
audience, urgency expectation, value hypothesis, or failure profile. An implementation primitive
becomes a scenario when users experience it directly (for example, an arbitrary scheduled prompt or
an external coding-session milestone). Pure storage, configuration, and suppression rules are listed
as **control/boundary records** so every mined user story remains traceable, but they are not counted
as unsolicited-message scenarios.

Scenario IDs are stable and family-prefixed:

- `AUT-*` — current automation and operational messaging;
- `TSK-*` — task-health and deadline suggestions;
- `PLN-*` — briefing and planning assistance;
- `CAL-*` — calendar-originated messaging;
- `CTL-*` — delivery controls and contextual/configuration boundaries.

Splitting or merging a record in later research should retain the old ID as an alias or tombstone.

### 2.2 Trigger type

| Code | Trigger                    | Definition                                                                                                                                                     |
| ---- | -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `T`  | **time**                   | A wall-clock instant, recurrence, elapsed interval, workday boundary, or release from a held window.                                                           |
| `Δ`  | **task-state-delta**       | A task or task-set enters, leaves, or changes a state. Static predicates are explicitly marked `Δ-state`; comparisons to a stored prior value are `Δ-change`.  |
| `C`  | **conversation-inference** | A prior conversation created relevant context or a completed reactive turn implies a follow-up; a direct request is marked `C-request` and is not unsolicited. |
| `X`  | **external-signal**        | An event originates outside papai's task/conversation state: service webhook, calendar, deployed version, or human admin action.                               |

Compound triggers are written with `+`, and all parts are required unless the evidence offers multiple
entry paths. For example, `T+Δ-state` means “the time boundary passed and the task is still open.”
`T or C-request` means the story supports separate proactive and reactive branches.

### 2.3 Cardinality and audience

| Value       | Meaning                                                                                                          |
| ----------- | ---------------------------------------------------------------------------------------------------------------- |
| `1:1 DM`    | One private chat target. “Creator”, “assignee”, “manager”, or “admin” further identifies the intended recipient. |
| `group`     | One group main context, visible to the group; mention policy must be stated.                                     |
| `thread`    | One originating group thread/topic, preserving the thread-scoped storage context.                                |
| `broadcast` | One source message fans out to multiple DMs and/or group main contexts.                                          |

`DM/group/thread` means the scenario follows the context in which its automation was created; it does
not mean cross-posting to all three. Current delivery evidence is
`DeferredPromptDelivery`, `deliveryPolicySchema`, and `buildDeliveryInput` in
`src/deferred-prompts/types.ts` and `src/deferred-prompts/delivery-input.ts`.

### 2.4 Urgency

| Value               | Definition                                                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| **interrupt-now**   | Delay materially reduces value or creates risk. This still does not imply bypassing quiet hours unless explicitly stated.       |
| **digest-safe**     | Useful after batching/deduplication; seconds or hours of latency do not defeat the value.                                       |
| **contextual-only** | Should appear only in an active/requested conversation or as part of another briefing, not as a standalone unsolicited message. |

### 2.5 Execution-mode need

The mode is the least expensive mode that can produce a trustworthy result, using the shipped
definitions in `EXECUTION_MODES` and `executionInputSchema`
(`src/deferred-prompts/types.ts`):

- **lightweight** — no conversation history or task tools; fixed/direct sends are noted
  `lightweight (direct)` because they need no LLM at all.
- **context** — conversation history is required, but no live task-provider operations.
- **full** — current task/calendar/provider data or tool execution is required.
- **standalone LLM + direct** — a code-owned one-call transformation with no deferred conversation
  history or toolset, followed by direct delivery; this is not the deferred `full` mode.
- **direct mutation** — deterministic application code performs an already configured provider
  mutation without the proactive L/C/F execution pipeline.
- **selectable L/C/F** — the general deferred-prompt substrate stores the creator's classification;
  it is not a property of one fixed product message.

Delivery gates such as quiet hours inherit the candidate's generation mode; their own queue/send step
is classified `lightweight (direct)`.

### 2.6 Lifecycle and maturity

| Label                                   | Meaning                                                                                                                                       |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **implemented — product path**          | Current code directly produces the described user-visible behavior.                                                                           |
| **implemented — substrate**             | Current generic machinery can express the behavior only when a user/LLM explicitly creates it; there is no product-owned default or detector. |
| **partially expressible**               | Some pieces exist, but the dynamic trigger, audience, lifecycle, or product composition does not.                                             |
| **documented — unbuilt**                | A Phase/user-scenario requirement with no matching current product path.                                                                      |
| **approved design — unbuilt**           | An approved adjacent design exists, but current code search found no implementing surface.                                                    |
| **reactive boundary**                   | Valuable behavior exists only after a direct request; included to prevent accidental claims of proactivity.                                   |
| **control/enabler — unbuilt**           | A preference or lifecycle operation governing messages rather than a new content scenario.                                                    |
| **legacy claim — unverified/unshipped** | Older scenario documentation uses an obsolete API/behavior and must not be cited as current state.                                            |

### 2.7 Current implementation invariants used in classification

The catalogue treats these as established constraints, not candidate features:

- `startPollers` registers scheduled polling every 60 seconds and alert polling every five minutes;
  the intervals and bounded concurrency are in `src/deferred-prompts/poller.ts`.
- `dispatchExecution` selects `lightweight`, `context`, or `full` in
  `src/deferred-prompts/proactive-llm.ts`. `buildFullToolSet` in
  `src/deferred-prompts/proactive-llm-full.ts` assembles the proactive toolset and applies contextual
  tool preferences; proactive work does not gain a separate permission bypass.
- `buildProactiveTrigger` in `src/deferred-prompts/proactive-trigger.ts` puts stored user prompt text
  and matched task data in user content rather than elevating them into system instructions, and
  tells the model to deliver rather than create another schedule. This is only a partial invariant:
  `buildMetadataMessages` in `src/deferred-prompts/proactive-llm-helpers.ts` separately emits stored
  delivery briefs and context snapshots as system-role messages, so those fields still need an
  explicit trust-boundary review.
- `sendProactiveMessage`/`resolveProactivePlatformInstanceId` in
  `src/deferred-prompts/proactive-delivery.ts` preserve the stored target and resolve an active
  platform instance. `recordProactiveInHistory` in `src/proactive-history.ts` best-effort records a
  successfully sent direct message in the exact thread-scoped conversation bucket.
- `ENTITY_SCOPES` in `src/chat/context-scope.ts` makes prompt delivery/history/snapshots
  thread-scoped while prompt creator/config ownership is group-scoped. A preference decision and a
  delivery decision may therefore require different keys.
- `docs/architecture/overview.md` (`src/run-control/`) states that run-control is `normal` mode only;
  proactive runs cannot be steered or stopped mid-run. This raises the bar for any `full` scenario
  that could perform lengthy or mutating work.
- Quiet hours, working days, digest/muted delivery, per-feature controls, and generic
  snooze/dismiss/reschedule have no current product symbols; Phase 10 marks them not implemented.

## 4. Scenario-family analysis

### 4.1 Explicit automation is mature; autonomous product judgment is not

AUT-001–005 are opt-in because a user asks the LLM to create a precise schedule or condition. That
explains why the current system can safely support arbitrary reminder text and conditional alerts
without yet possessing a global notification preference model. The code persists the delivery target,
creator, execution metadata, recurrence/condition, cooldown, and status; polls scheduled prompts every
60 seconds and alerts every five minutes; then dispatches one of three execution modes
(`ScheduledPrompt`, `AlertPrompt`, `startPollers`, and `dispatchExecution` in
`src/deferred-prompts/`). This is a strong substrate for experiments, not evidence that papai already
knows which task-health events deserve interruption.

The current field model is narrower than Phase 9:

- directly observable: status, priority, assignee, due date, project, labels;
- delta-snapshotted: status, priority, assignee, due date, project;
- `changed_to` implemented only for status, priority, assignee;
- absent: task creation, description/scope semantics, updated/comment activity, dependency changes,
  status-order regression, capacity/duration.

WS-B should therefore distinguish “the provider may expose a field” from “the current alert DSL can
detect the scenario.”

### 4.2 Task-health scenarios form lifecycles, not isolated notifications

Deadline scenarios should be modeled as one lifecycle with stages: pre-deadline (TSK-011), due-day
(TSK-012), first overdue response (TSK-006), later escalation (TSK-013), snooze/dismiss/reschedule
(CTL-007/008), and eventual resolution/suppression. AUT-005 is the generic condition substrate, not a
fifth product stage. A stable per-task/per-lifecycle identity is needed to stop each stage from
creating a new independent notification.

Likewise, completion has three distinct outcomes that should not be collapsed:

- AUT-008 silently creates the next instance of an explicitly configured on-complete template;
- TSK-005 proposes context-dependent next steps and potentially asks permission for writes;
- PLN-007 later evaluates completion against a user-confirmed daily plan.

### 4.3 Briefing and digest are different layers

TSK-008/009/010 and PLN-004 are authored content products. CTL-004 is a delivery policy that may
combine candidates from any product. A morning briefing can itself be immediate or digested; a daily
digest should not implicitly become a morning briefing. The phrase “briefing” is also overloaded
across the sources: task-only daily briefing, calendar-enriched briefing, weekly kickoff, end-week
review, on-demand briefing, and missed-briefing catch-up.

### 4.4 Planning value is conversational by default

PLN-001/002/005/006/007 are explicitly requested in their acceptance criteria. They should remain
reactive until research supplies a separate, opt-in activation event. PLN-003 and PLN-004 have real
proactive branches because the sources place them in a scheduled morning briefing. This distinction
avoids turning “assistant can answer this” into “assistant should interrupt with this.”

### 4.5 External and broadcast paths need their own trust model

AUT-006 and AUT-009–011 bypass the deferred LLM decision path. Their content is already determined by
a trusted service or administrator, so execution mode is not the risk boundary. Authentication,
target correctness, opt-in, approval, rate/frequency, and per-recipient dedup are. Release broadcast
already demonstrates useful patterns: default-off subscription, one shared reviewed message,
idempotent recipient records, bounded fan-out, and failure isolation. The manual admin broadcast is
an intentionally different emergency/general path with broader reach and fewer controls.

### 4.6 History is shared machinery, not a trigger

The proactive-history design audited six content-bearing outbound paths. Every one maps to a record:

- release subscriber broadcast → AUT-010;
- admin free-text broadcast → AUT-011;
- release review notice → AUT-009;
- recurring-task-created ping → AUT-007;
- external notify → AUT-006;
- deferred failure branches → AUT-012.

Deferred success delivery under AUT-001–005 is the reference path. `recordProactiveInHistory` stores
faithful assistant text after successful direct delivery, while deferred LLM results preserve their
own persistence ordering. History makes later conversation coherent; it should support dedup and
follow-up research, but the mere presence of old history is not permission to initiate a message.

## 7. Research conclusions feeding later workstreams

### WS-B — trigger feasibility

1. Evaluate compound triggers as first-class records. TSK-002, TSK-004, TSK-007, TSK-011–015,
   PLN-003/004, and CAL-002–004 cannot be assessed from a clock or one field alone.
2. Produce a provider-by-provider field matrix for creation time, updated/comment time, description,
   relations, workflow order, due-time semantics, duration estimates, and webhook/delta support.
3. Separate current DSL feasibility from provider feasibility. Due-date snapshots exist but arbitrary
   “pushed back” comparison does not; task descriptions may exist at the provider but are absent from
   `CONDITION_FIELDS` and snapshots.
4. Verify audience routing for AUT-007 and all group/thread scenarios rather than assuming a user ID
   is always a DM.

### WS-C — decide to interrupt

1. Use a candidate identity at least as specific as `(feature, task/event, lifecycle stage,
audience)` so TSK-006/011/012/013, briefings, and digests deduplicate coherently.
2. Treat user-authored exact reminders (AUT-001/002), trusted external input-needed milestones
   (AUT-006), hard due-day alerts (TSK-012), calendar events (CAL-001), and sync/auth conflicts
   (CAL-003/004) as the only plausible interrupt-now class. Every other family should default to
   digest-safe or contextual-only.
3. Score repeated static predicates differently from true deltas. A still-true `neq` or `overdue`
   predicate is not fresh evidence after the first delivery.
4. Dedup against conversation/proactive history, but never treat history alone as permission to send.

### WS-D — notification controls

1. Minimum control set implied by this catalogue is: master mute, quiet hours, urgent bypass opt-in,
   working days, per-feature keys, and one-candidate dismiss/snooze state. Digest is valuable but
   requires a queue/ranker and may be a second increment.
2. Define whether controls apply to explicit user-created reminders, service milestones, manual admin
   emergencies, release announcements, and operational failure notices; “all proactive” is currently
   ambiguous.
3. Resolve scope conflicts: creator/group config can be group-scoped while delivery and history are
   thread-scoped, and a member's personal quiet hours may conflict with a group-admin briefing.

### WS-E — scope and delivery

1. Carry all four audience forms—DM, group main, exact thread, broadcast—through the matrix.
2. Specify mention and ownership policy for task-health scenarios; Phase 9's “me” cannot safely imply
   a whole group.
3. Treat group calendar content as private by default until explicit calendar ownership and redaction
   rules exist.
4. Account for the lack of run-control on `full` proactive runs; long planning or multi-write
   completion scenarios should prefer a short suggestion/confirmation flow over autonomous work.

### WS-F — safety and trust

1. Threat-model task descriptions, calendar event text, external notify markdown, stored delivery
   briefs, and context snapshots as untrusted content. `buildProactiveTrigger` correctly keeps its
   stored user text and matched task summaries out of system-level instructions, but
   `buildMetadataMessages` still emits other stored metadata with the system role and full-tool
   execution still requires least privilege.
2. Review raw error strings in AUT-012 and external/broadcast trust boundaries independently of LLM
   prompt injection.
3. Make audience correctness a release blocker for group/thread candidates; wrong-context delivery is
   a privacy failure, not merely a UX bug.

### WS-G — synthesis and prioritization

The catalogue supports a thin-increment comparison rather than preselecting a winner:

- **lowest new-trigger effort:** productize an existing condition such as first overdue crossing
  (TSK-006 on AUT-005), but only with lifecycle dedup and basic controls;
- **lowest interruption risk:** task-only daily briefing (TSK-008) or weekly review (TSK-009) after
  working-day/quiet-hour support;
- **highest explicit-intent safety:** improve AUT-001/002 lifecycle controls and truthful history;
- **highest dependency/risk:** semantic scope reduction, staleness without provider timestamps,
  calendar planning, and autonomous completion follow-ups.

Any prioritization should score the _product scenario_, not the presence of a generic substrate. A
scenario that is technically expressible through a user-authored deferred prompt may still require
substantial product work in detection, ownership, controls, relevance, and safety.
