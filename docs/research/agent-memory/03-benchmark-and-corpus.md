# Benchmark and corpus

This document describes the frozen benchmark inputs and the identity of the
checked-in experiment artifacts. The normative scoring rules and gates remain
in the [research protocol](00-protocol.md); the measured decision is reported
in [04-results.md](04-results.md).

## Evidence boundary

The benchmark is an offline component-retrieval experiment. It compares four
implementations behind the same adapter:

| Candidate          | Frozen version        | Representation                                        |
| ------------------ | --------------------- | ----------------------------------------------------- |
| `as-shipped`       | `as-shipped-v1`       | Active-record retrieval/injection proxy               |
| `corrected-hybrid` | `corrected-hybrid-v1` | Dense/lexical fusion with validity and erasure        |
| `hierarchical`     | `hierarchical-v1`     | Canonical events plus rebuildable facts and summaries |
| `temporal-graph`   | `temporal-graph-v1`   | Canonical events plus a rebuildable temporal graph    |

It measures retrieval, safety, rebuild agreement, latency, and resource use. It
does not measure final-answer quality, live-reader behavior, graph extraction
quality, production traffic, or operational readiness. Artifact id
`as-shipped` does not execute working memory, capture/extraction, provisional
promotion, production SQLite/FTS, schedulers, or exact production
authorization; its results are not measurements of the whole deployed
subsystem. Context assembly was checked only for bounded completion; relevance
was scored for retrieval hits, not for the assembled context or a reader's use
of it.

## Frozen synthetic corpus

The suite is `papai-synthetic-v3`, generated by `memory-corpus-v3` with seed
`20260723`. It contains exactly 240 scenarios and one query per scenario. No
production conversation content is used.

| Scope/language cell | Development | Sealed test |   Total |
| ------------------- | ----------: | ----------: | ------: |
| Personal / English  |          15 |          45 |      60 |
| Personal / Russian  |          15 |          45 |      60 |
| Group / English     |          15 |          45 |      60 |
| Group / Russian     |          15 |          45 |      60 |
| **Total**           |      **60** |     **180** | **240** |

Scenario ordinals `001`–`015` form the development split. Ordinals `016`–`060`
form the sealed split in every cell. Stable identifiers encode the cell and
ordinal, for example `scenario-personal-en-001`.

Each cell follows the same 14-slice cycle:

1. `direct-fact`
2. `long-range`
3. `knowledge-update`
4. `temporal-conflict`
5. `lexical-exact`
6. `semantic-paraphrase`
7. `missing-embedding`
8. `graph-multi-hop`
9. `duplicate-out-of-order`
10. `restart-rebuild`
11. `erasure-non-recapture`
12. `abstention`
13. `guest-visibility`
14. `cross-scope`

Every query uses retrieval depth `k = 8` and a 512-token context budget.
Events carry stable event/evidence ids, scope, language, event and ingest
times, validity, embedding state, and optional entity/relation data. Fault
schedules are part of the hashed corpus: missing embeddings, embedding-version
changes, duplicate and out-of-order ingest, restart/rebuild, forget and blocked
recapture, and cross-scope probes.

The graph fixture contains explicit synthetic entities and relations. It tests
projection and traversal over those relations; it does not test extracting a
graph from unconstrained conversation.

The scenario identity is the SHA-256 of a canonical JSON payload containing the
manifest version, generator identity, and every scenario field that affects
execution or scoring. Object keys and scenarios are sorted; semantic array
order, including event and query order, is preserved.

| Identity                      | Exact value                                                        |
| ----------------------------- | ------------------------------------------------------------------ |
| Research protocol version     | `memory-research-protocol-v4`                                      |
| Scenario manifest version     | `memory-scenario-manifest-v3`                                      |
| Scenario manifest SHA-256     | `283044dbd97c119b5b76a639f4f28792e4ff12cc0bdc73e6a81761b083bb12f7` |
| Development selection SHA-256 | `73b33683d473df9dd90fd219d85ca2fa01be070003e26e33f52504518df8b19f` |
| Sealed selection SHA-256      | `f33c032f5fba2a870e9261041204bd4713860c25bdc738c5bfeff3e04d6623a2` |

Changing scenario content, labels, split assignment, budgets, faults, or
generator inputs requires a new corpus and scenario-manifest version. A new
result must not overwrite or be pooled with an earlier corpus identity.

Protocol v4 retained the v3 scenario identity, candidates, weights, gates, and
bootstrap procedure, but re-executed every track after enforcing operational
query redaction, a bounded raw-hit envelope, provenance-aware designated safety
gates, and the proxy claim boundary. Protocol-v3 outputs are historical only
and are not pooled with the v4 decision.

## Scale semantics

`scale` means unique stored records per scope, not scenarios, turns, tokens, or
users. For a component scenario, its canonical rows are retained and
deterministic synthetic distractors are generated until each scope represented
in that scenario has exactly the requested number of unique rows. The seed is
recorded. Each candidate/scenario job runs in an isolated worker.

The tracks have distinct purposes:

| Track              | Scenarios | Records per scope | Role                                                        |
| ------------------ | --------: | ----------------: | ----------------------------------------------------------- |
| Development        |        60 |             1,000 | Rerunnable implementation feedback; never decision evidence |
| Sealed sensitivity |       180 |             1,000 | Sensitivity only; never pooled with the primary score       |
| Sealed primary     |       180 |            10,000 | Sole representation-decision scale                          |
| Frozen storage     |         4 |           100,000 | Performance/storage decision only                           |

The 100,000-record track uses
`scenario-personal-en-022`, `scenario-personal-ru-022`,
`scenario-group-en-022`, and `scenario-group-ru-022`. These are the
graph-multi-hop scenario in each scope/language cell. Every candidate/cell runs
in a fresh worker with exactly 100,000 total records in the primary scope,
canonical rows included. Fixtures are materialized before candidate reset and
the RSS baseline. One retrieval is an unscored warmup; 25 are measured, giving
100 pooled latency samples per candidate when all four cells succeed.

The component scale study is single-process record-count scaling. It does not
establish concurrent durability, poisoning resistance, deferred-action
execution, crash recovery, or reader utilization over a million-token history.
Group namespaces test scope isolation, not speaker-conditioned beliefs. Its
resource measurements describe the research adapters and cannot diagnose
production SQLite. Crossing a storage threshold opens a separate evaluation;
it neither selects nor rejects a storage engine.

## Measurement and decision roles

Per-query component metrics are Precision@8, Recall@8, reciprocal rank, and
nDCG@8. Failures and timeouts remain in the denominator as zero. Safety
requires zero cross-scope and post-erasure hits. Rebuild agreement compares
ordered hit ids before restart with a reconstruction from canonical events.

Candidate differences use paired scenario-level bootstrap intervals: 10,000
resamples, xorshift32 seed `20260723`, two-sided percentile 95% intervals, and
type-7 quantiles. The sealed 10,000-record report supplies the registered
100-point component score and representation gates. The 1,000-record sealed
report is descriptive sensitivity evidence. The 100,000-record report decides
only whether the selected representation crosses the pre-registered SQLite
latency or RSS threshold.

reconstruction of the executed implementation. Protocol v4 was executed only
after license headers and validity hardening were complete; the checked-in
inventoried source bytes therefore hash directly to the recorded identity,
without historical reconstruction.

## Public datasets

The registered public datasets are LongMemEval, LoCoMo, MemBench, and
MemoryAgentBench. For every checked-in run:

- `importStatus` is `not_supplied`;
- `protocolStatus` is `not_run`;
- no local source hash is present; and
- no official reader or judge protocol was executed.

Import adapters exist for locally supplied data, but validating imported bytes
does not reproduce an official benchmark. Published scores from papers,
repositories, or vendors are not copied into this experiment.
