# ReposSection Close-Out Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close four of the five open `ReposSection` UX findings, moving `docs/ux-reviews/_BACKLOG.md` from 18 open to 14 open, without adding a visual baseline.

**Architecture:** Tasks are split by *expected pixel impact*, not by finding order. Task 1 holds the one fix that must not move a pixel and runs the visual audit **without re-shooting**, so a green audit is real evidence rather than a tautology. Tasks 2 and 3 each change a small, named set of baselines and must read the changed PNGs. Task 4 flips the findings docs and regenerates the backlog.

**Tech Stack:** Svelte 5 (runes), TypeScript (strict, `noUncheckedIndexedAccess`, `.js` import extensions), Bun test runner, Playwright + `@crvy/strybk` for Storybook screenshots, oxlint + oxfmt.

**Spec:** [`docs/superpowers/specs/2026-08-04-repossection-close-out-design.md`](../specs/2026-08-04-repossection-close-out-design.md)

## Global Constraints

- Statuses in `docs/ux-reviews/*.md` are exactly `open`, `fixed`, `superseded`. **There is no `partial`.** A non-`open` status requires a `- **Resolved:**` line with a real commit hash or the backlog parser fails loud.
- `client/shared/ui/` primitives are **not** modified by this sub-project. Every fix is local to `client/settings/sections/ReposSection.svelte`, its `<style>` block, its stories file, or its tests.
- **The shared rules in `client/settings/settings.css` are not edited either.** `.status-error` (`:91`) and `.status-success` (`:94`) have 30+ consumers across the settings UI and belong to sub-project SP3. This project moves *where those elements render*; it must not change the rules themselves, or it will re-baseline half the settings UI.
- **No new visual baseline. The audit floor stays 467.** Exactly three baselines may change, all named in the tasks below.
- Do not edit a pre-existing test to make something pass. (No pre-existing test needs editing in this plan — see the note in Task 2 Step 1.)
- Never `--no-verify`; never add a lint-disable or type-ignore comment.
- Branch `ui-ux-review-01`; **no merge, no push**; PR #212 untouched.
- `docs/ux-reviews/_BACKLOG.md` is generated by `bun run ux:backlog`. **Never hand-edit it.**
- Client tests must be run with `bun run test:client`, **never** `bun test tests/client/...` — `bunfig.toml:8` sets `pathIgnorePatterns` including `tests/client/**`, so the latter silently discovers nothing and reports success. Narrow with `bun run test:client -t '<substring>'`.
- `bun shoot` overwrites baselines. **Never run it to make a failing audit green.**
- `bun shoot:gen` regenerates the `@generated-begin auto-screenshots` region in *every* spec file. **Never run it** — it produces branch-wide churn.
- Repo formatter is **oxfmt** (`bun run format`), not prettier.
- The shell is fish. Quote any argument containing `*`, `?`, or `~`.

**Context you need — the current shape:**

The component has one feedback pair at `:124-125`, above the repo rows:

```svelte
  {#if error !== null}<p class="status-error" role="alert">{error}</p>{/if}
  {#if status !== null}<p class="status-success" role="status">{status}</p>{/if}
```

Three unrelated sources write into that pair — `load()`, `handleAdd()` and `handleDelete()` — and `status` is only ever cleared at the start of the next `handleAdd`/`handleDelete` (`:71`, `:98`), so a success message persists indefinitely.

**The target shape.** Two slots, each with its own error/success pair:

- **List slot**, rendered where the current pair is (above the repo rows): fed by `load()` and `handleDelete()`. Its error carries an inline `Retry` button that re-runs `load(contextId)`.
- **Add slot**, rendered at the end of the add-form card: fed by `handleAdd()` only.

The header's `⟳` `IconButton` at `:120` **stays**. It is the idle refresh affordance; removing it would regress the populated state.

**Why `Retry` also shows for a failed delete.** The list slot's error is fed by both `load()` and `handleDelete()`, and the button renders whenever that error is set. This is deliberate rather than sloppy: after a failed delete the list state is uncertain, and re-fetching is exactly the right recovery — it tells the user whether the delete actually landed. Keeping two separate error variables to hide the button in one case would add state for no user benefit.

**Note on pre-existing tests — read this before you start.** Three existing tests query the status elements: `:231` (`.status-error` after a failed delete), `:384` (`.status-error` with `role="alert"` after a failed load), `:414` (`.status-success` with `role="status"` after a successful add). All three use bare `querySelector` with no positional assertion, and all three still pass under the new routing, because each outcome still produces exactly one element with that class. **You must not edit them.** If any of them fails, your routing is wrong — fix the component, not the test.

  const parseEgress = (raw: string): string[] => {
    const seen = new Set<string>()
    for (const part of raw.split(/[\n,]/u)) {
      const host = part.trim().toLowerCase()
      if (host.length > 0) seen.add(host)
    }
    return [...seen]
  }
