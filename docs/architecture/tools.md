# Tools

> Referenced from `CLAUDE.md`. Tool assembly, capability/context gating, user-configurable permissions, and the experimental context-reduction and cross-thread-memory features. See also `src/tools/CLAUDE.md`.

Tool exposure is **capability-gated and context-dependent** (`dm` vs `group`, `normal` vs `proactive`, presence of a storage context, provider identity support). The full tool list is enumerated in `src/tools/` (core CRUD plus capability-gated provider tools for deletion, counting, relations, comments, projects, labels, statuses, work items, attachments, collaboration; and user/context tools for memos, recurring tasks, deferred prompts, instructions, group history, `web_fetch`, identity). Phase-five provider features (sprints, activities, saved queries, agiles) exist at the provider layer without tool wrappers yet.

**`create_alert` conditions** — the tool's required `condition` input is a recursive tree (`alertConditionSchema`, `src/deferred-prompts/condition-schema.ts`) whose leaves come in three shapes, composed under `and`/`or` arrays at any nesting depth. Firing semantics (cooldown, cursors, snapshot baselines, delivery) live in `behaviors.md`'s alert section. The three leaf shapes:

- **Field condition** — `{"field":"task.status","op":"changed_to","value":"Done"}` — evaluates across every task in the task instance. Fields and per-field operators (`FIELD_OPERATORS`): `task.status`/`task.priority`/`task.assignee` take `eq`/`neq`/`changed_to`, `task.dueDate` takes `eq`/`lt`/`gt` plus the valueless `overdue`, `task.project` takes `eq`/`neq`, `task.labels` takes `contains`/`not_contains`; values are strings or numbers. Validation rejects an operator outside the field's set (naming the field, the operator, and the valid operators) and any non-`overdue` leaf submitted without a value.
- **Per-task watch** — `{"field":"task.id","op":"eq","value":"42"}` — `task.id` supports only `eq` and selects one specific task ("tell me when this task changes"). Mixed into a field tree it merely narrows which tasks can satisfy the condition, keeping the matched-set edge semantics field alerts use.
- **Activity watch** — `{"kind":"activity","taskId":"TASK-1","categories":["comment"]}` — fires on new task-history entries for one task; optional `categories` (a non-empty array) restricts firing to those entry categories and is passed through to the history lookup.

**Condition tree rules** — a tree must be pure-field (field leaves, optionally including `task.id`) or pure-activity (activity leaves only); a tree mixing activity leaves with field leaves under `and`/`or` is refused with guidance to split the alert into two (`mixedActivityTreeError` in `src/deferred-prompts/activity-gating.ts`, applied at creation and at condition update). A pure-field tree consisting only of `task.id eq` leaves (any `and`/`or` shape) is a **pure watch**: it fires when a watched task's change-tracked fields (status, priority, assignee, due date, project, labels) differ from the snapshot stored for its conversation context — not on match-set edges.

**Targeted vs whole-list polling** — the fetch mode is decided per task instance over the full active routable alert set (so an alert entering cooldown cannot flip it mid-life): when every such alert is a pure watch or a pure activity watch, the poller fetches only the deduplicated union of watched task ids via `getTask` (bounded concurrency) plus the watched histories via `getTaskHistory`, issuing no project-listing, task-listing, or search request; as soon as one field-filter alert shares the instance, the whole-list path returns (`listProjects`+`listTasks`, `searchTasks` fallback, enriched via `getTask` when a condition references `task.assignee`/`task.labels`) with pure watches and history lookups evaluating alongside it.

**Activity conditions are capability- and instance-gated at creation** — exposure is capability-gated at assembly: `buildTools` computes `provider.capabilities.has('activities.read') && provider.getTaskHistory !== undefined` and threads the boolean through `addProviderIndependentTools` → `addDeferredPromptTools` → `makeCreateAlertTool` into `executeCreate`'s delivery context — the tool itself never builds a provider, and the flag defaults to false (fail closed) on providerless assembly and legacy call sites. At create time `createAlert` in `src/deferred-prompts/tool-handlers.ts` additionally requires a task instance configured for the delivery context and refuses any tree mixing activity leaves with field leaves (`mixedActivityTreeError`/`activitySupportError` in `src/deferred-prompts/activity-gating.ts`; the capability gate is create-only — an activity condition attached via update to an incapable tracker degrades to the poll-time skip-and-warn path); refusals return the standard `{ error }` guidance shape naming what is missing, so the model can fall back to field conditions instead of retrying blindly.

**User-configurable access** — beyond capability + context gating, each personal or managed-group context assigns every tool a three-state permission (`allow`/`ask`/`deny`) stored as JSON under the reserved `tool_prefs` key (`{ riskDefaults, domainDefaults, toolOverrides }`), applied as the final step in `makeTools()`. Resolution is most-specific-wins: `toolOverrides[name]` → `toolOverrides[RENAMED_TOOL_ALIASES[name]]` (legacy deferred-prompt name for renamed reminder/alert tools; see `src/tools/tool-aliases.ts`) → `domainDefaults[domain]` → `riskDefaults[risk]` → implicit `allow` (`resolveToolPermission` in `src/tools/tool-preferences.ts`). The three states:

- `allow` (default) — exposed normally.
- `deny` — removed from the set.
- `ask` — exposed wrapped: input schema gains a `_permission_reason` field and execution is gated on explicit per-call user permission.

**Permission presets** — the settings-UI Tools section offers one-click presets (`read-only`, `non-destructive`, `allow-all`) that set the `riskDefaults` tier by a tool's static risk class (`read`/`write`/`destructive`/`open-world` from `src/tools/tool-metadata.ts`). Presets are **sticky**: a newly-added tool with no explicit override inherits the active preset via its risk, so `open-world` tools (`web_fetch`, all MCP/plugin tools) land in `ask` under `read-only`. Applying a preset is reset-to-baseline — it clears `domainDefaults`/`toolOverrides` and writes `riskDefaults` (`applyPreset`); the UI confirms first and shows the active preset (or "Custom" when overrides diverge, via `detectActivePreset`). Wired through `POST /settings/api/tools/toggle` (`kind: 'preset'`) which also returns `activePreset`.

**Admin default tool permissions** — a bot admin can set a per-platform-instance default `tool_prefs` (settings-UI admin "Default tool permissions" section, `GET/POST /settings/api/admin/tool-defaults`, stored under the reserved `__admin_tool_defaults__:<platformInstanceId>` context). The default is **seeded once** into a context's own `tool_prefs` the first time its toolset is built with no stored prefs (`maybeSeedAdminToolDefaults` in `applyToolPreferences`), applying globally to DM and group contexts of that instance. It is a seed, not a live tier — later admin edits never override an already-seeded or user-customized context; no admin default (or an allow-all default) preserves today's implicit allow-all baseline. The admin catalog lists builtins plus native tool names of all active plugins; MCP-sourced tool names are not enumerable context-agnostically (they need per-context config/credentials), so admin defaults govern them via the `mcp`/`plugin` domain rows and the `open-world` risk tier.

**Admin-gated diagnostics** — `run_diagnostics` (`src/tools/diagnostics.ts`) is the one tool gated on actor identity: `maybeAddDiagnosticsTools` runs in both `buildToolDescriptors` and `buildProviderlessToolDescriptors` and adds it only when `isBotAdmin === true && contextType === 'dm' && mode === 'normal'`. The gate **fails closed** — the flag is threaded from the authorizing message (`AuthorizationResult.isBotAdmin` → `enqueueTurn` → queue coalescing, last-message-wins like `actorRole` → `processMessage` → descriptor options), and paths that resolve no per-message identity (proactive/deferred runs, `/config`-flow tool resolution) never pass a true flag, so no blocklist is needed. Identity absent anywhere defaults to non-admin. The turn's `platformInstanceId` rides the same thread and parameterizes the snapshot. Because a context can flip admin status between turns, the descriptor cache key (`getOrCreateDescriptors`, `src/llm-orchestrator-descriptor-cache.ts`) appends `:admin`/`:user` as its **last** segment — an admin turn never reuses non-admin descriptors or vice versa, and the prefix-based invalidation (`clearCachedToolsByPrefix`, matching up to and past `${contextId}`) still clears both variants unchanged. The tool itself returns only whitelisted count/boolean/enum/duration fields (instance active state, task instance id/type or `not_configured`, LLM config `central|byok|unconfigured`, MCP pool health counts, queue count, descriptor-cache presence, uptime); each probe is individually try/caught and degrades to a `probe_error` marker, and no token, key, or credential-bearing value can reach the result or the logs. It is registered `read('diagnostics')` in `tool-metadata.ts` (analytics-mapped to `diagnostics`), so `tool_prefs` and the sticky presets treat it as an ordinary read tool — `deny` removes it even for a qualifying admin, `ask` wraps it per-call.

**Self-diagnosis reader family** — beside `run_diagnostics`, the same `maybeAddDiagnosticsTools` call assembles four buffer readers: `read_recent_logs`, `read_llm_traces`, `read_recent_turns`, `read_recent_tool_failures` (one file each under `src/tools/diagnostics-*.ts`, per the one-tool-per-file rule). They inherit the identical fail-closed admin/DM/normal gate, descriptor-cache keying, and `/context` display-only behavior, and bind `options.chatUserId` as the **visibility principal** at assembly time — closure binding is safe because these tools only ever assemble in the admin's own DM, whose `chatUserId` is that same admin. The readers query the always-on in-process diagnosis buffers (the log ring buffer plus the event-derived trace/turn/tool-failure buffers from `src/debug/`) strictly read-only: buffers are never mutated, invocation logging is metadata-only (counts/limits), and each buffer access is individually try/caught, degrading to the shared `probe_error` marker. Egress reuses the exact shaping/attribution code paths as the dashboard REST/SSE surfaces, so the two cannot drift:

- **Logs** (`read_recent_logs`) mirrors `handleLogs`: entries attributable to the calling admin — an explicit `chatUserId` match, or a `turnId` resolving to a turn the admin can see (via `ownTurnIdsForAdmin`, resolved once per call) — pass verbatim; foreign and unattributed entries are shaped by `shapeLogEntry` to structural plus numeric/boolean fields only. Filters (`level` minimum, `scope` allowlist pattern, `turn_id`, `msg` substring) are built into the shared `LogFilter` model and applied **after** shaping — a security property: a text filter can never act as an oracle for content stripped from foreign entries. Limit defaults to 50 with a hard cap of 200; `distinct_scopes: true` short-circuits to scope/count pairs like `GET /logs/scopes`.
- **LLM traces** (`read_llm_traces`) shapes each trace with `shapeLlmTrace(trace, chatUserId)`: own traces verbatim; foreign/unattributed traces lose `generatedText`, `stepsDetail`, identity fields, and per-tool-call `args`/`result`, keeping model ids, durations, token/step counters, tool names, and `error`. `errors_only` and `model` filters; limit default 25, cap 100, sliced from the tail like the dashboard init frame.
- **Turns** (`read_recent_turns`) filters listings with `isVisibleToAdmin(scope, clientVisibility(chatUserId))` (same as the collector's init frame) and egresses only anonymous operational data — timings, status, tool names/durations, failure reasons, error strings, never message content. A `turn_id` fetch consults `findTurnById` (so in-flight running turns are observable) and returns `{ status: 'not_found' }` indistinguishably for foreign, invisible, and unknown ids — the same no-existence-leak contract as `get_message`. Limit default 25, capped at the turn-buffer capacity (512).
- **Tool failures** (`read_recent_tool_failures`) applies the same visibility filter and egresses a fixed whitelist — timestamp, scope, `toolName`, `durationMs`, `ok`, `failureReason`, `turnId` — never the buffered `data` bag (tool arguments, provider bodies, identities). Limit default 25, capped at the failure-buffer capacity (1024).

**Volatility is surfaced honestly**: every reader result carries the queried buffer's derived stats (entry count, capacity from the exported `RECENT_*`/`LLM_TRACE` capacity constants, oldest/newest bounds), and log results additionally carry `history_starts_at_process_start: true`. The buffers are in-process and start empty at boot, so after a restart the readers return empty result sets with zero-count stats and complete successfully — never errors, never invented pre-restart history. All four names are registered `read('diagnostics')` in `tool-metadata.ts` (analytics-mapped, slugs in `src/analytics/generated/tool-slugs.ts`): implicit `allow` by default, `deny` removes them from the resolved `ToolSet` even for a qualifying admin, `ask` wraps each call in the `_permission_reason` confirmation flow (approve → execute, decline → structured `permission_denied`), and the sticky presets never gate read-risk tools. Oversized results beyond the caps flow into the always-on compaction wrap and `expand_result` paging like any other tool.

The system prompt (`src/system-prompt.ts`) is composed from permission-aware fragments: never instructs the agent to use a denied tool, lists ask-gated tools with their permission requirement, and appends an "Unavailable tools" line for denied domains. Managed in the Tools section of the settings UI. MCP-sourced tools (`mcp_<server>__<tool>` for user endpoints, `plugin_<server>__<tool>` for plugin-sourced) are subject to the same per-context permissions, and the settings Tools section lists them individually: the route enumerates the exact runtime surface (async `buildToolDescriptors`/`buildProviderlessToolDescriptors`, so provider-less contexts see their providerless surface, a downed MCP server temporarily drops its tools from the list, and a slow MCP server can delay the settings request — connections are pooled, so only cold requests pay connect latency), groups plugin/MCP entries per plugin id / server id via a derived `group` field, and supports per-group bulk toggles (`kind: 'group'`, written as per-tool overrides). Tools requiring live-turn-only inputs are absent from the settings list (display-only discrepancy): `resolve_chat_participant` (needs a ChatRouter-bound resolver) and thread-gated builtins like `lookup_group_history` (need a thread-scoped storage context id; settings operates on the config-context id). They still obey domain/risk-tier prefs at runtime — only per-tool overrides can't be set from the UI.

**Result compaction (always on)** — `prepareLlmInvocation` wraps the toolset per turn (`src/tools/compaction/wrap-compaction.ts`, applied after `applyToolPreferences`): successful tool results over 8 KB are stored in a per-context TTL/LRU store and replaced by a `_compacted` envelope (query-aware SMALL_MODEL summary, or preview-only truncation on summarizer failure); the `expand_result` tool (registered only in `normal` mode — proactive runs never compact) pages the stored raw result. Failures, already-compacted envelopes, and non-serializable results are never compacted.

**Progressive disclosure (always on)** — `buildFullToolSet` (`src/llm-orchestrator-tools.ts`) applies `maybeApplyDisclosure` (`src/tools/disclosure/wire.ts`) after compaction: a turn-scoped `DisclosureSession` is created, `search_tools`/`load_tool` meta-tools are injected, and `invokeModel` attaches a `prepareStep` so each step's `activeTools` is only core (`get_current_time`) ∪ meta (`search_tools`, `load_tool`, `expand_result` when registered) ∪ explicitly loaded names — full tool schemas stay registered for execution/permissions but are not serialized until loaded. `search_tools` returns ranked schema-less briefs from a BYOK-aware embedding-backed retriever (`getToolRetriever`, resolving per-context credentials, recording usage, with per-endpoint+model brief caches; falls back to lexical ranking internally when embeddings are unavailable or no LLM config resolves); a latched stall fallback opens all tools after 2 steps with no real loads, or when the last 2 completed steps were nothing but `search_tools`/`load_tool` churn (`disclosure:fallback` event). On an empty result, `search_tools` returns a conditional `hint` listing the domains present in the discoverable set (or a bare retry-with-different-wording note when the context has no discoverable tools); `load_tool` returns a conditional `warning` naming any unrecognized names — both fields are absent on the happy path. The system prompt gains a TOOL DISCOVERY preamble (advertises `expand_result` only when registered). `disclosure:search`/`disclosure:load` events carry counts/lengths only. The proactive/deferred path applies disclosure too, via its own `buildFullToolSet` in `src/deferred-prompts/proactive-llm-full.ts`: every deferred prompt now runs a single unified full-generation path on the main model, and `runFullGeneration` (`src/deferred-prompts/proactive-llm.ts`) attaches a standalone `createDisclosurePrepareStep` to its direct `generateText` call (the normal chat path composes that prepareStep with steering; the proactive path has no steering, so it's attached alone). This does not change compaction: `expand_result` is still not registered on the proactive path, so proactive runs still never compact (see above).

**Cross-thread memory bridge (always on)** — the bot does not rediscover recurring facts in every new thread of a group. The mechanism lives in `src/long-term-memory/` and extends the long-term store: `memory_records` has a `provisional` status + `thread_context_id` (migration `056`). (1) **Capture** — an idle-debounce pipeline (`capture.ts` + `capture-debounce.ts`, armed every group-thread turn from `llm-history.ts`; `memory-capture-sweep` scheduler backstop over a `memory_extraction_state` watermark) runs the SMALL_MODEL extractor and writes provisional, thread-tagged, embedding-populated records. (2) **Retrieval** — the `search_memory` tool runs the server-side cascade (`recall-cascade.ts`): current-thread provisional → active group memory → sibling-thread provisional, with optional `kind`/`include_stale` filters. (3) **Promotion** — when a provisional fact clusters across ≥`MEMORY_PROMOTION_MIN_THREADS` (3) distinct threads and a SMALL_MODEL confirms it is durable/general, it is promoted to `active` group memory (`promotion.ts`; `memory-promotion-sweep` backstop). `memory:promote` events carry counts only. Capture can be disabled per context via the settings Memory section "Disable capture" toggle (the memory-profile `enabled` flag). The provisional/promotion store lives in `src/long-term-memory/provisional-store.ts` (shared `recordScopeCondition` in `record-conditions.ts`), re-exported from `store.ts`. The settings-UI Memory section surfaces provisional records in a separate **Pending (provisional)** subsection.
