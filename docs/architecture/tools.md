# Tools

> Referenced from `CLAUDE.md`. Tool assembly, capability/context gating, user-configurable permissions, and the experimental context-reduction and cross-thread-memory features. See also `src/tools/CLAUDE.md`.

Tool exposure is **capability-gated and context-dependent** (`dm` vs `group`, `normal` vs `proactive`, presence of a storage context, provider identity support). The full tool list is enumerated in `src/tools/` (core CRUD plus capability-gated provider tools for deletion, counting, relations, comments, projects, labels, statuses, work items, attachments, collaboration; and user/context tools for memos, recurring tasks, deferred prompts, instructions, group history, `web_fetch`, identity). Phase-five provider features (sprints, activities, saved queries, agiles) exist at the provider layer without tool wrappers yet.

**User-configurable access** — beyond capability + context gating, each personal or managed-group context assigns every tool a three-state permission (`allow`/`ask`/`deny`) stored as JSON under the reserved `tool_prefs` key (`{ riskDefaults, domainDefaults, toolOverrides }`), applied as the final step in `makeTools()`. Resolution is most-specific-wins: `toolOverrides[name]` → `domainDefaults[domain]` → `riskDefaults[risk]` → implicit `allow` (`resolveToolPermission` in `src/tools/tool-preferences.ts`). The three states:

- `allow` (default) — exposed normally.
- `deny` — removed from the set.
- `ask` — exposed wrapped: input schema gains a `_permission_reason` field and execution is gated on explicit per-call user permission.

**Permission presets** — the settings-UI Tools section offers one-click presets (`read-only`, `non-destructive`, `allow-all`) that set the `riskDefaults` tier by a tool's static risk class (`read`/`write`/`destructive`/`open-world` from `src/tools/tool-metadata.ts`). Presets are **sticky**: a newly-added tool with no explicit override inherits the active preset via its risk, so `open-world` tools (`web_fetch`, all MCP/plugin tools) land in `ask` under `read-only`. Applying a preset is reset-to-baseline — it clears `domainDefaults`/`toolOverrides` and writes `riskDefaults` (`applyPreset`); the UI confirms first and shows the active preset (or "Custom" when overrides diverge, via `detectActivePreset`). Wired through `POST /settings/api/tools/toggle` (`kind: 'preset'`) which also returns `activePreset`.

**Admin default tool permissions** — a bot admin can set a per-platform-instance default `tool_prefs` (settings-UI admin "Default tool permissions" section, `GET/POST /settings/api/admin/tool-defaults`, stored under the reserved `__admin_tool_defaults__:<platformInstanceId>` context). The default is **seeded once** into a context's own `tool_prefs` the first time its toolset is built with no stored prefs (`maybeSeedAdminToolDefaults` in `applyToolPreferences`), applying globally to DM and group contexts of that instance. It is a seed, not a live tier — later admin edits never override an already-seeded or user-customized context; no admin default (or an allow-all default) preserves today's implicit allow-all baseline. The admin catalog lists builtins plus native tool names of all active plugins; MCP-sourced tool names are not enumerable context-agnostically (they need per-context config/credentials), so admin defaults govern them via the `mcp`/`plugin` domain rows and the `open-world` risk tier.

The system prompt (`src/system-prompt.ts`) is composed from permission-aware fragments: never instructs the agent to use a denied tool, lists ask-gated tools with their permission requirement, and appends an "Unavailable tools" line for denied domains. Managed in the Tools section of the settings UI. MCP-sourced tools (`mcp_<server>__<tool>` for user endpoints, `plugin_<server>__<tool>` for plugin-sourced) are subject to the same per-context permissions, and the settings Tools section lists them individually: the route enumerates the exact runtime surface (async `buildToolDescriptors`/`buildProviderlessToolDescriptors`, so provider-less contexts see their providerless surface, a downed MCP server temporarily drops its tools from the list, and a slow MCP server can delay the settings request — connections are pooled, so only cold requests pay connect latency), groups plugin/MCP entries per plugin id / server id via a derived `group` field, and supports per-group bulk toggles (`kind: 'group'`, written as per-tool overrides). Tools requiring live-turn-only inputs are absent from the settings list (display-only discrepancy): `resolve_chat_participant` (needs a ChatRouter-bound resolver) and thread-gated builtins like `lookup_group_history` (need a thread-scoped storage context id; settings operates on the config-context id). They still obey domain/risk-tier prefs at runtime — only per-tool overrides can't be set from the UI.

**Result compaction (always on)** — `prepareLlmInvocation` wraps the toolset per turn (`src/tools/compaction/wrap-compaction.ts`, applied after `applyToolPreferences`): successful tool results over 8 KB are stored in a per-context TTL/LRU store and replaced by a `_compacted` envelope (query-aware SMALL_MODEL summary, or preview-only truncation on summarizer failure); the `expand_result` tool (registered only in `normal` mode — proactive runs never compact) pages the stored raw result. Failures, already-compacted envelopes, and non-serializable results are never compacted.

**Progressive disclosure (always on)** — `buildFullToolSet` (`src/llm-orchestrator-tools.ts`) applies `maybeApplyDisclosure` (`src/tools/disclosure/wire.ts`) after compaction: a turn-scoped `DisclosureSession` is created, `search_tools`/`load_tool` meta-tools are injected, and `invokeModel` attaches a `prepareStep` so each step's `activeTools` is only core (`get_current_time`) ∪ meta (`search_tools`, `load_tool`, `expand_result` when registered) ∪ explicitly loaded names — full tool schemas stay registered for execution/permissions but are not serialized until loaded. `search_tools` returns ranked schema-less briefs from a BYOK-aware embedding-backed retriever (`getToolRetriever`, resolving per-context credentials, recording usage, with per-endpoint+model brief caches; falls back to lexical ranking internally when embeddings are unavailable or no LLM config resolves); a latched stall fallback opens all tools after 2 steps with no real loads, or when the last 2 completed steps were nothing but `search_tools`/`load_tool` churn (`disclosure:fallback` event). The system prompt gains a TOOL DISCOVERY preamble (advertises `expand_result` only when registered). `disclosure:search`/`disclosure:load` events carry counts/lengths only. The proactive/deferred path applies disclosure too, via its own `buildFullToolSet` in `src/deferred-prompts/proactive-llm-full.ts`: every deferred prompt now runs a single unified full-generation path on the main model, and `runFullGeneration` (`src/deferred-prompts/proactive-llm.ts`) attaches a standalone `createDisclosurePrepareStep` to its direct `generateText` call (the normal chat path composes that prepareStep with steering; the proactive path has no steering, so it's attached alone). This does not change compaction: `expand_result` is still not registered on the proactive path, so proactive runs still never compact (see above).

**Cross-thread memory bridge (always on)** — the bot does not rediscover recurring facts in every new thread of a group. The mechanism lives in `src/long-term-memory/` and extends the long-term store: `memory_records` has a `provisional` status + `thread_context_id` (migration `056`). (1) **Capture** — an idle-debounce pipeline (`capture.ts` + `capture-debounce.ts`, armed every group-thread turn from `llm-history.ts`; `memory-capture-sweep` scheduler backstop over a `memory_extraction_state` watermark) runs the SMALL_MODEL extractor and writes provisional, thread-tagged records, each stamped with its embedding's model/dimension/version identity on write (`embedding-writer.ts`) so the dense channel can later tell compatible vectors apart per config context (BYOK). (2) **Retrieval** — the `search_memory` tool runs the server-side cascade (`recall-cascade.ts`): current-thread provisional → active group memory → sibling-thread provisional, with optional `kind`/`include_stale` filters. Each layer queries through `searchHybrid` (`hybrid-search.ts`), which fuses an independent Unicode-tokenized FTS5/bm25 lexical channel and a version-gated dense cosine channel by weighted reciprocal rank fusion rather than choosing one or the other (see `docs/architecture/behaviors.md`); expired-but-still-`active` records are excluded at query time. (3) **Promotion** — when a provisional fact clusters across ≥`MEMORY_PROMOTION_MIN_THREADS` (3) distinct threads and a SMALL_MODEL confirms it is durable/general, it is promoted to `active` group memory (`promotion.ts`; `memory-promotion-sweep` backstop). `memory:promote` events carry counts only. Capture can be disabled per context via the settings Memory section "Disable capture" toggle (the memory-profile `enabled` flag). The provisional/promotion store lives in `src/long-term-memory/provisional-store.ts` (shared `recordScopeCondition` in `record-conditions.ts`), re-exported from `store.ts`. The settings-UI Memory section surfaces provisional records in a separate **Pending (provisional)** subsection.

**Durable memory erasure (always on)** — forgetting a memory is a permanent purge, not a soft archive. `forget_memory` (tool) and the settings-UI per-record delete (`src/debug/settings/memory-routes.ts`) both call `purgeMemoryRecord` (`src/long-term-memory/store.ts`), which — in one transaction — hard-deletes the canonical row (the `embedding` column goes with it; an `AFTER DELETE` trigger removes the matching `memory_records_fts` entry) and writes a content-hash **tombstone** (`memoryTombstones`: scope + SHA-256 of normalized content, never the content itself; `src/long-term-memory/tombstone.ts`). Background capture (`capture.ts`) and the recapture path in `runner.ts` consult `isContentTombstoned` before writing a new provisional record for matching content, so a forgotten fact is not silently re-learned from later conversation; an explicit `remember_memory` call for the same content clears the matching tombstone (`deleteMatchingTombstone`) so the user can deliberately reinstate it. `archiveMemoryRecord` (soft status flip, no deletion) still exists but is now used only by the promotion pipeline (`promotion.ts`) to retire a superseded provisional record, not by forget/delete. The settings-UI "Clear memory" scope action (`clearMemoryScope`, `src/long-term-memory/scope-clear.ts`) goes further than a record-level purge: in one transaction it deletes every long-term record and the memory profile for the scope, working memory (conversation history, summaries, facts, matched by scope id and any `scopeId:thread:*` sub-key), the `memory_extraction_state` watermark, and **all tombstones for that scope** (so a full scope clear also resets recapture suppression — content forgotten before the clear can be recaptured afterward, since nothing durable remains to suppress it against). In-memory caches for cleared working-memory keys are evicted after the transaction commits (`evictUser`). `PRAGMA secure_delete=ON` is set on the database connection so deleted bytes are overwritten rather than left as SQLite freelist/WAL residue. None of this touches external backups; only the live database is affected.
