# ACP Coding Sessions

> Referenced from `CLAUDE.md`. The `plugins/acp/` plugin and its integration with the external **magi** control service, including credentials, forge connections, and operator/group guardrails.

ACP coding sessions (`plugins/acp/`): a thin first-party plugin exposing LLM tools (start/list/status/finish/cancel a coding session, answer a permission, review a PR, list projects/agents), an `/acp` command, and a prompt fragment. It is a stateless HTTP client of the external **magi** control service (admin-scoped `magi_base_url` + sensitive `magi_token` plugin config; outbound via `providerRuntime.httpFetch`, with the admin base URL allowlisted through `providerAllowedHostsFromConfig`). It injects the chat's `storageContextId` as the magi session `contextId` (so magi's milestone notifier posts back to `/api/notify`) and uses `plugin_kv` to scope `list_sessions` to the originating chat. Because plugin source cannot static-import bare modules (discovery rejects them), the tools use raw JSON-Schema `inputSchema` with manual guards instead of Zod. The `coding_session_credentials` vault has two namespaces: **`agent-provider`** (the sandboxed agent's LLM key and choice of coding agent, supplied per-session via the `coding.secrets`-gated `codingSecrets` capability; `start_session` and `review_pr` refuse with `error: 'not_configured'` when empty) and **`forge`** (the user's code-host token — GitHub/GitLab PAT — stored in the settings-UI "Code host" section; `finish_session` and `review_pr` refuse with `error: 'not_configured'` when unconfigured, preventing push/PR without the user's identity; `start_session` includes the token when present and does not require it for SaaS repos (magi derives the forge), but **pre-flights self-hosted repos** — when the repo host is not SaaS-derivable (`canDeriveForge`, `plugins/acp/tools.ts`) and no forge is configured, it refuses with `error: 'not_configured'` rather than letting magi 400). No host/global forge token is used or expected on the magi side.

## Agent/provider picker (Phase 4a/4c)

The `agent-provider` namespace has four fields: `agent` (enum: `claude`/`codex`/`opencode`; default `claude`), `provider` (enum: `anthropic`/`openai`/`openai-compatible`), `provider_api_key`, and `provider_base_url`. A `compatible(agent, provider)` rule constrains valid pairs: claude→anthropic only; codex→openai or openai-compatible; opencode→any. The `openai-compatible` provider targets any OpenAI-compatible endpoint (e.g. a self-hosted LLM proxy) and **requires a `provider_base_url`** — the route 422s without one. The settings-UI **AI provider** section renders `agent` and `provider` as `<select>` dropdowns (controlled by `control: 'select'` + `options` metadata from the route); the provider dropdown is client-side filtered to only the options compatible with the currently-selected agent; when `openai-compatible` is selected the base-URL field shows as required. The section saves as a **whole record**: selecting a value only updates the local draft (changing the agent resets the provider draft to the first compatible option), and one Save button PATCHes all fields together — untouched masked secrets are omitted so the store preserves them — so the route's cross-field validation (compatibility + base-URL presence for `openai-compatible`, 422 on violations) always sees a complete, consistent record. (Per-field auto-save previously 422'd when a field was saved before its cross-field dependency — e.g. `openai-compatible` before its base URL — silently dropping the field.) A **Clear** button (rendered only when the section reports `configured`) removes the whole `agent-provider` vault for the context via `PATCH /settings/api/coding-credentials { clear: true }` behind a `danger` confirm dialog — the same scope-checked route/`clearCodingCredentials` primitive the admin `shared-key-clear` uses, but keyed to the per-user/group identity context rather than the operator vault. `resolveAgentSecrets` maps `provider→{ANTHROPIC_API_KEY,OPENAI_API_KEY}`; `resolveAgent` returns the stored agent (default `null`); `resolveProviderHost` derives the model hostname from provider + base URL (e.g. `openai-compatible` + `https://llm.corp.com/v1` → `llm.corp.com`). The acp plugin reads all three via `codingSecrets` and carries `agent` and `providerHost` in the `projectSpec` sent to magi. All three coding agents — **claude**, **codex**, and **opencode** — are now functional in the self-serve model.

## Derived sandbox egress (Phase 4c)

magi derives the per-session sandbox egress from the `projectSpec`: operator base ∪ `providerHost` (from `resolveProviderHost`) ∪ agent-infra (codex→`chatgpt.com`, opencode→`models.dev`). This **narrows** the prior broad default and makes custom `openai-compatible` endpoints reachable within the operator's geofront ceiling. The repo host is **not** included in the sandbox egress (the agent cannot auth to the forge anyway). A session using an `openai-compatible` endpoint whose host is not in the geofront ceiling will fail to reach the model; the operator must widen the ceiling to admit that host.

## Typed forge connections (Phase 4b)

The `forge` namespace has three fields: `kind` (enum: `github`/`github-enterprise`/`gitlab`/`gitlab-self-hosted`; rendered as a `<select>` in the settings-UI **Code host** section), `instance_url` (text; shown only when `needsInstanceUrl(kind)` — i.e. `github-enterprise` or `gitlab-self-hosted`; hidden for SaaS kinds), and `forge_token` (sensitive; rendered masked). `deriveApiBaseUrl(kind, instance_url)` maps the UI kind to an API base URL (`https://api.github.com`, `https://gitlab.com/api/v4`, or `<instance_url>/api/v3|v4`). `forgeMagiKind` maps UI kinds to magi's two-value enum (`github`|`gitlab`). `resolveForge` reads the vault and returns `{ kind, apiBaseUrl }` — `null` when unconfigured, **and `null` for a partial vault** (`instance_url` present but `kind` missing) rather than silently mis-deriving GitHub SaaS and ignoring the instance URL; a legacy token-only vault with neither `kind` nor `instance_url` still defaults to `github`. The acp plugin carries the result as `projectSpec.forge`. The route validates: `kind` must be a known `FORGE_KINDS` member (422 on unknown); when `needsInstanceUrl(kind)`, `instance_url` must be present and start with `https://` (422 otherwise). The **Code host** section saves as a **whole record** (kind + instance_url + token in one PATCH), matching that cross-field validation — saving fields individually previously 422'd when `kind` was set before `instance_url`, leaving `kind` empty and triggering the `resolveForge` partial-vault guard. A **Clear** button (shown only when `configured`) removes the `forge` vault via the same `{ clear: true }` PATCH behind a `danger` confirm dialog. **Self-hosted instance hosts must be operator-allowlisted** in magi's standalone `MAGI_ALLOWED_REPO_HOSTS` (SSRF gate); the two fixed SaaS API hosts (`api.github.com`, `gitlab.com`) are always admitted for the forge-API check, but the **repo clone host is never exempt** — even SaaS repo hosts (`github.com`/`gitlab.com`) must appear in the allowlist. The allowlist is decoupled from magi's project defaults and **fail-closed** (empty/unset → serve refuses to start).

## Model selection + codex base-URL fix (Phase 4d)

The `agent-provider` namespace has an optional `model` field. It is stored in the **identity context only** — `resolveModel` always calls `identityContext`, so 5a's `forceSharedKey` does **not** override it (unlike `resolveAgentSecrets`/`resolveProviderHost`, which use the shared-key context when forced). The model is carried as `projectSpec.model` — it is **not** part of the `secrets` bundle. magi applies it after `session/new` via ACP `session/set_config_option` (uniform across claude/codex/opencode). `selectModelConfig` matches the requested value against the agent's `configOptions[category=model]` list by value, then by display name. If the model is not offered by the agent, magi logs a warning and uses the agent's default; it never hard-fails on an unknown model.

The settings-UI **AI provider** section renders `model` as a `combobox` control: a free-text `<input list>` backed by a `<datalist>` populated by the new `GET /settings/api/coding-credentials/models` route (`src/debug/settings/coding-credentials-models-route.ts`). That route is a server-side proxy to the provider's `/v1/models` endpoint; it reads the stored key and base URL from the vault (key never returned to the client), calls `assertPublicUrl` + `redirect:'error'` for SSRF defense, and handles both OpenAI-shaped (`{ data: [{ id }] }`) and Anthropic-shaped responses. For opencode, model ids are prefixed with the provider name (`openai/gpt-5`, `anthropic/claude-sonnet-4-6`) because opencode uses `provider/model` routing; custom `openai-compatible` endpoints receive no prefix. The route degrades to `{ ok: false, models: [] }` on any error — the combobox falls back to free-text. Changing the agent resets the model draft to blank (the prior agent's model ids are unlikely to be valid for the new one). Model validation on save: max 200 characters, no control characters; the route 422s on violations.

**Codex base-URL fix.** Codex reads its provider base URL from `~/.codex/config.toml` (it ignores `OPENAI_BASE_URL`). magi now generates this file from the configured base URL via `generateCodexConfigToml` (`src/runtime/geofront/provisioning/codex-config.ts`), which emits a `[model_providers.custom]` section with `env_key="OPENAI_API_KEY"` and `wire_api="chat"`. The file is staged through the provisioning manifest's `file` kind (not an env secret target). The previous `OPENAI_BASE_URL` env secretTarget in the codex preset was a no-op and has been removed. When no base URL is configured the file is not staged and codex uses its built-in default.

**Router agent reconciliation.** magi's `/sessions` router now derives the launch agent from the validated `projectSpec.agent` rather than the unvalidated top-level `body.agent`. The two values were always supposed to be identical, but the unvalidated read bypassed `validateRepoSpec`'s agent allowlist check, making 5a's `allowedAgents` guardrail ineffective at the launch layer. The validated spec is now the single source of truth.

## Operator guardrails (Phase 5a)

A per-platform-instance policy (`__admin_coding_guardrails__:<platformInstanceId>` context key `coding_guardrails`, read/written by `src/coding-credentials/guardrails.ts` via `getCachedConfig`/`setCachedConfig`) bounds coding-session self-serve with three fields, all defaulting to allow-all / reference-identical when unset:

- **`allowedAgents`** (`string[]`, default `['claude','codex','opencode']`) — which coding agents users may pick. The agent-picker in the settings-UI **AI provider** section filters its `<select>` options to this list (A1). magi **re-enforces** this at `/sessions` and `/reviews` via `validateRepoSpec` → rejects with `agent not permitted: <agent>` (B1).
- **`whoMayUse`** (`'members' | string[]`, default `'members'`) — who may **start** a coding session. Enforced host-side in `buildFullToolSet` (`src/llm-orchestrator-tools.ts`) via `applyWhoMayUseFilter`: when `'members'`, the filter is a reference-identical pass-through; when an allowlist, actors whose `chatUserId` is not listed have the five ACP session-action tools (`plugin_acp__start_session`, `__review_pr`, `__finish_session`, `__cancel_session`, `__answer_permission`) silently removed from their tool set — read-only tools like `plugin_acp__list_sessions` / `__session_status` are kept. Guests are already excluded by `applyGuestReadOnlyFilter` (runs first). `platformInstanceId` is derived via `parseScopedContextId`; unscoped context IDs are not gated.
- **`forceSharedKey`** (`boolean`, default `false`) — when true, `resolveAgentSecrets` and `resolveProviderHost` read the operator-stored `agent-provider` vault at `adminCodingGuardrailsContextId(pi)` instead of the user's own config-context (A2). Forge credentials (`resolveForgeToken`, `resolveForge`) always remain per-user identity regardless of this flag.

The admin section (`GET/POST /settings/api/admin/coding-guardrails`, `src/debug/settings/admin/coding-guardrails-routes.ts`) surfaces all three fields; the POST body is discriminated: `{ kind:'policy', guardrails }` updates the policy, `{ kind:'shared-key', ... }` stores the shared `agent-provider` vault, `{ kind:'shared-key-clear' }` clears it. The GET response includes `sharedKeySet: boolean` — the key value is **never** returned. The client section `CodingGuardrailsSection.svelte` renders allowed-agents checkboxes, who-may-use radio + textarea, force-shared-key toggle, and the shared-key credential fields.

## Group-session identity (Phase 5b)

A per-group `coding_identity` policy (`authorized_groups.coding_identity`, migration `065`, default `'initiator'`) controls whose credential vault a group coding session reads. Three values:

- **`initiator`** (default) — the acting user's own personal context (keyed by `toScopedContextId({ platformInstanceId, nativeContextId: chatUserId })`). Each user must have their own key/forge/agent configured; the group vault is never consulted.
- **`shared`** — the group config-context vault, as in pre-Phase-5b behavior. Useful when a single shared team key is intentional.
- **`designated:<userId>`** — a named group member's personal context. The settings UI validates that `<userId>` is an actual group member (422 otherwise); the designee's absence from the group is a save-time error.

`identityContext(storageContextId, chatUserId)` in `src/coding-credentials/resolve-agent-secrets.ts` resolves the effective context from the policy and threads it through all five resolvers (`resolveAgentSecrets`, `resolveProviderHost`, `resolveForgeToken`, `resolveForge`, `resolveAgent`) via `buildCodingSecretsFacade`. For DM contexts, `getGroupCodingIdentity` returns the `'initiator'` default (no `authorized_groups` row), so `identityContext` resolves to the DM's own config-context — **byte-identical** to pre-Phase-5b behavior.

5a's `forceSharedKey` still overrides **only** the provider key and host (`resolveAgentSecrets`/`resolveProviderHost` use `sharedKeyContext(storageContextId) ?? identityContext(...)`); forge credentials (`resolveForgeToken`, `resolveForge`) always follow the identity context regardless. When no creds are found for the resolved identity, `start_session` and `review_pr` **refuse** with `error: 'not_configured'` — they never fall back to another vault. The refusal message is always phrased as "your" credentials, since even a designated-identity refusal is that identity's missing creds (not the caller's problem to debug differently).
