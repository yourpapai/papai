# ACP Coding Sessions

> Referenced from `CLAUDE.md`. The `plugins/acp/` plugin and its integration with the external **magi** control service, including credentials, forge connections, and operator/group guardrails.

ACP coding sessions (`plugins/acp/`): a thin first-party plugin exposing LLM tools (start/list/status/finish/cancel a coding session, answer a permission, review a PR, list projects/agents), an `/acp` command, and a prompt fragment. It is a stateless HTTP client of the external **magi** control service (admin-scoped `magi_base_url` + sensitive `magi_token` plugin config; outbound via `providerRuntime.httpFetch`, with the admin base URL allowlisted through `providerAllowedHostsFromConfig`). It injects the chat's **thread-scoped** `storageContextId` as the magi session `contextId` — so magi's milestone notifier posts back to `/api/notify` and `buildNotifyTarget` re-derives the thread, delivering the notification to the originating thread rather than the group channel. (The plugin runtime receives the raw thread-scoped id even though the manifest sets `storageScope: 'group'`; the group scope only remaps `plugin_kv`, keeping `list_sessions` shared across a group's threads.) Because plugin source cannot static-import bare modules (discovery rejects them), the tools use raw JSON-Schema `inputSchema` with manual guards instead of Zod. The `coding_session_credentials` vault has two namespaces: **`agent-provider`** (the sandboxed agent's LLM key and choice of coding agent, supplied per-session via the `coding.secrets`-gated `codingSecrets` capability; `start_session` and `review_pr` refuse with `error: 'not_configured'` when empty) and **`forge`** (the user's code-host token — GitHub/GitLab PAT — stored in the settings-UI "Code host" section; `finish_session` and `review_pr` refuse with `error: 'not_configured'` when unconfigured, preventing push/PR without the user's identity; `start_session` includes the token when present and does not require it for SaaS repos (magi derives the forge), but **pre-flights self-hosted repos** — when the repo host is not SaaS-derivable (`canDeriveForge`, `plugins/acp/tools.ts`) and no forge is configured, it refuses with `error: 'not_configured'` rather than letting magi 400). No host/global forge token is used or expected on the magi side.

## Agent/provider picker (Phase 4a/4c)

The `agent-provider` namespace has four fields: `agent` (enum: `claude`/`codex`/`opencode`; default `claude`), `provider` (enum: `anthropic`/`openai`/`openai-compatible`), `provider_api_key`, and `provider_base_url`. A `compatible(agent, provider)` rule constrains valid pairs: claude→anthropic only; codex→openai or openai-compatible; opencode→any. The `openai-compatible` provider targets any OpenAI-compatible endpoint (e.g. a self-hosted LLM proxy) and **requires a `provider_base_url`** — the route 422s without one. The settings-UI **AI provider** section renders `agent` and `provider` as `<select>` dropdowns (controlled by `control: 'select'` + `options` metadata from the route); the provider dropdown is client-side filtered to only the options compatible with the currently-selected agent; when `openai-compatible` is selected the base-URL field shows as required. The section saves as a **whole record**: selecting a value only updates the local draft (changing the agent resets the provider draft to the first compatible option), and one Save button PATCHes all fields together — untouched masked secrets are omitted so the store preserves them — so the route's cross-field validation (compatibility + base-URL presence for `openai-compatible`, 422 on violations) always sees a complete, consistent record. (Per-field auto-save previously 422'd when a field was saved before its cross-field dependency — e.g. `openai-compatible` before its base URL — silently dropping the field.) A **Clear** button (rendered only when the section reports `configured`) removes the whole `agent-provider` vault for the context via `PATCH /settings/api/coding-credentials { clear: true }` behind a `danger` confirm dialog — the same scope-checked route/`clearCodingCredentials` primitive the admin `shared-key-clear` uses, but keyed to the per-user/group identity context rather than the operator vault. `resolveAgentSecrets` maps `provider→{ANTHROPIC_API_KEY,OPENAI_API_KEY}`; `resolveAgent` returns the stored agent (default `null`); `resolveProviderHost` derives the model hostname from provider + base URL (e.g. `openai-compatible` + `https://llm.corp.com/v1` → `llm.corp.com`). The acp plugin reads all three via `codingSecrets` and carries `agent` and `providerHost` in the `projectSpec` sent to magi. All three coding agents — **claude**, **codex**, and **opencode** — are now functional in the self-serve model.

## Derived sandbox egress (Phase 4c)

magi derives the per-session sandbox egress from the `projectSpec`: operator base ∪ `providerHost` (from `resolveProviderHost`) ∪ agent-infra (codex→`chatgpt.com`, opencode→`models.dev`). This **narrows** the prior broad default and makes custom `openai-compatible` endpoints reachable within the operator's geofront ceiling. The repo host is **not** included in the sandbox egress (the agent cannot auth to the forge anyway). A session using an `openai-compatible` endpoint whose host is not in the geofront ceiling will fail to reach the model; the operator must widen the ceiling to admit that host.

Each project may also carry `additionalEgressDomains` (set in settings → Repositories):
bare hostnames that are **added to** the derived per-session egress (operator base ∪
`providerHost` ∪ agent-infra). They are additive only — a user cannot remove the
derived set, only append candidates. Note: an added domain is still subject to the
operator's geofront egress **ceiling** (`[egress.policy.ceiling]` in `org.toml`); a
domain outside the ceiling is silently dropped, so the operator must widen the
ceiling to admit it.

## Sandbox MCP broker (Phases 1-3A)

Lets a sandboxed coding agent use a credential-bearing upstream MCP server without the credential ever entering the sandbox or widening the agent's egress (design D; spec `docs/superpowers/specs/2026-07-05-sandbox-mcp-broker-design.md`).

**Transport (Phase 1).** When MCP is enabled for a session, the agent's ACP `mcpServers` config declares a dumb `mcp-tunnel` binary that the agent spawns itself; the tunnel dials a bind-mounted host unix socket (`--mcp-mount` → `/run/magi/mcp.sock` inside the sandbox), which magi-main's mediator accepts on the host side. Because this relies on a bind-mounted socket, magi and the sandbox must share a kernel — native Linux/CI only, not VM-backed docker (e.g. macOS Docker Desktop).

**Worker (Phase 2).** magi launches a **second** geofront enclosure per MCP-enabled session (`AgentKind::Other`, entrypoint `mcp-worker`) with kernel-enforced egress restricted to the upstream MCP host only. The upstream credential is staged into this worker (never the agent sandbox) via a `magi-init` secret manifest and shredded after read. The worker is driven over its stdio via geofront's `--acp` relay and translates stdio-MCP → HTTP-MCP: each request becomes an opaque POST to the upstream with the credential injected, behind a fail-closed host allowlist, no redirects, TLS verification, and size/time caps. magi-main itself is a dumb byte relay between the mediator connection and the worker's control socket — it never parses MCP traffic.

**Invariants.** INV-1: the upstream credential never enters the agent sandbox. INV-2: the agent gains no new egress — the worker's restricted egress lives in a separate enclosure. Both magi-main and the worker treat upstream request/response bodies as opaque.

**Config (Phase 3A, per-identity vault — env config retired).** The worker's upstream URL + credential now come from a new `mcp` namespace in papai's `coding_session_credentials` vault (fields `upstream_url`/`upstream_header`/`upstream_token`), alongside the existing `forge`/`agent-provider` namespaces — it rides the generic `coding-credentials` route and is unrelated to the orchestrator's `McpSection`/`mcp_endpoints` feature (`src/mcp/`). `resolveMcp`/`resolveMcpToken` (`src/coding-credentials/resolve-agent-secrets.ts`) resolve it per-identity (honoring the `coding_identity` group policy, mirroring `resolveForge`/`resolveForgeToken`): `resolveMcp` returns the non-secret `{url,host,header,allowedHosts}`; `resolveMcpToken` returns the credential separately. `buildSessionProjectSpec` (`plugins/acp/tools.ts`) adds the non-secret result as `projectSpec.mcp`; `startSessionTool` adds `mcpToken` to the `/sessions` POST body as a sibling field (like `forgeToken`, never inside the spec). magi re-validates `projectSpec.mcp` at the trust boundary (`validateRepoSpec`, fail-closed: https + host in `policy.allowedHosts`) and now sources the worker's `WorkerConfig` + credential + the MCP enable-gate (`spec.mcp !== undefined`) from the validated session spec instead of `process.env` — no magi-main path reads `MAGI_MCP_UPSTREAM_*`/`MAGI_MCP_TUNNEL_SERVERS` anymore. INV-1 is unchanged: the credential still rides the same staged-secret channel as the coding-agent/forge credentials, into the worker enclosure only. Only a single upstream per session is supported today; multi-server multiplexing is a follow-up. The operator catalog, the settings-UI section, and magi-side per-tool gating/audit are **Phase 3B**, not yet built.

**Cost.** Each MCP-enabled session costs two geofront enclosures (agent + worker), each with its own egress proxy. Sessions with MCP disabled are unaffected — no mediator or worker is started.

## Typed forge connections (Phase 4b)

The `forge` namespace has three fields: `kind` (enum: `github`/`github-enterprise`/`gitlab`/`gitlab-self-hosted`; rendered as a `<select>` in the settings-UI **Code host** section), `instance_url` (text; shown only when `needsInstanceUrl(kind)` — i.e. `github-enterprise` or `gitlab-self-hosted`; hidden for SaaS kinds), and `forge_token` (sensitive; rendered masked). `deriveApiBaseUrl(kind, instance_url)` maps the UI kind to an API base URL (`https://api.github.com`, `https://gitlab.com/api/v4`, or `<instance_url>/api/v3|v4`). `forgeMagiKind` maps UI kinds to magi's two-value enum (`github`|`gitlab`). `resolveForge` reads the vault and returns `{ kind, apiBaseUrl }` — `null` when unconfigured, **and `null` for a partial vault** (`instance_url` present but `kind` missing) rather than silently mis-deriving GitHub SaaS and ignoring the instance URL; a legacy token-only vault with neither `kind` nor `instance_url` still defaults to `github`. The acp plugin carries the result as `projectSpec.forge`. The route validates: `kind` must be a known `FORGE_KINDS` member (422 on unknown); when `needsInstanceUrl(kind)`, `instance_url` must be present and start with `https://` (422 otherwise). The **Code host** section saves as a **whole record** (kind + instance_url + token in one PATCH), matching that cross-field validation — saving fields individually previously 422'd when `kind` was set before `instance_url`, leaving `kind` empty and triggering the `resolveForge` partial-vault guard. A **Clear** button (shown only when `configured`) removes the `forge` vault via the same `{ clear: true }` PATCH behind a `danger` confirm dialog. **Self-hosted instance hosts must be operator-allowlisted** in magi's standalone `MAGI_ALLOWED_REPO_HOSTS` (SSRF gate); the two fixed SaaS API hosts (`api.github.com`, `gitlab.com`) are always admitted for the forge-API check, but the **repo clone host is never exempt** — even SaaS repo hosts (`github.com`/`gitlab.com`) must appear in the allowlist. The allowlist is decoupled from magi's project defaults and **fail-closed** (empty/unset → serve refuses to start).

## Model selection + codex base-URL fix (Phase 4d)

The `agent-provider` namespace has an optional `model` field. It is stored in the **identity context only** — `resolveModel` always calls `identityContext`, so 5a's `forceSharedKey` does **not** override it (unlike `resolveAgentSecrets`/`resolveProviderHost`, which use the shared-key context when forced). The model is carried as `projectSpec.model` — it is **not** part of the `secrets` bundle. magi applies it after `session/new` via ACP `session/set_config_option` (uniform across claude/codex/opencode). `selectModelConfig` matches the requested value against the agent's `configOptions[category=model]` list by value, then by display name. If the model is not offered by the agent, magi logs a warning and uses the agent's default; it never hard-fails on an unknown model.

The settings-UI **AI provider** section renders `model` as a `combobox` control: a free-text `<input list>` backed by a `<datalist>` populated by the new `GET /settings/api/coding-credentials/models` route (`src/debug/settings/coding-credentials-models-route.ts`). That route is a server-side proxy to the provider's `/v1/models` endpoint; it reads the stored key and base URL from the vault (key never returned to the client), calls `assertPublicUrl` + `redirect:'error'` for SSRF defense, and handles both OpenAI-shaped (`{ data: [{ id }] }`) and Anthropic-shaped responses. For opencode, model ids are prefixed with the provider name (`openai/gpt-5`, `anthropic/claude-sonnet-4-6`) because opencode uses `provider/model` routing; custom `openai-compatible` endpoints receive no prefix. The route degrades to `{ ok: false, models: [] }` on any error — the combobox falls back to free-text. Changing the agent resets the model draft to blank (the prior agent's model ids are unlikely to be valid for the new one). Model validation on save: max 200 characters, no control characters; the route 422s on violations.

**Codex base-URL fix.** Codex reads its provider base URL from `~/.codex/config.toml` (it ignores `OPENAI_BASE_URL`). magi now generates this file from the configured base URL via `generateCodexConfigToml` (`src/runtime/geofront/provisioning/codex-config.ts`), which emits a `[model_providers.custom]` section with `env_key="OPENAI_API_KEY"` and `wire_api="chat"`. The file is staged through the provisioning manifest's `file` kind (not an env secret target). The previous `OPENAI_BASE_URL` env secretTarget in the codex preset was a no-op and has been removed. When no base URL is configured the file is not staged and codex uses its built-in default.

**Router agent reconciliation.** magi's `/sessions` router now derives the launch agent from the validated `projectSpec.agent` rather than the unvalidated top-level `body.agent`. The two values were always supposed to be identical, but the unvalidated read bypassed `validateRepoSpec`'s agent allowlist check, making 5a's `allowedAgents` guardrail ineffective at the launch layer. The validated spec is now the single source of truth.

## Operator guardrails (Phase 5a)

A per-platform-instance policy (`__admin_coding_guardrails__:<platformInstanceId>` context key `coding_guardrails`, read/written by `src/coding-credentials/guardrails.ts` via `getCachedConfig`/`setCachedConfig`) bounds coding-session self-serve with three fields, all defaulting to allow-all / reference-identical when unset:

- **`allowedAgents`** (`string[]`, default `['claude','codex','opencode']`) — which coding agents users may pick. The agent-picker in the settings-UI **AI provider** section filters its `<select>` options to this list (A1). magi **re-enforces** this at `/sessions` and `/reviews` via `validateRepoSpec` → rejects with `agent not permitted: <agent>` (B1).
- **`whoMayUse`** (`'members' | string[]`, default `'members'`) — who may **start** a coding session. Enforced host-side in `buildFullToolSet` (`src/llm-orchestrator-tools.ts`) via `applyWhoMayUseFilter`: when `'members'`, the filter is a reference-identical pass-through; when an allowlist, actors whose `chatUserId` is not listed have the five ACP session-action tools (`plugin_acp__start_session`, `__review_pr`, `__finish_session`, `__cancel_session`, `__answer_permission`) silently removed from their tool set — read-only tools like `plugin_acp__list_sessions` / `__session_status` are kept. Guests are already excluded by `applyGuestReadOnlyFilter` (runs first). `platformInstanceId` is derived via `parseScopedContextId`; unscoped context IDs are not gated.
- **`forceSharedKey`** (`boolean`, default `false`) — when true, `resolveAgentSecrets` and `resolveProviderHost` read the operator-stored `agent-provider` vault at `adminCodingGuardrailsContextId(pi)` instead of the user's own config-context (A2). Forge credentials (`resolveForgeToken`, `resolveForge`) always remain per-user identity regardless of this flag.

The admin section (`GET/POST /settings/api/admin/coding-guardrails`, `src/debug/settings/admin/coding-guardrails-routes.ts`) surfaces all three fields; the POST body is discriminated: `{ kind:'policy', guardrails }` updates the policy, `{ kind:'shared-key', ... }` stores the shared `agent-provider` vault, `{ kind:'shared-key-clear' }` clears it. The GET response includes `sharedKeySet: boolean` — the key value is **never** returned. The client section `CodingGuardrailsSection.svelte` renders allowed-agents checkboxes, who-may-use radio + textarea, force-shared-key toggle, and the shared-key credential fields.

## Group-session identity (Phase 5b)

A per-group `coding_identity` policy (`authorized_groups.coding_identity`, migration `065`, default `'initiator'`) controls whose credential vault a group coding session reads. Three values:

- **`initiator`** (default) — the acting user's own personal context (keyed by `toScopedContextId({ platformInstanceId, nativeContextId: chatUserId })`). Each user must have their own key/forge/agent configured; the group vault is never consulted.
- **`shared`** — the group config-context vault, as in pre-Phase-5b behavior. Useful when a single shared team key is intentional.
- **`designated:<userId>`** — a named group member's personal context. The settings UI validates that `<userId>` is an actual group member (422 otherwise); the designee's absence from the group is a save-time error.

`identityContext(storageContextId, chatUserId)` in `src/coding-credentials/resolve-agent-secrets.ts` resolves the effective context from the policy and threads it through all five resolvers (`resolveAgentSecrets`, `resolveProviderHost`, `resolveForgeToken`, `resolveForge`, `resolveAgent`) via `buildCodingSecretsFacade`. For DM contexts, `getGroupCodingIdentity` returns the `'initiator'` default (no `authorized_groups` row), so `identityContext` resolves to the DM's own config-context — **byte-identical** to pre-Phase-5b behavior.

5a's `forceSharedKey` still overrides **only** the provider key and host (`resolveAgentSecrets`/`resolveProviderHost` use `sharedKeyContext(storageContextId) ?? identityContext(...)`); forge credentials (`resolveForgeToken`, `resolveForge`) always follow the identity context regardless. When no creds are found for the resolved identity, `start_session` and `review_pr` **refuse** with `error: 'not_configured'` — they never fall back to another vault. The refusal message is always phrased as "your" credentials, since even a designated-identity refusal is that identity's missing creds (not the caller's problem to debug differently).

## Follow-up coding sessions

A `continue_session({ sessionId?, prNumber?, project?, prompt })` tool (`plugins/acp/continue-tool.ts`) lets a chat keep iterating on a prior session's branch/PR instead of starting a fresh one. The target resolves to a parent session id in one of two ways: directly via `sessionId`, or by `prNumber` (+ optional `project`) matched against magi's done-list (`GET /sessions?filter=done`) — matching is **scoped to sessions this chat started**, i.e. only rows with a locally-known `plugin_kv` record are considered, so a chat cannot target another chat's session by guessing a PR number. `continue_session` requires **both** coding secrets and a forge token (via the same `codingSecrets` capability as `start_session`/`review_pr`); it refuses with `error: 'not_configured'` otherwise, since a follow-up always needs to push back to the existing branch/PR. On success it records the child session locally, inheriting the parent's `prNumber`/`prUrl`.

**History index.** The `plugin_kv` value at key `session:<id>` (`plugins/acp/history.ts`) is a JSON `SessionRecord` (`project`, `title`, `createdAt`, optional `parentSessionId`, `prNumber`, `prUrl`, `status`) rather than the legacy `"1"` marker used pre-follow-up; `readRecord` still tolerates the legacy marker (returns `null`, treating it as "no record" rather than erroring). `start_session` and `review_pr` write these records; `list_sessions` merges each magi row with its local record — adding `title`/`parentSessionId`/`prNumber` to the response — and opportunistically refreshes the local record's `status`/`prUrl`/`prNumber` from magi's latest view as a side effect of listing, with no additional notify wiring.

**magi `POST /sessions/:id/follow-up`** (`{ prompt, secrets?, forgeToken? }`, `src/server/router.ts`): loads the parent session and re-validates its stored `projectSpec` against the current operator policy (`validateRepoSpec`) — so a guardrail tightened after the parent session started still applies to the follow-up. Only parent sessions in a **continuable** status (`waiting_input`/`done`/`failed`/`cancelled`, `CONTINUABLE` in `src/session/state.ts`) may be continued; an active parent is refused with `409`. `manager.followUpSession` creates a CHILD session (`parentSessionId` set) that reuses the parent's `branch`, `projectSpec`, and `prUrl`; `buildFollowUpPrompt` (`src/session/helpers.ts`) prepends the parent's original prompt and final answer (each clipped to 4000 chars) as context ahead of the new prompt. The run is launched via `WorkspaceManager.prepareContinue`, which checks out the **existing branch** instead of branching from `baseBranch`, and finishes by pushing back to that **same branch** — updating the existing PR. A **PR-reuse guard** (`session.prUrl ?? openPullRequest(...)` in `autoPublishDirty`) skips opening a duplicate PR since the child inherits the parent's `prUrl` at creation.

`continue_session` is gated by the Phase-5a `whoMayUse` operator guardrail like the other session-action tools (it is in `ACP_SESSION_ACTION_TOOLS`, `src/llm-orchestrator-tools.ts`) — actors off the allowlist lose it along with `start_session`/`review_pr`/`finish_session`/`cancel_session`/`answer_permission`.

**Documented limitations / future work.** A merged/closed PR is **not** detected before continuing (magi has no `getPullRequest` yet — continuing a session whose PR was already merged/closed will push to a branch with no open PR to update). Continuing an arbitrary/non-papai PR by number is **not** supported — only sessions this chat started can be resolved by `prNumber`. Auto-fetching CI/check status to feed failures into the follow-up prompt is future work; today the follow-up sandbox has the branch checked out and the agent is expected to run the build/tests itself.

## Transcript viewer

magi mints an opaque `shareToken` + `transcriptUrl` (papai's public origin, per `MAGI_TRANSCRIPT_BASE_URL` — a **magi-side** setting) when a coding session is created, and embeds the URL in the PR it opens. `shareFieldsOf` (`plugins/acp/tools.ts`) lifts both fields off `start_session`/`review_pr` responses; `session-records.ts` persists them on the `SessionRecord` (`plugins/acp/history.ts`), and `list_sessions` (via `enrichSession`) surfaces `transcriptUrl` back into the tool result. The `/acp` prompt fragment (`plugins/acp/index.ts`) nudges the model to include the link in its reply whenever one comes back, so the user can watch the session live and share it.

Serving is entirely in core, not the plugin: `src/debug/transcript-viewer.ts` exposes `/t.js`, `/t.css`, `/t/<token>` (the SPA shell), `/t/<token>/transcript` (paginated JSON history proxy), and `/t/<token>/stream` (SSE proxy) — all mounted in `src/debug/server.ts` **before** the dashboard session-cookie auth gate. These routes are deliberately public and unauthenticated: possession of the opaque token _is_ the access control, mirroring magi's own token-scoped endpoints. The viewer is read-only — approvals and other session actions stay in chat, never in the browser.

The proxy reads `magi_base_url`/`magi_token` from the acp plugin's admin config (`getPluginAdminConfig('acp', …)`, `getViewerMagiConfig`) and forwards a bearer-authed request to magi's matching `/t/:token/{transcript,stream}` endpoints, rewriting only the response headers/body — magi's base URL and token never reach the browser. The stream proxy deliberately does **not** go through the shared `providerRuntime.httpFetch` (which caps requests at 30s) — coding sessions run far longer — and instead binds the upstream fetch directly to the client's own `req.signal`, so the connection lives exactly as long as the browser tab does and cleans up the moment it disconnects.

The client SPA (`client/transcript/`, bundled as `transcript.js`/`.css`/`.html` via `scripts/build-client.ts`) fetches paged history and opens the SSE stream in parallel, then stitches both sources into one ordered timeline by event `seq` (`mergeBySeq`, history wins on a seq collision). A runes-based state store drives reconnect/self-heal on stream drop — it re-opens the SSE connection and re-fetches any history gap rather than surfacing a dead viewer.

**Residual risk.** The transcript is the raw, unredacted session log — treat a `transcriptUrl` as a bearer secret; anyone with the link can read the full session. There is no per-event redaction and no revocation/expiry on the papai side today; both are deferred to magi, since magi mints and owns the token's lifetime.
