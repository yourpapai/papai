# Project & Non-Obvious Behaviors

> Referenced from `CLAUDE.md`. Detailed description of papai's runtime model and its non-obvious behaviors.

## Project

papai is a chat bot that manages tasks via LLM tool-calling. A user sends natural-language messages through configured chat platform instances (Telegram, Mattermost, Discord, or Kontur Talk), the bot invokes a configurable OpenAI-compatible LLM (via Vercel AI SDK), executes capability-gated task-tracker tools, and replies. Runtime behavior depends on the source platform instance, assigned task instance, conversation context, and per-user or group-targeted configuration stored in SQLite.

## Notable non-obvious behaviors

<!-- behavior:thread-scoped-contexts -->

- Telegram and Mattermost group contexts are thread-aware via thread-scoped storage context IDs; **Discord group contexts are not thread-scoped**.

<!-- behavior:scope-model -->

- **Scope model:** within a group, _live conversation_ state (history, short-term summary/facts) is **thread-isolated**, while _durable assets and config_ (memos, instructions, recurring tasks, long-term memory, settings, tool prefs, group-discoverable attachments) are **group-shared** across threads. Identity and the web-fetch quota are per-user. Effective scope per entity is declared once in `src/chat/context-scope.ts` (`ENTITY_SCOPES` + `getScopeKey`); the `threadScoped` flag in `scoped-context-owned-columns.ts` describes the raw column, not effective scope, and is reconciled against the registry by a consistency test.
- Chat startup runs through `ChatRouter`, which manages DB-backed platform instances and tags incoming messages/interactions with `platformInstanceId`.

<!-- behavior:settings-only-configuration -->

- **All configuration happens in the settings web UI**, not in chat. `/config` (DM only) issues a single-use link to it; `SETTINGS_PUBLIC_BASE_URL` must be set or `/config` refuses. The `/plugin` and `/set` chat commands are retired. Chat callback config flows (`gsel:`/`cfg:`/`wizard_`/`plg:`/`tgl:`) were removed; `interaction-router.ts` now handles only `perm:`/`edit:`/`lang:` prefixes and is otherwise a safe sink.

<!-- behavior:reply-to-bot-routing -->

- **Telegram and Discord** treat a user's reply to the **bot's own message** in a group as equivalent to an `@mention` — the bot processes it without an explicit mention. Mattermost and Kontur Talk are not affected by this path.
- **Multi-language support (en/ru):** user-facing framework text localizes to a per-config-context `language` preference (`en`|`ru`, default `en`; select field in the settings-UI Profile section; `getContextLanguage` in `src/utils/config-language.ts` resolves it, so it is **group-shared** across a group's threads like the other durable config). Typed catalogs live in `src/i18n/` (`Dictionary` shape, `en` authoritative, `ru` typed and key-parity-tested, `t(key, locale, params)` with `{slot}` interpolation); a missing `ru` key **falls back to `en` with a logged warn** — the raw key is never returned. **First-interaction picker:** the first authorized, non-guest message (or `/start`) from a context with no stored language posts a two-button `lang:en`/`lang:ru` picker via `reply.buttons` and sets the internal `language_prompted` config key (storable but never a `ConfigField`, so invisible in the settings UI); the `lang:` callback route in `src/chat/interaction-router.ts` persists the choice and clears the marker. Buttonless platforms (Kontur Talk) and guests skip the picker; the bot never re-asks after the marker is set. **Localized surfaces:** the system prompt (assembled from the catalogs' `systemPrompt` fragments — the old "in the user's language" mirror is replaced by an explicit answer-in-`<locale>` instruction; tool names/parameter keys/JSON examples stay verbatim), verified-completion verifier prompt + neutral fallback, command replies (help/config/context/clear/dashboard/stop/start), unauthorized-reply texts, tool progress lines, steer/stop acks, interaction-failure replies, the admin release-announcement notice, the live-status indicator texts (thinking placeholder, per-tool labels, preparing placeholder — `liveStatus.*`), and the `/context` view (section labels, fact/message counts, progressive-disclosure line, and per-platform renderer chrome — `contextView.*`; sections carry stable machine `id`s so the emoji grid/legend key on ids, and digit grouping stays `en-US` in every locale). The turn's locale is derived at each localized surface from the storage context id via `getConfigContextIdFromStorageContextId` (`src/chat/scoped-context.ts`) — equivalent to the message's config context — or read straight off the auth result's `configContextId` where one is at hand.

<!-- behavior:identity-provisioning -->

- Settings-UI admin "Users" adds accept `@username`. Live resolution is tried first (`resolveSettingsUserId`); when the platform cannot resolve it (Telegram's Bot API never can for user accounts), a **pending entry** is stored (`users.platform_user_id = 'placeholder-<uuid>'`) and rebound case-insensitively to the real ID on the user's first DM (`src/auth.ts` → `resolveUserByUsername`). Group-member adds stay strict and 422 on unresolvable usernames. Open DM access is a per-platform-instance toggle (admin "Users" section → `open_dm_access` column). When on, an unknown user's first DM auto-provisions a `users` row (`added_by = 'open-access'`) and is granted normal DM auth; admins can durably block individuals (`users.blocked_at`). It replaces the removed `DEMO_MODE` env flag.

<!-- behavior:guest-readonly -->

- **Guest mode** is a per-_group_ toggle (`authorized_groups.guest_mode`) enabled by bot or group admins in the settings UI group section. When on, any user in an authorized group who is otherwise unrecognized (not admin/member) is allowed as a **guest**: identified by `AuthorizationResult.isGuest` → `actorRole: 'guest'` threaded through the queue/orchestrator, given a hardcoded **read-only** toolset (`applyGuestReadOnlyFilter`, read-risk tools only, bypassing `tool_prefs`), and excluded from long-term memory capture/extraction. Guests are **never** provisioned into `users`/`group_members` (so they never become members). v1 abuse control is toggle-off.
- **On-demand next-task ranking (`suggest_next_task`):** answers "what should I work on next?" with a deterministic, explainable ranking of the context's open tracker tasks — overdue magnitude, due windows (≤48h, ≤7d), stacking priority tokens, and a creation-recency fallback, each suggestion carrying a one-line `reason` built only from the facts that scored (pure `rankTasks` in `src/tools/suggest-next-task-ranking.ts`). Read-only: no tracker mutation. Registered beside `list_tasks` whenever a task instance is configured (DM and group, normal and proactive modes), classified `read('task')` so its default `tool_prefs` permission is `allow` and it stays available in the guest-mode read-only toolset; standard allow/ask/deny resolution still applies. Without an explicit `projectId` it fans out over the instance's projects (p-limit 3, dueDate-ascending page per project); when the provider cannot list projects it returns `project_required` guidance instead of an error, and `assigneeId: 'me'` reuses the identity-resolution path (`identity_required` guidance when unresolvable).
- Supports incoming files, file-to-task relay, identity mapping, memo search, recurring tasks, deferred prompts, public web fetch.

<!-- behavior:alert-edge-triggering -->

- **Alert edge-triggering:** each alert stores the set of matching task IDs and fires only when a task newly enters (or, after leaving, re-enters) the recorded match set — a task leaving the match updates the recorded set without firing (`collectFieldFirings` in `src/deferred-prompts/poller-alerts-watch.ts`). After deploying migration 069, every alert's stored match set starts empty, so each alert fires once for all currently-matching tasks on its first eligible cycle (respecting cooldown), then edge-triggered semantics take over. **Pure per-task watches are the exception:** an instance whose active routable alerts are all pure watch conditions (`task.id`-`eq`-only trees, `isPureWatchCondition` in `src/deferred-prompts/condition-eval.ts`) never lists projects/tasks — `fetchAlertTasks` partitions the instance and fetches only the deduped union of watched ids via `getTask` (`fetchWatchedTasks`, bounded concurrency 4, not-found ids skipped with a warn, any other failure aborts the cycle without state or snapshot updates). Because `getTask` returns full tasks, all snapshot fields (incl. assignee/labels) participate. A pure watch fires when a matched watched task has a **snapshot-visible change** (`watchTaskChanged`/`collectPureWatchFiring` in `src/deferred-prompts/poller-alerts-watch.ts`), not on match-set edges; a task with no stored snapshot is a baseline sighting that records state without firing, and cooldown still gates refires. Any field-filter (non-watch) alert on the same instance keeps the whole-list path (with enrichment) verbatim, and composed `task.id` + field conditions keep matched-set edge semantics. Activity watches extend the same targeted partition — see the activity-watches bullet below.
- **Alert activity watches (migration 082):** an alert whose condition is a pure activity tree (`{ kind: 'activity', taskId, categories? }` leaves only — trees mixing activity with field leaves are refused at create and at condition update by `src/deferred-prompts/activity-gating.ts`) is edge-triggered on task-history entries instead of snapshots. **Creation is gated:** `create_alert` accepts an activity leaf only when the delivery context has a configured (non-null) task instance whose provider exposes activity reading (`activities.read` + `getTaskHistory`, threaded fail-closed from assembly); otherwise the call is refused with the standard `{ error }` guidance shape — tracker without task history, or no task instance configured — steering the model back to field conditions (`activitySupportError` in `src/deferred-prompts/activity-gating.ts`; the capability gate is create-only, so a tracker losing the capability afterwards degrades to the poll-time skip-and-warn path below). Each alert stores a `last_activity_cursor` (`alert_prompts.last_activity_cursor`, reset to null when the condition is edited); the **first poll baselines** the cursor to the newest visible entry without firing, later polls fire on entries **strictly newer** than the cursor, and the cursor plus `lastTriggeredAt` advance **only after successful delivery** (`updateAlertActivityState`) — a failed narration of a pure-activity batch sends no error chatter and retries the same entries on the next poll, so entries are never lost. Entries with unparseable timestamps are skipped with a warn; entries at or below the cursor never refire. **Cooldown catch-up** — a suppressed alert is skipped by the eligibility filter without touching its cursor, and the next eligible poll fires everything accumulated since the last delivery. History is fetched per instance as the deduped union of watched task ids via `provider.getTaskHistory(taskId, { categories })` (`src/deferred-prompts/poller-alerts-activity.ts`: bounded concurrency 4 inside the instance scope lease; per-task categories are the sorted union across leaves, with a categories-less leaf dropping the filter and per-leaf filtering applied client-side); a poll-time capability re-check (method or `activities.read` missing) skips that instance's activity alerts with a warn and leaves cursors untouched. **Activity-only instances skip the whole-list fetch:** the instance partition that used to be "all pure watches" is now "all targeted" (pure watch ∪ pure activity, still computed on the full active set so cooldown entries cannot flip the fetch mode), so such instances make no `listProjects`/`listTasks`/`searchTasks` calls; any field-filter alert on the instance keeps the whole-list path verbatim with history fetched alongside. Activity firings join the same per-context firing batch as field alerts, and their summary wraps author/category/field/added/removed in the shared external-data boundary (`buildActivitySummary` in `poller-alerts-activity.ts`).
- **Alert task-instance pinning (migration 081):** every alert stores the task instance it was created against (`alert_prompts.task_instance_id`, FK → `task_instances` `ON DELETE CASCADE`). **Capture** — `createAlert` in `src/deferred-prompts/tool-handlers.ts` resolves the delivery target's config context (`getConfigContextIdFromStorageContextId`, so a thread-scoped group delivery pins to the parent group's assignment) and stores `getContextSettings(configContextId)?.taskInstanceId ?? null`; a context with no instance stays NULL. **Evaluation** — `pollAlertsOnce` groups alerts by effective instance (`alert.taskInstanceId ?? context-settings instance ?? null`, `groupAlertsByInstance` in `src/deferred-prompts/poller-alerts-grouping.ts`); a pinned alert is evaluated against its pinned instance's provider (`TaskProviderResolver.resolveForInstance(contextId, taskInstanceId)` via the production `resolveProductionTaskProvider`, context-scoped credentials still from the context), **not** the context's current assignment — switching a group's tracker does not silently retarget existing alerts. **NULL-pin semantics** — an unpinned alert behaves as before: it follows the context's current instance from settings, and an unresolvable provider keeps the legacy warn-and-retry (stays eligible for later cycles). **Auto-cancel** — an alert whose non-null pin no longer resolves (instance stopped, plugin gone, config invalid) is cancelled (`cancelActiveAlertsPinnedToInstance`, info log) and skipped, because it can never come back by re-editing the context. **Cancel paths** — switching a context's task instance in the settings UI (old ≠ new) cancels active alerts pinned to the old instance whose delivery resolves into that config context (`handlePatch` in `src/debug/settings/context-task-instance-routes.ts`); deleting a task instance cancels all its pinned alerts across every delivery context *before* the row removal (`handleTaskInstanceDelete` in `src/debug/settings/admin/instances-routes.ts`), so each gets a `cancelled` status and audit log line rather than vanishing via the FK cascade.
- **Prompt-injection boundary (`src/security/prompt-boundary.ts`, always on, no config flag):** third-party-writable text that enters LLM prompts — alert-summary task titles/urls/statuses (`buildAlertSummary` in `src/deferred-prompts/poller-alerts-summary.ts`, which also prepends one framing line telling the model that delimited content is data, not instructions; activity entries get the same treatment via `buildActivitySummary`) and memory-fact identifier/title/url (`renderEntity` in `src/memory-context-block.ts`, no framing line — the `<memory trust="compacted_low">` guidance already carries trust) — is sanitized (boundary-forging `<external-data` sequences stripped, newlines collapsed, capped at 500 chars) and wrapped as `<external-data token="…" kind="…">…</external-data>`. The `token` is crypto-random **per process**, never logged, never derived from content, so tracker users cannot forge a closing boundary; sanitizing before wrapping means forgery attempts are neutralized while the payload text itself is preserved. Authorized users' chat messages are deliberately **not** wrapped (the auth gate already limits senders; residual risk is self-injection only).

<!-- behavior:repo-catalogue -->

- **User-defined repo catalogue (`coding_session_repos`):** a plain (non-encrypted) per-context table of repos (name, repoUrl, baseBranch, permissionPreset). CRUD route `GET`/`POST`/`DELETE /settings/api/coding-repos`; settings-UI **Repositories** section (Advanced group). The acp plugin's `list_projects` reads this catalogue and `start_session`/`review_pr` resolve a repo name → inline `projectSpec` sent to magi. **magi has no static project registry** (`InMemoryProjectRegistry`/`MAGI_PROJECTS` removed); the inline `projectSpec` is the sole project source, validated against magi's repo-host SSRF gate (a standalone operator allowlist `MAGI_ALLOWED_REPO_HOSTS` listing permitted repo+forge hosts; SaaS `api.github.com`/`gitlab.com` always admitted; **fail-closed** — empty/unset refuses to serve) and persisted with the session. `projectSpec.forge` is **required or derived from the repo host** (SaaS `github.com`→GitHub, `gitlab.com`→GitLab; self-hosted must be explicit) — magi keeps **no default-forge fallback**.

<!-- behavior:release-announcements -->

- **Version release announcements (opt-in, localized):** on startup `announceNewVersion` (`src/announcements.ts`) extracts the current `## [version]` changelog section, humanizes it **once per locale** via the **central/global** LLM (`src/announcements/humanize.ts`, `resolveAdminLlmConfig` + `main_model`; never BYOK), persists the draft on `version_announcements` (`raw_body`/`humanized_body`/`humanized_bodies`/`broadcast_at`), and DMs the bot admin a **review notice** — it does **not** fan out. Humanization is two-pass with **one shared classify pass** (drops entries with no end-user value; when in doubt, drop) and **one write pass per supported locale** (`en`, `ru`), each from its own prompt: output-language instruction + localized headers ("✨ New"/"⚡ Improvements"/"🛠 Fixes" vs "✨ Новое"/"⚡ Улучшения"/"🛠 Исправления"). Write passes are **failure-isolated per locale** (sequential): a thrown or empty ru pass logs a `warn` naming the locale and is simply omitted — the en body and the overall result survive; only both passes failing yields an empty map. A release with zero surviving entries yields the localized behind-the-scenes one-liner per locale (`announcements.emptyReleaseNote` i18n key) instead of the raw changelog. Bodies live in the `humanized_bodies` JSON column (migration `080`, `{"en":…,"ru":…}`; `z.partialRecord`-validated, unknown locales stripped on write): **no backfill** of historical rows, the legacy `humanized_body` column is dual-written with the `en` body on every en write, and `getAnnouncementDraft` applies legacy coalescing **once at the single read point** — a pre-080 row's `humanized_body` reads back as the `en` body; no consumer touches the JSON column directly. The admin DM uses one `adminLocale` lookup (`getContextLanguage` over the admin's DM scoped id) for both the wrapper (`t('announcements.adminNotice', adminLocale)`) and the body via `selectAnnouncementBody`. The admin reviews/edits/regenerates **per locale** in the settings-UI admin **Release notes** section (`GET/POST /settings/api/admin/release-notes`): a locale switcher with one editor per locale, `save`/`regenerate` carrying `locale: z.enum(SUPPORTED_LOCALES)` (unsupported locale → 422; regenerate runs the pipeline but persists only the requested locale's write pass, failure → 422 leaving the other locale untouched). **Broadcast** (`src/announcements/broadcast.ts`, p-limit, per-recipient idempotency via `announcement_deliveries`, failure-isolated) resolves each recipient's locale live from config — DMs via `getContextLanguage(toScopedContextId({platformInstanceId, nativeContextId: userId}))` (per-user config-context id), groups via `getContextLanguage(groupId)` (group-shared across threads) — and selects the body through the single fallback chain **locale → `en` → raw changelog section** (`selectAnnouncementBody`); dedup keys and delivery isolation are locale-independent. Opt-in is a per-DM toggle (`users.announce_subscribed`, self-serve) and a per-group toggle (`authorized_groups.announce_subscribed`, group-admin) surfaced as the settings-UI **Release announcements** section (`GET/PATCH /settings/api/release-subscription` and `/settings/api/group/release-subscription`); default off, no backfill for past versions. This is **distinct** from the admin **Announce** section (`/settings/api/admin/announce`), a manual free-text broadcast to **all** users with no opt-in and no group support.

<!-- behavior:mid-run-control -->

- **Mid-run steering & interruption (always on):** while an agent turn runs, a non-command message (DM, or group `@mention`/reply-to-bot) is **injected at the next tool-step boundary** to steer the live run — never restarting it, with an instant code-generated `✋` ack. State lives in `src/run-control/` (a `RunRegistry` keyed by `storageContextId`; one active run per context). The `/stop` command is the deterministic stop ladder: a typed "stop" lets the model wind down; first `/stop` flips a `stopWhen` flag (graceful halt after the current tool step); a second `/stop` while stopping force-aborts via `AbortSignal`. Partial side-effects are reported honestly (`buildStopSummary`), not rolled back. **One run per thread** — the message-queue different-user fire-and-forget gap was closed — so a steer has one unambiguous target. `/stop`-command only (no buttons); commands bypass the queue, so it reaches a running turn on every platform incl. Kontur Talk.

<!-- behavior:live-status -->

- **Live task status (per-context toggle, default on):** while a turn runs, a single **ephemeral status message** is posted alongside `Typing…` and edited in place to show the executing tool (`💭 Thinking…` between tools; `🌐 Fetching example.com…`, `🔍 Searching memory: "budget"…` during one). When the model's tool phase ends the message is **not** deleted but **frozen to a `💬 Preparing response…` placeholder** `reporter.placeholder(t('liveStatus.preparingResponse', locale))`, which survives any post-turn verification round-trip and is **deleted only immediately before the real reply posts** — closing the gap where neither status nor answer was visible while the verifier ran (`sendLlmResponse`'s `beforeFirstMessage` hook, in `src/llm-orchestrator-send.ts`, dismisses it right before `reply.formatted`). Built from a `ReplyFn.createStatus` → `StatusHandle` (`update`/`dismiss`) capability (Telegram/Discord/Mattermost edit+delete; Kontur Talk omits it). Lives in `src/live-status/`: `tool-status-labels.ts` is a pure label + **allowlisted-argument** registry (only explicitly-mapped fields surface; mcp/plugin/unmapped tools show no argument; entry labels are `liveStatus.tools.*` catalog keys, so the localized `runningTool` fallback covers unregistered tools), and `reporter.ts` (`createLiveStatusReporter(reply, { enabled, locale?, minLabelMs?, now?, schedule? })`) owns the lifecycle, driven by the existing `experimental_onToolCallStart`/`Finish` hooks; created, transitioned to the placeholder, and dismissed in `invokeWithLiveStatus` from the **unwrapped** reply so the typing heartbeat is never cancelled. Once the placeholder is shown the reporter is **frozen** — tool-driven engine emits are ignored so it never flickers — and a `finally`-block `dismiss()` guarantees it never hangs if the turn errors. To stop fast tools from flickering, a tool label is **held at least `minLabelMs` (default 1000ms)** before reverting to `💭 Thinking…` — the revert is deferred (not pushed synchronously on tool finish), a new tool start within the window cancels the pending revert and shows its label immediately, and `dismiss()` cancels it; the clock/timer are injectable (`now`/`schedule`, defaulting to `Date.now`/`setTimeout`) so tests are deterministic. Gated per context by the `ai_live_status` setting (settings-UI **AI output** section, default **on** → preserves the historical always-on behavior; **off** leaves only the `Typing…` indicator), read at the **config-context id** (`getAiOutputSettings`) so it shares scope across a group's threads like the other AI-output settings. All status ops are best-effort (errors swallowed); independent of `ai_tool_visibility`. **Localized (en/ru):** every status text resolves from the `liveStatus.*` catalog keys (`💭 Thinking…`/`💭 Думаю…`, tool labels, the preparing placeholder); `invokeWithLiveStatus` resolves the turn's locale once (`getContextLanguage` over the turn's context id) and passes it in the reporter options — the engine receives the resolved idle text as `idleText`, so emitted and compared strings are the same string in every locale, and a mid-run settings change never re-localizes in-flight statuses.

<!-- behavior:chat-participant-resolution -->

- **Chat participant resolution (`resolve_chat_participant`):** in group contexts (provider-backed and providerless), the bot resolves a named person ("Alice") to a chat user ID before populating `delivery.mention_user_ids`. It queries `group_members` ∪ `message_metadata` (recent senders), resolves display names via `ChatRouter.resolveUserLabel` (p-limited, fallback display-name→username→userId), and fuzzy-ranks candidates (exact>prefix>substring). The `resolve_chat_participant` tool (read risk, group-only) is registered only when a `chatParticipantResolver` is injected from `ChatRouter` at startup; the descriptor cache key carries a resolver-scope segment. The system prompt (`GROUP_DEFERRED`) spells out the population procedure. Lives in `src/chat/participants/roster.ts`.

<!-- behavior:privacy-gated-analytics -->

- **Privacy-gated analytics (`src/analytics/`):** four independently gated lanes resolved from the `analytics_policy` singleton plus the `ANALYTICS_KILL_SWITCH` env override (`resolveEffectiveLanes`, `src/analytics/governance/policy-store.ts`): two **local** lanes — `local_aggregate` (the shipping default; closed C0 daily counters/histograms only — no actors, sessions, intent, cohorts, retention, or feature penetration) and `local_pseudonymous` (governed actor-keyed canonical events, requires complete governance fields + both HMAC keyrings, fail-closed) — and two **external** lanes: thresholded aggregate release to reviewed webhook sinks, and external pseudonymous egress, which stays closed (no production sink passes the strict AND of caller-controlled destination idempotency, deterministic reconciliation, and complete per-actor deletion; OpenPanel fails it per `docs/research/analytics-metrics/05-provider-scorecard-and-poc.md`). **Source-to-store flow:** observers at the chat/LLM/tool/command boundaries emit strict-contract source facts → the normalizer rejects anything off-contract and pseudonymizes identifiers with purpose-keyed HMAC → governance eligibility decides per event (mode × basis × preference × role) → canonical `analytics_events` plus exact aggregate epoch contributions → derive jobs materialize sessions/outcomes/intent/features/friction → a fresh-empty allowlisted Metabase snapshot is staged, byte-scanned, and atomically published; egress goes through a nine-state delivery ledger with DNS-pinned HTTPS-only transport. **Identity/scope:** actor keys are purpose-keyed per platform instance (no cross-instance continuity); Discord has no fake threads, so the effective conversation is the channel/DM itself; **guests never produce actor/session/intent/feature rows** — guest activity exists only as aggregate cells gated on ≥10 turns AND ≥10 contexts. **Key domains:** `ANALYTICS_HMAC_KEYRING` pseudonymizes actors/conversations/turns; the separate `ANALYTICS_GOVERNANCE_HMAC_KEYRING` keys collection-eligibility refs, consent fences, and encrypts deletion-target bundles; sink secrets encrypt under `INSTANCE_CONFIG_KEY`; canonical storage carries storage-only physical generations with one persisted active-generation pointer (rekey workflow in `src/analytics/rekey/`). **Retention:** deadline-aware expiry (`expiresAtMs > now` guard at every read/derive/export/snapshot/lease/send boundary, startup purge barrier, earliest-deadline wake); maxima in `src/analytics/retention/expiry-guard.ts` (canonical events 90d, pending delivery 14d, receipts 30d, assessed rollups 400d, rephrase sets 30min in-memory only). **Settings routes:** actor self-service `GET/PUT /settings/api/analytics/preferences`, `POST /settings/api/analytics/{export,withdraw,delete}`; admin `GET/PATCH /settings/api/admin/analytics`, `POST /settings/api/admin/analytics/reconcile`, `POST /settings/api/admin/analytics/sinks` + `…/sinks/:id/{verify,rotate,disable}`. Any UTC day intersecting an `unreconciled_restart_gap` is blocked from dashboard publication, external release, and rollout evidence — crash loss is never estimated. Operations: `docs/operations/analytics-runbook.md` + `docs/operations/analytics-incident-runbook.md`; rollout stage gates are executable in `src/analytics/rollout/stage-gates.ts`.
